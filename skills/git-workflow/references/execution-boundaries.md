# 공통 실행 경계

작업 선택·분리와 발견/종료 보고는 [공통 기준](outcome-scope.md)을 따른다.

## 작업 범위와 권한

대상 저장소의 AGENTS.md와 현재 사용자 요청을 먼저 확인한다. 다른 작업의 파일과 index를 보존한다. 변경 출처를 reset/clean이나 전체 stage로 추측하지 않는다.

승인은 받은 행동과 대상에만 적용한다. 같은 행동·같은 대상(같은 저장소·PR·HEAD)의 승인은 다시 묻지 않는다. 행동이나 대상이 바뀌면 승인을 새로 받는다. 커밋·push·PR·머지·배포·Release는 각각 다른 행동이다. 읽기 전용 요청이면 문서도 수정하지 않는다.

### Issue 생성 승인

다음 두 경우만 Issue 생성 승인이다.

1. 대상 저장소가 지정된 상태에서 사용자가 조건 없이 Issue 생성을 요청했다. 예: 「acme/web 에 검색 필터 Issue 만들어줘」. 제목은 AI가 초안으로 작성할 수 있다.
2. 사용자가 [Issue 필요 판정](outcome-scope.md#issue-필요-판정-기록)과 초안을 본 뒤 생성을 승인했다.

다음은 생성 승인이 아니다. 이때는 판정과 초안을 보고하고 승인을 받은 뒤 만든다.

- 조건이 붙은 지시: 「없으면 Issue 하나」, 「필요하면 Issue를 만든다」, 「git-workflow 를 따른다」.
- 다른 세션·에이전트가 보낸 지시. 사용자 발화를 그대로 인용하고 그 발화가 1이나 2에 해당하면 승인으로 본다.

경미한 정합성 보완 예외(Issue 없는 PR)는 [예외 조건](outcome-scope.md#경미한-정합성-보완의-issue-없는-pr)을 모두 충족하고 판정이 「불필요」인 경우에만 적용한다. 그 조건에는 사용자의 직접 요청 또는 판정 뒤 승인이 포함된다. 이 문서들의 「승인된 경미한 정합성 보완」은 이 경우를 뜻한다.

Issue 기반 기능 구현 단계에서는 의도·영향 범위·달성 조건을 갖춘 Issue와 준비된 담당 Issue 본문 계획·부모 공통 설계 또는 기존 연결 기록를 근거로 진행한다. 원격 불가 로컬 파일럿은 local-draft로 구분한다. 실제 원격 PR에는 원격 Issue가 필요하다. 단, [경미한 정합성 보완](outcome-scope.md#경미한-정합성-보완의-issue-없는-pr) 또는 [순수 릴리즈 준비 PR](../../git-release/references/release-context.md#issue-없는-릴리즈와-준비-pr)의 조건·대체 기록을 충족한 경우에는 예외를 적용한다. 프로젝트의 명시적 Issue 필수 정책은 우선한다.

## 프로젝트 브랜치 정책

일반 브랜치 생성·PR 대상 결정·hotfix 작업에서도 [프로젝트 정책 읽기](project-branch-policy.md)를 먼저 적용한다. 승인된 프로젝트 정본이 패키지 dev/prod 후보보다 우선한다. 필요한 규칙의 충돌·미정은 관련 행동 전에 확인하며, 정책 문서가 없다고 초기화를 강제하지 않는다. 전략 기록은 workflow-init의 별도 승인 범위다.

## 실행 대상과 근거

현재 저장소의 remote, 브랜치, HEAD와 staged/미커밋 변경을 확인한다. 인증 계정은 해당 저장소의 지침을 따른다. 인계에는 Issue·PR·검토한 커밋·실행 근거와 남은 승인 범위를 전달한다.

테스트와 검토 결과에는 대상 커밋을 적는다. 미커밋 변경이 있으면 변경 파일 목록과 안전하게 확인할 수 있는 patch 또는 digest를 함께 기록한다. 이를 확인할 수 없으면 한계를 적고 해당 작업본을 다시 대조한다. HEAD만으로 미커밋 변경을 식별했다고 하지 않는다.

새 작업의 설계·작업 계약은 [Issue 계획·sub-issue 규칙](../../issue-create/references/plan.md)을 따른다. 신규 plan/task/handoff/review 작업 기록 파일을 만들지 않는다. 비밀값·원시 로그·머신 절대 경로는 공유 문서에 복사하지 않는다.

### 공개 기록의 비공개 식별자

공개 저장소의 Issue·PR·커밋 메시지·댓글에는 다음을 쓰지 않는다.

- 비공개 저장소·조직 이름과 그 Issue·PR 번호
- 사내 시스템·서비스·DB 테이블·컬럼·문서 이름
- 로컬 절대 경로

같은 역할을 나타내는 일반 이름으로 바꾼다. 예: 비공개 저장소의 Issue는 `` `acme/report-batch#41` ``처럼 가상 이름을 코드 표기로 쓴다. 코드 표기는 GitHub 자동 링크 생성을 방지한다. 테이블은 「대시보드 설정 테이블」, 문서 저장 시스템은 「문서 저장소」, 로컬 경로는 저장소 기준 상대 경로로 쓴다. `[사내 저장소]` 같은 자리 표시는 쓰지 않는다. 사용자 요청 원문을 인용할 때도 이 치환만 허용하고, 바꿨으면 인용 아래에 바꾼 종류를 한 줄로 쓴다. 이 치환은 대상 저장소가 공개일 때만 한다. 공개 여부는 게시 전에 `gh repo view --json visibility`로 확인한다. 비공개 저장소의 기록과, 공개 여부를 아직 확인하지 않은 초안에는 실제 이름을 그대로 쓴다. 게시 직전에도 공개 여부를 확인할 수 없으면 게시하지 않고 사용자에게 묻는다. 이미 공개된 기록은 일괄 수정하지 않는다.

대상 저장소에 spec-it manifest/lock이 있으면 그 파일이 고정한 spec-it 원문을 읽는다. 규칙을 복제하거나 자동으로 최신 버전으로 바꾸지 않는다. 확인되지 않은 번호·테스트 결과·URL·머지·배포 상태를 만들지 않는다.

## 검증 준비

구현 전 메인 또는 독립 검토 담당이 공개 AC·계획으로 판정 가능한지 확인하고 준비 상태를 인계한다. [독립 기준 보관](review-criteria.md#보관-위치)을 따른다.

| 상태 | 필요한 근거 | 다음 행동 |
| --- | --- | --- |
| 공개 기준으로 충분 | 공개 AC·계획과 기존 검사로 판정 방법이 명확함 | 별도 입력 파일·리뷰 위치 없이 구현 진행 |
| 별도 입력 고정 완료 | 필요한 독립 사례·기준·실행 계획을 결과 확인 전에 고정 | 구현자는 존재·고정 상태만 받고 진행 |
| 필요한 입력 미준비 | 필요한 별도 사례·기준이 없거나 고정 상태 미확인 | 영향받는 구현만 보류하고 독립 담당에게 준비 인계 |

별도 파일 부재 자체는 준비 부족이 아니다. 공개 기준의 충분성이나 필요한 입력의 고정 상태 자체가 확인되지 않았으면 관련 준비를 확인한다. 공개 계약을 읽는 것은 비공개 입력 열람이 아니다. 비공개 기준·고정 입력을 작성하거나 읽은 세션은 해당 Issue를 구현하지 않는다.

## 검증 방법과 비교

실행 전에 변경이 주장하는 행동마다 AC·대표 입력·기대 동작·판정 기준·주장 유형·실행 계획을 연결한다. 공개 계획으로 충분하면 파일을 추가하지 않는다. 링크·구조·오타와 의미 보존을 정적으로 확인할 수 있으면 정적 검사 근거와 행동 실행 미실행 이유를 기록한다. 분기·권한·우선순위·해석에 따른 행동이 바뀌면 행동 실행을 한다. 중복 문장 삭제도 유일한 보호 규칙을 없애면 행동 변경이다. 정적 통과는 모델 행동 증거가 아니다.

| 주장 유형 | 비교 방법 |
| --- | --- |
| 개선 | 변경 전 소스(RED)·변경 후 소스(GREEN)를 같은 입력·기준으로 비교. 변경 전에도 통과한 항목은 개선 증거에서 제외 |
| 유지 | 변경 후 확인을 기본으로 하고 실패 원인·상호작용을 구별할 필요가 있으면 변경 전 추가 |
| 새 기능 | 변경 후 기능 사례로 확인. 변경 전 실행은 기존 동작과의 차이·사례 판별력을 설명할 때 사용 |

서로 다른 경계 사례는 적용 범위를, 같은 입력 반복은 결과 안정성을 확인하며 서로 대신하지 않는다. 승인·비공개 입력·다른 작업 보존 경계에서는 서로 다른 실패 사례를 우선한다. 일괄 기본 3회나 기본 1회 대신 주장별 근거로 사례와 필요한 반복 범위를 결정한다.

관찰된 불일치뿐 아니라 기존 편차·해석 모호성·안정성 자체의 주장도 실행 전에 판단한다. 반복이 필요하면 추가 횟수·판정·종료 조건을 결과 전에 결정한다. 결정한 범위에서도 실행 결과가 서로 일치하지 않으면 불안정과 남은 판단을 기록하고 지시 보강 또는 human-review로 연결한다. 통과할 때까지 반복하거나 유리한 실행만 선택하지 않는다. 사례를 본 뒤 지시를 수정하면 해당 주장과 영향받는 유지 조건을 최종 소스로 재검증한다.

중간 실패·버린 실행·수정·재실행을 포함한 모든 실행의 대상·결과·판정 요약을 기록한다. 원시 로그 전문의 일괄 보존은 요구하지 않는다. 미실행과 이유·미검증 범위도 기록한다. 최종 사례 통과만으로 충분성을 확정하지 않고 누락된 행동 주장·대표성·작성자 선정 편향·설치 호스트와의 차이를 대조한다. 스킬을 직접 제공한 실행은 호스트의 스킬 선택·로딩 검증과 구별한다. 시간·토큰·실패율·비용 효과는 별도 측정 없이는 주장하지 않는다.

## 검증 실행 주체

판정과 시나리오 실행의 주체를 지정하는 정본이다.

| 작업 | 주체 | 주는 입력 |
| --- | --- | --- |
| 판정 (AC 대조, 리뷰 상태, 통과 기준 대조) | 현재 세션 또는 이미 위임된 리뷰 에이전트. 판정을 다른 모델에 다시 위임하지 않음 | Issue·plan·task·diff·검토 기준 |
| 명령 실행 (테스트, 기계 확인) | 판정 주체 | - |
| 구현 세션의 공개 사례 실행 | 실행마다 새 하위 에이전트(실행자). 실행자는 판정하지 않음 | 공개 계획으로 만든 요청문과 대상 스킬만. 기대 결과·판정 기준·다른 실행 결과는 주지 않음 |
| pr-review의 고정 입력 실행 | 실행마다 새 하위 에이전트(실행자). 실행자는 판정하지 않음 | 검증 입력의 「입력」 절과 대상 스킬만. 「기대 지적」·「통과 기준」·검토 기준·다른 실행 결과는 주지 않음 |

실행자의 결과는 판정 주체가 기준과 대조한다. 구현 세션의 자체 결과는 독립 판정을 대신하지 않는다. 요청문·결과 요약·대상은 PR 검증 근거 또는 접근 가능한 재현 자료에 기록한다. 하위 에이전트를 쓸 수 없으면 해당 시나리오를 `미실행`으로 기록한다.

## 결과 상태

스킬이 반환하는 상태 이름의 정본이다. 리뷰 판정(pass·warn·fail·human-review)은 [pr-review](../../pr-review/SKILL.md#6-결과)가 정의한다.

| 상태 | 조건 | 반환하는 스킬 |
| --- | --- | --- |
| issue-incomplete | Issue에 의도·영향 범위·달성 조건 중 하나가 없음 | issue-create |
| local-draft | 원격 Issue를 만들거나 조회할 수 없는 로컬 파일럿. 원격 Issue를 대신하지 않음 | issue-create |
| local-pr-draft | Issue 연결 검사 실패 또는 원격 접근 불가로 PR을 만들지 않은 본문 초안 | pr-request |
| review-pending | 구현 인계 후 리뷰나 테스트 증거 보완 대기 | pr-request |
| merge-unconfirmed | 머지 명령 후 실제 `state=MERGED`와 merge commit을 확인하지 못함 | pr-merge |
| close-unconfirmed | 종료·기존 CLOSED 결과 보완 후 실제 `state=CLOSED`, 기대한 stateReason, 종료 코멘트 또는 최종 본문 정합성을 확인하지 못함 | issue-close |

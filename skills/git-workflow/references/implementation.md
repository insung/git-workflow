# 준비된 계획 구현

[공통 실행 경계](execution-boundaries.md), [문체](writing-conventions.md), [커밋](../../commit-rule/SKILL.md)을 따른다.

## 입력

담당 Issue의 요청·목표·영향·제약·AC·현재 계획을 읽는다. 부모·선행 Issue가 있으면 공통 설계·AC 대응·현재 상태를 추가로 읽는다. 관계가 미확인이면 먼저 조회하고 선행 완료를 추정하지 않는다. 기존 상세 plan이나 담당 task가 연결되어 있으면 추가로 읽는다. 기존 작업은 [재개 규칙](../../issue-create/references/plan.md#기존-작업-재개)을 따른다. plan/task/handoff 파일 부재 자체는 입력 부족이 아니다.

읽지 않음: 독립 리뷰 브랜치·worktree·리뷰 전용 위치의 기준·고정 입력·기대 지적. 목록·검색·checkout·git show·diff로도 읽지 않는다. 공개된 실패 지적은 읽되 숨은 입력은 읽지 않는다. 이 Issue의 비공개 기준을 작성/열람했으면 구현하지 않고 별도 구현 역할로 인계한다 ([보관 위치](review-criteria.md#보관-위치)).

의도·범위·AC 또는 실행 방향·검증·전달 준비가 부족하면 [issue-create](../../issue-create/SKILL.md)의 작성·계획 절차로 보완한다. 구현 요청에서 승인된 계획 보완은 이어서 처리하고, 계획만 요청된 경우 구현하지 않는다. 구현 결과에 영향을 주는 인간 결정이 보류면 해당 단계만 보류한다. 조사로 알 수 있는 내용을 사용자에게 떠넘기지 않는다.

## 구현자 인계

메인은 담당 Issue URL과 공개 계획을 정본으로 연결하고 담당/제외 범위·유지할 결정·작업 위치·기준 브랜치·base/HEAD·승인 범위, [검증 준비 상태](execution-boundaries.md#검증-준비)를 인계한다. 부모·선행 관계와 연결 설계는 있을 때만 연결한다. 검증·전달 방법이 공개 계획에 있으면 반복 복사하지 않으며 미기록·변경된 정보만 보완한다. 구현자는 공개 계약과 현재 사실을 대조하고, 비공개 검토 기준·고정 입력은 전달하거나 조회하지 않는다. 사용자에게 스킬 이름이나 내부 단계 구분을 외우도록 요구하지 않는다.

## 절차

1. 브랜치·HEAD·index·미커밋 변경과 담당 경계를 확인한다. 인계의 준비 상태를 [공통 기준](execution-boundaries.md#검증-준비)으로 대조한다. 공개 기준으로 충분하면 별도 파일·리뷰 위치 없이 진행하고, 필요한 입력이 미준비인 관련 구현만 보류한다.
2. Issue 계획의 준비된 단위를 실행한다. sub-issue가 있으면 담당 독립 범위와 선행 조건을 적용하고 기존 표가 있으면 현재 계획과 대조한다. 목적·제약·유지 조건을 실제 변경과 대조한다.
3. 해당하는 정상·실패·경계·유지 검증을 실행한다. [검증 방법과 비교](execution-boundaries.md#검증-방법과-비교)에 따라 주장별 사례·기준·실행 계획을 결과 전에 정하고 정적 검사와 행동 실행을 구별한다. 개선은 변경 전 소스(RED)와 변경 후 소스(GREEN)를 같은 입력·기준으로 비교한다. 실행 주체·조건부 반복·전체 요약·미실행은 공통 경계를 따른다.
4. [인계 정보](../../pr-request/references/handoff.md)에 맞춘 AC별 결과 요약을 대화/임시 초안에 한 번 작성하고 PR에 재사용한다. 소스가 바뀌면 영향받는 증거와 대상 식별을 갱신한다. 과거 통과는 이력이다.
5. 중요한 선택·계획 이탈·범위 밖 발견을 구분한다. 승인되지 않은 의도·범위 변경은 제안으로 남긴다. 범위 밖 문제를 자동 구현하거나 후속 Issue로 자동 게시하지 않는다.
6. 커밋이 요청·승인된 범위이면 주제별로 커밋한다. 커밋이 없으면 파일·patch/digest를 식별한다. 결과 기록을 위한 handoff·task·docs 전용 커밋은 필수가 아니다.
7. 사용자가 반영과 회신을 요청했으면 [공통 수정 결과 회신](pr-comment-reply.md)을 적용해 원래 리뷰 스레드에 처리 결과를 돌려준다. 회신 요청이 없으면 초안/미회신을 반환하고 게시하지 않는다. resolve·머지는 별도 승인이다.
8. 합의된 최종 검증과 전달 조건을 확인하고 [pr-request](../../pr-request/SKILL.md)에 공개 계약 링크와 결과 요약·남은 조치를 인계한다. PR 또는 대화의 기존 요약을 재사용하고 바뀐 부분만 보완한다. 신규 task/handoff 파일을 만들지 않는다.

## 기록 규칙

실제 실행 결과와 독립 판정을 구별한다. 기존 plan/task의 체크·결정·결과 갱신은 [합의된 재개 범위](../../issue-create/references/plan.md#기존-작업-재개)에서만 수행하고 완료 표시는 근거가 있을 때만 한다. 새 방식에서는 같은 내용을 Issue·task·handoff에 반복하지 않는다. [증거 수명](document-links.md#증거와-실행-로그)을 적용하며 임시 파일을 공유 가능한 결과로 대신하지 않는다. 실제 Issue/PR 갱신과 댓글은 승인 범위에서만 실행한다.

# 준비된 계획 구현

[공통 실행 경계](execution-boundaries.md), [문체](writing-conventions.md), [커밋](../../commit-rule/SKILL.md)을 따른다.

## 입력

담당 Issue의 요청·목표·영향·제약·AC·현재 계획을 읽는다. 부모·선행 Issue가 있으면 공통 설계·AC 대응·현재 상태를 추가로 읽는다. 관계가 미확인이면 먼저 조회하고 선행 완료를 추정하지 않는다. 기존 상세 plan이나 담당 task가 연결되어 있으면 추가로 읽는다. 기존 작업은 [재개 규칙](../../issue-create/references/plan.md#기존-작업-재개)을 따른다. plan/task/handoff 파일 부재 자체는 입력 부족이 아니다.

읽지 않음: 독립 리뷰 브랜치·worktree·리뷰 전용 위치의 기준·고정 입력·기대 지적. 목록·검색·checkout·git show·diff로도 읽지 않는다. 공개된 실패 지적은 읽되 숨은 입력은 읽지 않는다. 이 Issue의 비공개 기준을 작성/열람했으면 구현하지 않고 별도 구현 역할로 인계한다 ([보관 위치](review-criteria.md#보관-위치)).

의도·범위·AC 또는 실행 방향·검증·전달 준비가 부족하면 [issue-create](../../issue-create/SKILL.md)의 작성·계획 절차로 보완한다. 구현 요청에서 승인된 계획 보완은 이어서 처리하고, 계획만 요청된 경우 구현하지 않는다. 구현 결과에 영향을 주는 인간 결정이 보류면 해당 단계만 보류한다. 조사로 알 수 있는 내용을 사용자에게 떠넘기지 않는다.

## 구현자 인계

메인은 담당·부모 Issue URL, 해결할 AC·담당/제외 범위, 공통 목적·유지할 결정·공개 계획과 선행 관계, 작업 위치·기준 브랜치·base/HEAD, 검증·결과 인계 방법, 승인된 행동과 대상을 전달한다. 구현자는 인계뿐 아니라 담당 Issue와 연결된 부모·선행 Issue를 읽고 현재 사실을 대조한다. 비공개 검토 기준·고정 입력은 전달하거나 조회하지 않는다. 사용자에게 스킬 이름이나 내부 단계 구분을 외우도록 요구하지 않는다.

## 절차

1. 브랜치·HEAD·index·미커밋 변경과 담당 경계를 확인한다. 독립 검토 기준·입력의 고정 상태를 인계에서 확인한다. 미확인이면 구현 준비 부족으로 기록한다.
2. Issue 계획의 준비된 단위를 실행한다. sub-issue가 있으면 담당 독립 범위와 선행 조건을 적용하고 기존 표가 있으면 현재 계획과 대조한다. 목적·제약·유지 조건을 실제 변경과 대조한다.
3. 의미 있는 정상·실패·경계·유지 검증 중 해당 사례를 실행한다. SKILL.md·references·assets의 지시 변경이면 변경 전 소스(RED)와 변경 후 소스(GREEN)의 같은 시나리오를 [새 실행자](execution-boundaries.md#검증-실행-주체)로 실행한다. 변경 전에도 통과한 항목은 개선을 입증했다고 하지 않는다. 미실행이면 이유를 남긴다.
4. 결과는 PR 본문 준비용 대화/임시 초안에 AC별 기대·실제·명령/방법·대상 commit·환경·시각·미실행 이유를 남긴다. 현재 소스가 바뀌면 영향받는 검증을 다시 확인한다. 과거 통과는 이력이다.
5. 중요한 선택·계획 이탈·범위 밖 발견을 구분한다. 승인되지 않은 의도·범위 변경은 제안으로 남긴다. 범위 밖 문제를 자동 구현하거나 후속 Issue로 자동 게시하지 않는다.
6. 커밋이 요청·승인된 범위이면 주제별로 커밋한다. 커밋이 없으면 파일·patch/digest를 식별한다. 결과 기록을 위한 handoff·task·docs 전용 커밋은 필수가 아니다.
7. 사용자가 반영과 회신을 요청했으면 [공통 수정 결과 회신](pr-comment-reply.md)을 적용해 원래 리뷰 스레드에 처리 결과를 돌려준다. 부분 반영·미반영 이유, 실제 반영 commit·파일/원고·검증·남은 판단과 작성 AI를 구별한다. 기존 답글 전체 조회·중복 생략·게시 후 URL과 본문 재조회를 수행하며 resolve·머지는 별도 승인이다. 회신 요청이 없으면 초안/미회신을 반환하고 게시하지 않는다.
8. 합의된 최종 검증과 전달 조건을 확인하고 [pr-request](../../pr-request/SKILL.md)에 Issue·결과·근거·남은 조치를 인계한다. [인계 정보](../../pr-request/references/handoff.md)를 PR 또는 대화에 기록한다. 신규 task/handoff 파일을 만들지 않는다.

## 기록 규칙

실제 실행 결과와 독립 판정을 구별한다. 기존 task의 완료·처리 내용·결과 칸은 계속 갱신하고 완료 표시는 근거가 있을 때만 한다. 기존 plan의 단계·결정 기록도 합의된 범위에서 이어간다. 새 방식에서는 같은 내용을 Issue·task·handoff에 반복하지 않는다. [증거 수명](document-links.md#증거와-실행-로그)을 적용하며 임시 파일을 공유 가능한 결과로 대신하지 않는다. 실제 Issue/PR 갱신과 댓글은 승인 범위에서만 실행한다.

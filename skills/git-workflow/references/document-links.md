# 기록의 정본과 연결

Issue는 요청·기준·계획, PR은 실제 구현·검증·검토·전달 결과의 기본 진입점이다. 새 작업의 plan·task·handoff·review 파일은 생성하지 않는다. 공통 설계는 부모 Issue, 독립 추적 결과는 [분리 기준](../../issue-create/references/plan.md#sub-issue-분리-판단)에 따른 sub-issue, 실제 결과·검토는 PR 또는 요청 범위의 대화에 둔다. 아래 증거 기준은 유지한다.

## 문서별 역할과 읽기 순서

| 위치 | 남길 답 |
| --- | --- |
| Issue | 원문, 왜·무엇을 바꿀지, 영향·제약·AC, 현재 계획, 남은 결정, 참고 링크 |
| PR | 실제 변경과 중요한 선택 이유, 계획 대비 차이, AC별 결과·미검증, 위험·배포·다음 조치 |
| 프로젝트 브랜치 정책 | 승인된 일반 작업·긴급 수정·배포·미정의 단일 정본. AGENTS에는 정본 링크 또는 간단 정책만 최소 기록 |
| 부모 Issue 계획 | 공통 설계·의존성·중요한 결정 이유·통합 검증 |
| 담당 sub-issue | 부모 AC 대응·독립 결과의 범위·검증·전달 계약 |
| 검토 결과 | 대상 HEAD·독립 판정·조치·근거·한계. 대화 또는 요청된 PR 리뷰 기록 |

기본 읽기 순서는 담당 Issue → 존재하는 부모의 공통 기준·관련 선행 Issue → PR과 diff·검증 근거다. 브랜치·PR 대상·hotfix 행동 전에는 [프로젝트 전략 정본](project-branch-policy.md)을 추가로 읽는다. 구현은 Issue의 준비된 계획과 제약을 읽고, 역할별로 담당 범위를 추가한다. 기존 plan·task가 실제 연결되어 있을 때만 읽는다. 기존 작업은 [기존 작업 재개](../../issue-create/references/plan.md#기존-작업-재개)의 순서를 따른다. 인계는 Issue URL·담당 범위·유지할 결정·base/HEAD·증거 위치·미실행·승인 범위·다음 행동만 연결한다.

PR 생성 전 결과는 대화나 작업용 임시 초안으로 유지한다. 원격 PR 생성 시 필요한 결과를 본문에 반영한다. 임시 초안은 공유 정본으로 취급하지 않으며 다른 세션에는 실제 접근 가능한 입력을 전달한다.

## 커밋에서 출발하는 읽기 순서

파일·함수·구간·동작에서 출발하는 조사는 [git-history](../../git-history/SKILL.md)를 사용한다. 직접 연결이 없을 때 기록 관행·문서 확인과 후보 검색, 후속 변경·접근 한계는 해당 스킬의 탐색 기준을 따른다.

코드의 해당 변경을 `git blame`이나 `git log`로 찾아 커밋 메시지를 읽는다. Refs의 출처는 [커밋 메시지 정본](../../commit-rule/references/commit-message.md#issue-출처-refs)의 표기·실제 Issue 확인 기준으로 해석한다.

1. 커밋의 Refs에서 Issue로 이동해 `사용자 요청 원문`, 의도·판단·합의, 현재 계획을 읽는다.
2. Issue가 연결한 PR에서 해당 커밋과 해결 범위를 대조하고 실제 구현·검증·미실행·중요한 선택을 읽는다. 연결된 PR이 여러 개면 해당 변경을 포함하는 PR을 확인한다.
3. Refs가 없거나 Issue에서 PR을 찾기 어려우면 GitHub의 커밋별 PR 조회로 연결된 PR을 찾고, PR 본문의 관련 Issue에서 원문·판단을 읽는다. 결과가 없거나 접근이 불가하면 추적 한계를 남기며 관계를 만들어 넣지 않는다.

확인된 기존 사례는 [커밋 3344dbd](https://github.com/insung/git-workflow/commit/3344dbd9fcad9171fd93b4d17e555a4e13ee8033) → [PR #38](https://github.com/insung/git-workflow/pull/38) → [Issue #36의 요청 원문](https://github.com/insung/git-workflow/issues/36)이다. 이 커밋에는 Refs가 없으며 [커밋별 PR API](https://api.github.com/repos/insung/git-workflow/commits/3344dbd9fcad9171fd93b4d17e555a4e13ee8033/pulls)로 연결을 확인했다. Refs는 직접 진입할 출처를 명시한다. 효과 비교 측정 결과는 없다.

Issue와 PR은 같은 정보를 복사하는 대신 위 역할에 따라 읽는다. Squash의 최종 메시지 보존은 [머지 지침](../../pr-merge/SKILL.md#squash-최종-메시지)에서 확인한다. 기존 공개 커밋의 이력을 다시 쓰지 않는다.

## 증거와 실행 로그

별도 설계가 있다는 이유로 evidence/·evidences/·txt·digest 파일을 생성하지 않는다. 확장자보다 쓰임과 보존 필요를 판단한다.

| 자료 | 보관 기준 |
| --- | --- |
| 핵심 결과 | PR에 AC·기대/실제·pass/fail/not-run·명령/확인 방법·대상 commit과 필요한 환경·시각·미실행 이유를 필요한 만큼 기록 |
| 제품 테스트·반복 재현 fixture | tests 등 프로젝트의 기존 경로에서 코드와 함께 유지 |
| 일시 명령 출력·작성 실행 결과 | 작업용 임시 경로. 커밋·공유 문서에 전문 복사하지 않음 |
| 외부 상태·복잡한 실패를 입증하는 고유 자료 | 다시 얻기 어렵고 판정에 필요할 때만 비밀값을 제거한 최소 자료를 접근 가능한 영구 위치에 보존 |
| 비공개 독립 검토 입력 | [검토 보관 위치](../../git-workflow/references/review-criteria.md#보관-위치)에서 공개 기록과 분리 |

임시 경로는 사용자·리뷰어가 읽을 영구 링크가 아니다. PR에 필요한 요약·재현 방법과 실행 대상이 남아 있으면 원시 로그 전체를 보존하지 않아도 된다. 임시 자료만으로 주장하는 결과는 검증 근거 부족으로 기록한다. 다시 실행하기 어려운 고유 증거는 영구 보관 또는 확보 전까지 미확인으로 남긴다. 세션 재개에 필요한 자료가 다른 환경에 없으면 접근 부족을 기록하고 다시 확보한다.

기존 docs/git-workflows 파일과 고정 링크는 당시 증거로 보존한다. 새 방식 적용만으로 삭제·이름 변경하지 않는다. 별도 정리 요청이 있을 때만 참조·고유 정보·진행 중 작업·보존 상태를 조사한다.

## 링크를 만들기 전

- 실제 원격 Issue·PR·commit과 접근 가능한 파일만 연결한다. 참고 링크 절은 Issue에서 필수이며 링크가 없으면 `확인된 참고 링크 없음`으로 쓴다.
- 로컬 미push 문서·임시 경로·비공개 입력에 원격 URL을 만들어 넣지 않는다. 공유 기록에 머신 절대 경로·비밀값·원시 로그를 넣지 않는다. 사용자가 준 요청 원문의 경로는 원문 인용이며 AI가 생성한 근거 링크와 구별한다.
- 실행 증거는 확인한 commit permalink를 우선한다. 최신 계획 링크와 검증 당시 고정 자료를 구별한다. 문서-only 후속 commit이 있으면 코드 검증 대상과 문서 보존 commit을 각각 표시한다.
- Issue·PR 본문 갱신, 댓글 신규 게시·수정, push는 해당 행동의 승인 범위에서만 실행한다. 생성·검토·머지 승인을 댓글 권한으로 확대하지 않는다. 기존 인간 본문·다른 작업 댓글을 덮어쓰지 않는다.

## 문서 허브 인계

별도 document-handoff 파일을 기본 생성하지 않는다. 원천 Issue·PR와 실제 배포 확인 자료로 아래 최소 정보를 전달한다.

- 기획 식별자·문서 링크, 이번 구현 결과와 중요한 결정 이유
- 현재 코드·구성·인프라 정의와 관련 저장소/commit
- 실제 배포 대상·버전·확인 시점·근거 또는 배포 대기·미확인
- 운영·롤백·남은 일과 원천 Issue·PR 링크

코드에 배포 설정이 존재한다는 사실을 실제 인프라 배포 완료로 쓰지 않는다. 머지·테스트 통과도 실제 배포 증거가 아니다. 문서 허브는 기획별 현재 구현·운영 상태를 갱신하며 전체 작업 로그를 복사하지 않는다. 실제 허브 작성·동기화는 요청된 범위에서만 실행한다.

## AI 작성 표기

AI가 실제로 작성하여 승인 범위에서 게시하는 PR·Issue 댓글과 리뷰 스레드 답글의 본문에는 작성 AI와 회신 유형을 표시한다. 회신 유형은 `수정 결과`, `검토 결과`, `질문 답변`, `반려·보류 사유` 중 본문의 주된 목적에 맞게 선택한다. 게시 계정은 본문에 반복하지 않고 실제 API 작성자 대조에 사용한다. 확인된 실제 도구명(Codex/Claude 등)을 쓰고 모델명은 확인되는 경우에만 선택적으로 쓴다. 여러 도구가 실제 기여했으면 각 도구의 기여를 구별한다. 미확인 주체를 계정명이나 문체로 추정하지 않는다.

```markdown
---
작성 AI: Codex
회신 유형: 수정 결과
```

일반 검토 요약은 `검토 결과`, 구현 반영 설명은 `수정 결과`, 질문 설명은 `질문 답변`, 반려·보류 이유 설명은 `반려·보류 사유`로 적는다. 최초 검토·재검토·머지 직전 확인 등 실행 단계와 Issue 종료 상태는 필요할 때 본문에서 설명하며 별도 유형을 만들지 않는다. 본문 표기는 GitHub의 작성자 계정을 변경하지 않으며 인간 승인·독립 리뷰·머지 완료를 뜻하지 않는다. 같은 계정으로 게시한 인간 댓글을 AI 댓글로 바꾸거나 기존 댓글에 서명을 소급 추가하지 않는다. 커밋의 Co-authored-by는 [커밋 정본](../../commit-rule/references/commit-message.md#ai-기여-co-authored-by)을 따른다.

# 기록의 정본과 연결

실제 관계·직접 요청/결정 출처와 단순 배경 링크는 [공통 기준](outcome-scope.md#관계와-배경-링크)을 적용한다. 완료·인계의 남은 일도 [발견과 남은 일](outcome-scope.md#발견과-남은-일)로 범위를 결정한다.

Issue는 요청·기준·계획, PR은 실제 구현·검증·검토·전달 결과의 기본 진입점이다. 새 작업의 plan·task·handoff·review 파일은 생성하지 않는다. 공통 설계는 부모 Issue, 독립 추적 결과는 `issue-create` 스킬의 분리 기준에 따른 sub-issue, 실제 결과·검토는 PR 또는 요청 범위의 대화에 기록한다. 아래 증거 기준은 유지한다.

## 문서별 역할과 읽기 순서

| 위치 | 기록할 내용 |
| --- | --- |
| Issue | 원문, 왜·무엇을 바꿀지, 영향·제약·AC, 현재 계획, 남은 결정, 참고 링크 |
| PR | 실제 변경과 중요한 선택 이유, 계획 대비 차이, AC별 결과·미검증, 위험·배포·다음 조치 |
| 프로젝트 브랜치 정책 | 승인된 일반 작업·긴급 수정·배포·미정의 단일 정본. AGENTS에는 정본 링크 또는 간단 정책만 최소 기록 |
| 부모 Issue 계획 | 공통 설계·의존성·중요한 결정 이유·통합 검증 |
| 담당 sub-issue | 부모 AC 대응·독립 결과의 범위·검증·전달 계약 |
| 검토 결과 | 대상 HEAD·독립 판정·조치·근거·한계. 대화 또는 요청된 PR 리뷰 기록 |
| 릴리즈 | 배포 범위·전환 안내·발행 결과. 같은 전문을 Issue·PR 에서 반복하지 않음 |

기본 읽기 순서는 담당 Issue → 존재하는 부모의 공통 기준·관련 선행 Issue → PR과 diff·검증 근거다. 브랜치·PR 대상·hotfix 행동 전에는 [프로젝트 전략 정본](project-branch-policy.md)을 추가로 읽는다. 구현은 Issue의 준비된 계획과 제약을 읽고, 역할별로 담당 범위를 추가한다. 기존 plan·task가 실제 연결되어 있을 때만 읽는다. 기존 작업은 `issue-create` 스킬의 기존 작업 재개 순서를 따른다. 인계는 Issue URL·담당 범위·유지할 결정·base/HEAD·증거 위치·미실행·승인 범위·다음 행동만 연결한다.

PR 생성 전 결과는 대화나 작업용 임시 초안으로 유지한다. 원격 PR 생성 시 필요한 결과를 본문에 반영한다. 임시 초안은 공유 정본으로 취급하지 않으며 다른 세션에는 실제 접근 가능한 입력을 전달한다.

릴리즈만의 기록과 Issue 없는 준비 PR의 대체 기록은 `git-release` 스킬의 릴리즈 기록 기준을 따른다.

## 커밋에서 출발하는 읽기 순서

파일·함수·커밋에서 출발해 변경 이유를 찾는 조사는 `git-history` 스킬을 사용한다. 커밋의 Refs → Issue 의 요청 원문·판단(하위 Issue 이면 부모의 공통 설계와 하위가 가리킨 부모 결정까지) → 연결된 PR 의 구현·검증 순서로 읽는다. Issue 와 PR 은 같은 정보를 복사하는 대신 위 역할에 따라 읽는다. 기존 공개 커밋의 이력을 다시 쓰지 않는다.

## 증거와 실행 로그

별도 설계가 있다는 이유로 작업 브랜치에 evidence/·evidences/·txt·digest 파일을 생성하지 않는다. 확장자보다 쓰임과 보존 필요를 판단한다. PR에 이미지로 보여야 하는 증거(화면 스크린샷 등)는 작업 브랜치가 아닌 [orphan 증거 브랜치](#이미지-증거)에만 커밋한다.

| 자료 | 보관 기준 |
| --- | --- |
| 핵심 결과 | PR에 AC·기대/실제·pass/fail/not-run·명령/확인 방법·대상 commit과 필요한 환경·시각·미실행 이유를 필요한 만큼 기록 |
| 제품 테스트·반복 재현 fixture | tests 등 프로젝트의 기존 경로에서 코드와 함께 유지 |
| 일시 명령 출력·작성 실행 결과 | 작업용 임시 경로. 커밋·공유 문서에 전문 복사하지 않음 |
| 외부 상태·복잡한 실패를 입증하는 고유 자료 | 다시 얻기 어렵고 판정에 필요할 때만 비밀값을 제거한 최소 자료를 접근 가능한 영구 위치에 보존 |
| 화면 스크린샷 등 이미지 증거 | [orphan 증거 브랜치](#이미지-증거)에 커밋하고 PR에 commit SHA 고정 링크로 연결 |
| 검증이 만든 테스트 데이터(DB 행 등) | AI가 삭제하지 않음. 대상 환경·DB·테이블·식별자를 PR 또는 요청 범위의 대화·코멘트에 기록하고 삭제 여부는 사용자가 판단·실행 |
| 숨긴 검증 입력 | [검토 보관 위치](review-criteria.md#보관-위치)에서 공개 기록과 분리 |

임시 경로는 사용자·리뷰어가 읽을 영구 링크가 아니다. 필요한 요약·재현 방법과 실행 대상이 PR에 기록되어 있으면 원시 로그 전체를 보존하지 않아도 된다. 임시 자료만으로 주장하는 결과는 검증 근거 부족으로 기록한다. 다시 실행하기 어려운 고유 증거는 영구 보관 또는 확보 전까지 미확인으로 기록한다. 세션 재개에 필요한 자료가 다른 환경에 없으면 접근 부족을 기록하고 다시 확보한다.

### 화면이 있는 변경의 E2E 증거

화면 입력·버튼 동작으로 확인하는 TC(종류 E2E)에 적용한다. 로컬 개발 서버와 개발용 DB 에서만 실행하고 운영 DB 를 쓰지 않는다. 화면이 없는 변경은 위 표의 핵심 결과 기준만 적용한다. PR 에 두는 형식은 [PR 본문 규칙](../../pr-request/references/pr.md#검증-상태와-확인-절)을 따른다.

| 증거 | 남기는 방법 |
| --- | --- |
| 대상 | 검증한 commit SHA·시각·화면 URL·DB 연결 이름. HEAD 가 바뀌면 다시 실행. 공개 저장소에서는 내부 호스트·DB 연결 이름에 [공개 기록의 비공개 식별자](execution-boundaries.md#공개-기록의-비공개-식별자) 치환을 적용 |
| 화면 | 유효·무효 입력과 버튼 동작마다 상태가 바뀐 시점(오류 표시, 제출 결과)만 찍음. 입력할 때마다 찍지 않음. [이미지 증거](#이미지-증거) 기준으로 보관 |
| 서버 응답 | 메서드·경로·상태·응답 본문의 오류 코드나 문구를 텍스트로 쓰고 코드·AC 에 정의한 오류와 나란히 대조. 상태 코드만으로 판정하지 않음(Server Action 처럼 오류에도 200 을 돌려주는 경우). DevTools 화면 캡처는 요구하지 않음 |
| DB | 실행 전·후 읽기 조회문과 결과 표를 텍스트로 씀. 무효 입력은 행이 생기지 않았음(0건)을 보임. 쓰기는 화면 동작으로만 일어나게 하고 쓰기 쿼리를 직접 실행하지 않음 |
| 개인정보 | 검증용 계정만 조건으로 조회하고 필요한 열만 표시. 비밀번호 해시·토큰은 형식(앞 몇 글자, NULL 여부)만 보임. 실제 사용자 계정으로 시험하지 않음 |
| 검증용 데이터 | 위 표의 「검증이 만든 테스트 데이터」 기준 |

### 이미지 증거

`gh` CLI는 Issue·PR에 이미지를 첨부하지 못하므로 이미지 증거는 같은 저장소의 orphan 브랜치 `evidence`에 커밋한다.

1. `evidence` 브랜치가 없으면 기본 브랜치와 이력을 공유하지 않는 orphan 브랜치로 만든다. 작업 브랜치·기본 브랜치에는 이미지를 커밋하지 않는다.
2. 파일은 `<작업 브랜치 이름>/<AC 또는 TC>-<짧은 설명>.png` 경로에 둔다. 한 상태 변화(오류 표시, 제출 결과 등)에 이미지 하나를 쓴다.
3. 커밋 전에 이미지에 비밀값·실제 사용자의 개인정보·다른 계정의 데이터가 보이지 않는지 확인한다. 보이면 가리거나 다시 찍는다. 공개 저장소에서는 [공개 기록의 비공개 식별자](execution-boundaries.md#공개-기록의-비공개-식별자) 기준도 적용한다.
4. push는 PR 게시와 같은 승인 범위에서 실행한다.
5. PR 링크는 브랜치 이름이 아닌 증거 커밋의 전체 SHA로 만든다: `https://github.com/<owner>/<repo>/blob/<commit SHA>/<경로>?raw=true`. 브랜치를 정리하거나 다시 써도 PR 기록이 바로 깨지지 않게 하기 위해서다.
6. `evidence`는 장기 유지 브랜치다. [머지 후 정리](../../pr-merge/references/post-merge-cleanup.md)의 삭제 대상에 넣지 않는다.

기존 docs/git-workflows 파일과 고정 링크는 당시 증거로 보존한다. 새 방식 적용만으로 삭제·이름 변경하지 않는다. 별도 삭제·이름 변경 요청이 있을 때만 참조·고유 정보·진행 중 작업·보존 상태를 조사한다.

## 링크를 만들기 전

- 실제 원격 Issue·PR·commit과 접근 가능한 파일만 연결한다. 참고 링크 절은 Issue에서 필수이며 링크가 없으면 `확인된 참고 링크 없음`으로 쓴다.
- 로컬 미push 문서·임시 경로·숨긴 검증 입력에 원격 URL을 작성하지 않는다. 공유 기록에 머신 절대 경로·비밀값·원시 로그를 기록하지 않는다. 사용자가 준 요청 원문의 경로는 원문 인용이며 AI가 생성한 근거 링크와 구별한다. 공개 저장소에서는 원문 인용에도 [공개 기록의 비공개 식별자](execution-boundaries.md#공개-기록의-비공개-식별자) 치환을 적용한다.
- 실행 증거는 확인한 commit permalink를 우선한다. 최신 계획 링크와 검증 당시 고정 자료를 구별한다. 문서-only 후속 commit이 있으면 코드 검증 대상과 문서 보존 commit을 각각 표시한다.
- Issue·PR 본문 갱신, 댓글 신규 게시·수정, push는 해당 행동의 승인 범위에서만 실행한다. 생성·검토·머지 승인을 댓글 권한으로 확대하지 않는다. 기존 인간 본문·다른 작업 댓글을 덮어쓰지 않는다.

## 문서 허브 인계

별도 document-handoff 파일을 기본 생성하지 않는다. 원본 Issue·PR와 실제 배포 확인 자료로 아래 최소 정보를 전달한다.

- 기획 식별자·문서 링크, 이번 구현 결과와 중요한 결정 이유
- 현재 코드·구성·인프라 정의와 관련 저장소/commit
- 실제 배포 대상·버전·확인 시점·근거 또는 배포 대기·미확인
- 운영·롤백·남은 일과 원본 Issue·PR 링크

코드에 배포 설정이 존재한다는 사실을 실제 인프라 배포 완료로 쓰지 않는다. 머지·테스트 통과도 실제 배포 증거가 아니다. 문서 허브는 기획별 현재 구현·운영 상태를 갱신하며 전체 작업 로그를 복사하지 않는다. 실제 허브 작성·동기화는 요청된 범위에서만 실행한다.

## AI 작성 표기

AI가 실제로 작성하여 승인 범위에서 게시하는 PR·Issue 댓글과 리뷰 스레드 답글의 본문에는 작성 AI와 회신 유형을 표시한다. 회신 유형은 `수정 결과`, `검토 결과`, `질문 답변`, `반려·보류 사유` 중 본문의 주된 목적에 맞게 선택한다. 게시 계정은 본문에 반복하지 않고 실제 API 작성자 대조에 사용한다. 확인된 실제 도구명(Codex/Claude 등)을 쓰고 모델명은 확인되는 경우에만 선택적으로 쓴다. 여러 도구가 실제 기여했으면 각 도구의 기여를 구별한다. 미확인 주체를 계정명이나 문체로 추정하지 않는다.

신규 게시 본문의 첫 줄은 아래처럼 두 필드를 함께 강조한다. 인용·코드 블록 밖에 실제 도구명과 허용된 회신 유형을 작성한다. 기존 댓글은 소급 변경하지 않는다.

```markdown
**회신 유형: 수정 결과 · 작성 AI: Codex**

기간 필터 반영. 상태 필터는 데이터 계약 결정 대기.
```

작성 요청 전에는 준비한 본문의 첫 줄을 확인하고, 작성 후에는 API 로 재조회(read-back)해 실제 저장된 본문의 첫 줄과 전체 내용이 같은지 확인한다. 두 표기 중 하나가 없거나 예시 자리표시자가 남으면 게시하지 않는다. 게시 뒤 누락을 발견하면 완료로 보고하지 않고 미확인 상태·실제 URL·필요한 다음 행동을 반환한다. 별도 승인 없이 기존 댓글 수정·재게시로 보정하지 않는다. 표기 검사는 실제 AI 기여의 진위를 입증하지 않으며 도구명은 확인한 작성 기록을 근거로 결정한다.

일반 검토 요약은 `검토 결과`, 구현 반영 설명은 `수정 결과`, 질문 설명은 `질문 답변`, 반려·보류 이유 설명은 `반려·보류 사유`로 적는다. 최초 검토·재검토·머지 직전 확인 등 실행 단계와 Issue 종료 상태는 필요할 때 본문에서 설명하며 별도 유형을 만들지 않는다. 본문 표기는 GitHub의 작성자 계정을 변경하지 않으며 인간 승인·독립 리뷰·머지 완료를 뜻하지 않는다. 같은 계정으로 게시한 인간 댓글을 AI 댓글로 바꾸거나 기존 댓글에 서명을 소급 추가하지 않는다. 커밋의 Co-authored-by는 `commit-rule` 스킬의 커밋 메시지 규칙을 따른다.

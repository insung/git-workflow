# 마일스톤 운영

마일스톤은 목표 버전에 포함할 작업의 범위다. Issue 생성·연결과 릴리즈 준비 전에 대상 저장소·목표 버전·승인 범위를 확인한다. Projects나 브랜치를 함께 생성하지 않는다.

## 저장소 기준 읽기

1. 대상의 AGENTS.md와 연결된 정책, README의 마일스톤·릴리즈 기준을 읽는다. 이미 승인된 이름·연결 대상·기한·종료 규칙이 우선이다. 정책이 충돌하면 관련 변경만 보류한다.
2. 규칙이 없으면 이름은 태그와 맞춘 `vX.Y.Z`, 연결은 Issue 중심, 기한은 합의된 출시일이 있을 때만 설정하는 안을 제시한다. 예를 들어 목표 버전 0.9.0은 `v0.9.0`이다. 프로젝트가 `release-0.9.0`을 사용하면 그 이름을 유지한다. 접두사를 중복하거나 기존 이름을 일괄 변경하지 않는다.
3. 목표 버전은 사용자 결정이나 승인된 저장소 기준에서 확인한다. 최신 열린 마일스톤·최근 태그·제목 type만으로 추정하지 않는다. 목표 미정은 연결하지 않고 미지정 사유를 보고한다.
4. Issue 중심 운영이면 같은 작업의 PR을 자동 추가하지 않는다. 마일스톤은 하나의 저장소에 속하며, 다른 저장소의 같은 이름은 다른 대상이다.

## 조회·생성·연결

실제 owner/repo와 인증 계정은 프로젝트 지침을 따른다. 아래 예시는 승인된 대상·이름·파일로 바꿔 사용한다.

```bash
gh api --paginate 'repos/OWNER/REPO/milestones?state=all&per_page=100'
# 대상 이름의 부재와 생성 권한이 확인된 경우만 실행
gh api --method POST repos/OWNER/REPO/milestones -f title='v0.9.0'
# 확인된 마일스톤에 새 Issue 생성 또는 승인된 기존 Issue 연결
gh issue create --repo OWNER/REPO --title 'TITLE' \
  --body-file /tmp/issue-body.md --milestone 'v0.9.0'
gh issue edit NUMBER --repo OWNER/REPO --milestone 'v0.9.0'
gh issue view NUMBER --repo OWNER/REPO --json number,state,milestone
```

1. 열린/닫힌 목록을 끝 페이지까지 조회하고 정확한 이름·번호·상태를 대조한다. 조회 실패는 부재가 아니다. 같은 이름의 후보가 여럿이면 대상 확인 전 변경하지 않는다.
2. 기존 대상은 재사용하고 설명·기한·이름·상태를 덮어쓰지 않는다. 닫힌 마일스톤에 과거 완료 작업을 연결하는 요청은 가능하지만, 새 예정 작업이라면 목표를 확인한다. 임의 재오픈하지 않는다.
3. 누락 생성은 이름·저장소·생성이 요청되거나 이미 승인된 경우만 실행한다. Issue 생성 요청만으로 목표 버전이나 없는 마일스톤 생성 권한을 추정하지 않는다. 승인된 설명만 쓰고 기한이 미정이면 `due_on`을 보내지 않는다. 합의된 기한은 시간대를 확인해 API의 UTC 시각으로 변환한다.
4. 생성 응답 불명·타임아웃·중복 오류 시 다시 조회한다. 대상이 발견되면 재사용하고 생성 요청을 반복하지 않는다. 여전히 조회 불가이면 변경 결과 미확인으로 보고한다.
5. 새 Issue는 생성 시 `--milestone`으로 연결한다. 기존 Issue는 현재 연결부터 읽고 같은 대상이면 무변경이다. 다른 연결의 교체·해제는 명시된 대상과 승인 범위에서만 처리한다. 닫힌 Issue도 메타데이터만 연결할 수 있으며 재오픈하지 않는다.
6. Issue 생성 후 연결만 실패하면 생성된 Issue를 삭제하거나 중복 생성하지 않는다. Issue URL·실제 연결 상태와 실패를 보고하고 승인 범위에서 연결만 재시도한다.
7. 목록 검색은 반영이 늦을 수 있으므로 각 Issue의 `milestone`과 마일스톤 단건 API의 실제 필드를 재조회한다. 저장소·번호·이름·상태·기한과 연결 여부를 확인하고 적용/무변경/미지정/실패/미확인을 구분한다. URL을 받은 것만으로 성공이라 하지 않는다.

## 릴리즈 범위와 이월

마일스톤을 사용하는 릴리즈는 확정된 범위의 모든 Issue가 완료되고 완료율이 100%여야 발행 준비 조건을 충족한다. 100%는 Issue·PR의 열린/닫힌 상태 집계이며 태그 포함·검증·Release 발행의 증거가 아니다. 항목이 0개인 마일스톤은 범위 확인 전 준비 완료로 판단하지 않는다. 사용하지 않는 저장소에 마일스톤 생성을 강제하지 않는다.

1. 대상 마일스톤과 태그 commit을 고정한다. 연결 항목은 끝 페이지까지 읽고 각 Issue의 AC·완료 근거와 실제 태그에 포함된 커밋·PR을 대조한다. 닫힌 상태만으로 AC 충족을 추정하지 않으며 not planned·duplicate도 완료 결과로 집계하지 않는다. 저장소 정책상 PR도 연결하면 그 상태·실제 포함을 함께 확인한다.
2. 열린 필수 작업은 발행을 보류한다. 연기할 작업은 이월할 Issue·이유·대상 버전을 사용자에게 제시하고 결정된 범위만 이동한다. “다음 버전이면 되겠지”처럼 대상과 이월 승인이 미정이면 이동·종료·발행을 보류한다. AI가 완료율을 맞추려고 Issue를 닫거나 목표 버전을 지정하지 않는다.
3. 이월 이유·기존/새 마일스톤·남은 범위를 Issue의 계획 또는 남은 결정에 기록한다. 본문 갱신과 연결 교체도 승인 범위에서 처리하고 원문·기존 완료 결과를 보존한다. 이월은 Issue 완료가 아니다.
4. 이미 머지된 코드는 마일스톤을 옮겨도 대상 태그에서 빠지지 않는다. 일부만 머지된 Issue는 포함된 결과와 남은 범위를 대조한다. 코드 제외가 필요하면 별도 변경과 검증·승인을 거치며 자동 revert나 공개 이력 재작성은 하지 않는다.
5. 범위 조정 후 마일스톤과 대상 commit을 다시 확인한다. 미완료·미포함·출처 누락과 조회 실패는 필요한 수정·결정으로 보고하며 숫자만 맞춰 발행하지 않는다.
6. 종료 승인은 발행 승인 요청에서 대상 마일스톤의 이름·번호·완료율과 함께 별도 항목으로 묻는다. 태그·Release의 실제 발행과 대상 commit을 확인한 뒤, 해당 마일스톤 종료 승인이 있는 경우만 `PATCH /repos/OWNER/REPO/milestones/NUMBER`의 `state=closed`를 적용한다. 발행 승인은 종료 승인을 대신하지 않는다. 이미 종료된 대상은 무변경이며 재조회로 확인한다. 발행 확인 실패·종료 승인 미확인·새 미완료 작업이 있으면 종료를 보류한다.

발행 성공과 마일스톤 종료 결과는 별도로 보고한다. 종료 승인이 없어 닫지 않은 마일스톤은 열린 상태와 「마일스톤 종료 승인 대기」를 다음 행동으로 보고한다. 종료만 실패하면 Release를 중복 발행하거나 태그를 바꾸지 않고 종료 재확인·재시도만 처리한다.

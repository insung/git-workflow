# 커밋 이력 기반 릴리즈 노트

릴리즈 노트는 선택한 배포 범위에서 사용자가 겪는 변화를 설명한다. 커밋 제목은 후보를 찾는 색인이고, 실제 변경과 배포 범위가 근거다. 저장소에 기존 `CHANGELOG`, 릴리즈 템플릿, release-drafter 또는 제품별 발행 방식이 있으면 그 형식과 분류를 먼저 따른다.

## 범위 고정

1. 어떤 제품·패키지·배포 단위의 노트인지 확인한다. 여러 제품이 한 저장소에 있으면 해당 제품의 이전 배포 지점과 이번 대상 지점을 따로 찾는다.
2. 이전 릴리즈 태그 또는 확인된 배포 커밋을 `base`, 이번 릴리즈 후보 커밋을 `target`으로 정한다. 날짜순 최신 태그가 반드시 이전 배포 지점은 아니다. 태그 형식, 실제 배포 기록과 조상 관계를 확인한다.
3. 기준이 불명확하면 임의 버전과 날짜를 붙이지 않는다. 확인 가능한 커밋을 기준으로 `Unreleased` 초안을 만들거나 기준점 결정을 요청한다.

```bash
git merge-base --is-ancestor <base> <target>
git log --first-parent --format='%h %s' <base>..<target>
git log --format='%H %s%n%b' <base>..<target>
git diff --name-status <base> <target>
```

첫 로그는 통합 흐름의 변경 단위를, 두 번째는 병합된 브랜치 안의 세부 커밋과 본문을 확인하는 데 쓴다. `--first-parent`가 머지 커밋만 보여 주는 것은 아니다. squash, rebase, 일반 커밋도 통합 흐름에 따라 나타날 수 있다. PR과 label은 접근 가능할 때 보조 근거로 확인한다. GitHub 접근이 안 되면 로컬 Git 근거의 한계를 밝히고 계속할 수 있다.

## 내용 선정

- `feat`, `fix`, `perf`, `!`, `BREAKING CHANGE`를 후보로 찾되, 제목만 옮기지 않는다. 해당 diff, PR 설명 또는 변경 문서에서 사용자에게 나타나는 결과를 확인한다.
- 여러 커밋이 하나의 기능을 완성했으면 한 항목으로 묶는다. 머지 커밋과 내부 커밋을 중복 기재하지 않는다.
- `docs`, `build`, `ci`, `chore` 등도 설치 절차, 지원 환경, 운영 방식이나 호환성을 바꿨다면 포함한다. 내부 정리만 한 커밋은 보통 제외한다.
- 호환성 변경은 이전 사용 방법과 필요한 전환 조치를 확인해 별도로 드러낸다. 커밋 표기만으로 실제 호환성 단절을 단정하지 않는다.
- 아직 합쳐지지 않았거나 선택한 `target` 뒤에 들어간 변경은 제외한다. 모노레포에서는 경로만 보고 공용 코드의 영향을 놓치지 않도록 소비자도 확인한다.

## 작성과 재확인

저장소의 기존 언어, 제목, 순서와 링크 형식을 따른다. 형식이 없으면 기능·수정·성능·호환성·설치 또는 운영 변경 중 실제 내용이 있는 분류만 사용한다. 항목은 커밋 명령형 대신 사용자가 얻는 결과로 쓰고, 추적이 필요하면 확인된 커밋 또는 PR을 연결한다.

버전과 날짜는 저장소의 확정된 릴리즈 정보가 있을 때만 적는다. 테스트 결과나 배포 완료 여부도 별도의 실행 증거가 있을 때만 적는다. 초안을 `base..target`의 전체 변경과 다시 대조해 누락·중복·범위 밖 항목을 확인한다.

사용자가 노트를 저장할 파일을 지정했거나 저장소의 기존 발행 파일에 쓰라고 요청했다면 그 파일을 갱신한다. 그 외에는 검토할 초안을 제시한다. 노트 작성 자체는 커밋, 태그, 푸시, GitHub Release 발행 또는 배포를 실행하지 않는다.

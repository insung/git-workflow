# 공통 문체

Issue·PR·commit 본문, plan/todo, 리뷰 보고서와 릴리즈 기록을 작성할 때 읽는다. 사용자에게 답하는 대화 문체에는 적용하지 않는다. 대상 저장소의 지정 언어·기록 형식이 우선이다.

본문은 존댓말이나 대화체 반말 대신 기록 문체를 쓴다. 산문은 평어(~다), 제목·표의 짧은 값·달성 조건(AC)과 체크박스는 명사형으로 끝낸다. Issue·PR·릴리즈의 설명 목록은 결과와 조건을 이해할 수 있도록 완결된 문장으로 써도 된다. 문장형을 모든 목록에 강제하지 않으며, plan·task·review·commit 목록은 기존 명사형 기준을 유지한다. 템플릿 HTML 주석도 해당 요소의 기준을 따른다.

| 문서 요소 | 예 |
| --- | --- |
| 제목 | fix(app-usage): 재실행 시 중복 적재 차단 |
| 산문 | 같은 날짜 재실행 시 사용량이 중복 집계된다. |
| Issue·PR·릴리즈 설명 목록 | 일시 오류에서 재시도 방법을 안내한다. |
| 표의 짧은 값·다른 문서의 목록 | 마이그레이션: 없음 |
| 달성 조건 | 일별 배치를 재실행해도 집계값 유지 |

문서 요소는 제목·산문·목록·표·체크박스를 뜻한다. `feat`, `fix` 같은 변경 type은 [change-conventions](change-conventions.md)의 별도 규칙이다.

`수정했습니다`, `전부 통과했어요`, `확인 부탁드립니다` 대신 동작과 실제 증거를 적는다. 확인된 사실·사용자 결정·가정·미확인을 구분하고, 문서와 코드가 제공하지 않는 세부사항을 만들지 않는다.

사용자가 말한 증상을 그대로 옮길 때는 인용으로 표시하고 원문을 보존한다. 커밋의 `Co-authored-by:` 트레일러는 [commit-message의 푸터](../../commit-rule/references/commit-message.md#푸터)를 따른다. 선택 절은 내용이 있을 때만 만들지만, 필수 검증·배포 계획의 해당 없음은 이유와 함께 명시한다.

## 정보 단위와 작성 후 편집

결론이나 필요한 행동을 첫 문장에 쓴다. 쉬운 용어를 쓰고, 문장·목록 항목·표 행·달성 조건마다 하나의 주장 또는 판단 가능한 결과를 담는다. 한 항목에 서로 다른 완료 시점이나 조치가 있으면 나눈다. 결과와 그 구현 방법·검증 명령을 하나의 AC에 섞지 않는다.

초안 뒤 다음 순서로 편집한다.

1. 독자가 이 문서에서 결정하거나 실행할 일을 먼저 배치
2. 원문에서 결과·적용 조건·승인·보존 동작·전환 조치·검증 한계를 먼저 구별
3. 한 결과의 관련 조건은 짧은 설명으로 연결하고, 따로 판단하거나 실행할 정보는 항목 분리; 여러 커밋·경과가 같은 결과면 묶고 반복 제거
4. 상세 조사·명령·로그는 정본으로 연결하고 본문에는 판단에 필요한 근거 유지
5. 빈 선택 절 삭제, 필수 절의 해당 없음은 이유 명시
6. 원문과 대조해 사실·AC ID·재현·미검증·위험·필수 검증·전달 정보·중요한 결정 이유 보존 확인

Issue는 목표·범위·AC·확인된 사실·참고 링크로, PR은 변경 후 동작·현재 검증 결론·위험·다음 행동으로, 릴리즈는 핵심 요약·결과 분류·전환 안내·근거로 배치한다. 편집한 문장을 원문과 일대일 또는 결과별 묶음으로 대조하고, 의미가 달라지거나 근거를 찾지 못하면 표현을 보완한다.

짧게 만드는 것 자체는 목적이 아니다. 중요한 맥락을 삭제하지 않고 [문서 역할](document-links.md#문서별-역할과-읽기-순서)에 맞게 옮긴다. 과거 통과를 현재 HEAD의 통과로 바꾸거나 로컬 문서에 원격 링크를 만들어 넣지 않는다.

## 짧거나 모호한 요청의 근거 대조

일곱 질문을 필수 절로 늘리지 않는다. 사용자 원문은 독립된 Issue 절에 그대로 보존하고 PR은 연결한다. 원문 길이는 편집하지 않으며 AI 설명은 반복을 제거한다.

| 주장 | 대조할 근거 | 근거가 없을 때 |
| --- | --- | --- |
| 사용자 보고 | 실제 요청 인용 | 원문 미확인. 직접 재현으로 쓰지 않음 |
| 확인한 사실 | 읽은 코드·문서·실행 결과 | 미확인 또는 제거 |
| 해결 방향·수치·범위·AC | 사용자 요청과 합의 또는 제안 출처 | AI 제안으로 구분. 합의로 확정하지 않음 |
| 사용자 결정 | 승인된 행동·대상·범위 | 미합의로 구분 |
| 없음·해당 없음 | 실제 조사한 범위와 이유 | 미확인으로 구분 |

원인·목표 성능·재현 환경·연관 프로젝트 영향을 템플릿 칸을 채우려고 만들지 않는다. 조사가 확인한 사실과 인간이 결정해야 할 의도를 구별한다. 필수 의도·범위·AC를 정할 수 없으면 필요한 인간 결정만 질문하며 제안을 합의된 계획으로 실행하지 않는다.

목표는 이유, As-Is/To-Be는 동작 차이, AC는 완료 판정, 계획은 실행 방향, PR은 실제 결과다. 버그의 실제/기대 동작은 As-Is/To-Be와 중복하지 않는다. 제약은 수행 시 유지 조건이며 제외 범위와 다르다. 같은 규칙·결과를 여러 절에 복사하지 않는다. 독립 판단은 짧은 문장으로 나누고 결과·조건·한계를 한 문장에 압축하지 않는다.

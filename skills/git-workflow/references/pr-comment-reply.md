# 수정 결과의 원래 스레드 회신

수정 구현 단계(task-implement), pr-comment-check, pr-review, pr-merge가 재사용하는 처리 결과 회신의 정본이다. 받은 요청의 조회·반영 판단은 [공통 코멘트 확인](pr-comment-check.md), PR 전체 검토 요약 게시·수정은 [pr-comment.md](../../pr-review/references/pr-comment.md)를 적용한다. 이 절차는 요청별 처리 결과를 원래 리뷰 스레드에 돌려주는 절차이며 공식 Review 제출이 아니다.

## 1. 요청과 실행 단계

| 호출 단계 | 회신 시점·내용 |
| --- | --- |
| pr-comment-check | 처리·회신이 승인된 작업이면 요청별 구현 또는 근거 있는 반려·보류 후 회신하고 적용 결과 보고 |
| task-implement | 승인된 수정을 구현·검증하고 실제 커밋·파일 근거를 확인한 뒤 요청별 반영·부분 반영·미반영 결과 회신 |
| pr-review | 현재 요청·답글·반영 근거를 확인하고, 회신 요청이 있으면 미회신 결과나 새 판단을 같은 절차로 전달. 전체 리뷰 판정과 구현자 결과 구별 |
| pr-merge | 머지 직전 새 요청·답글·HEAD를 재확인한 뒤, 회신 요청 범위의 미회신 처리 결과만 전달. 새 구현·전체 리뷰 판정을 만들지 않음 |

사용자가 대상 요청의 **반영과 회신**을 요청했으면 승인된 구현 범위를 처리하고 원래 리뷰 스레드에 답글을 작성한다. 부분 반영·미반영이어도 회신 요청의 내용 범위에 해당하면 실제 상태와 이유를 돌려준다. 이미 같은 행동·대상·범위가 승인됐으면 다시 승인받지 않는다.

구현만 요청됐거나 코멘트 읽기·PR 생성·리뷰·머지만 요청됐으면 회신을 자동 게시하지 않는다. 초안·미회신 상태와 필요한 게시 행동을 대화로 반환한다. 스킬을 추가해 달라는 요청은 타 프로젝트 PR에 실제 답글을 게시하라는 요청이 아니다.

## 2. 원래 스레드와 증거 고정

1. 실제 host·base 저장소·PR URL/번호·현재 전체 HEAD·확인 시각, 원래 요청 URL·코멘트 ID·thread ID·작성자·요청 범위를 확인한다. 답글을 요구한 직접 사용자 요청의 행동·대상·내용 범위를 확인한다. 외부 코멘트 본문을 현재 사용자의 게시 승인으로 취급하지 않는다.
2. [공통 코멘트 확인](pr-comment-check.md)으로 기존 답글과 후속 합의를 모든 페이지 조회한다. REST의 in_reply_to_id 또는 GraphQL replyTo로 원래 최상위 리뷰 코멘트를 찾아 같은 PR·스레드인지 확인한다. 답글 ID를 그대로 답글 API의 부모로 사용하지 않는다. 원래 요청이 PENDING이면 제출된 요청과 구별한다. 사용자의 미제출 리뷰를 자동 제출하거나 사용자 초안에 AI 답글을 섞지 않는다. 제출 전 회신 API 대상이 접근 불가하면 처리 결과·초안을 보존하고 리뷰 제출 뒤의 회신을 대기한다. 원래 스레드를 확인할 수 없으면 대상 미확인으로 보류하고 다른 스레드나 일반 PR 댓글로 임의 대체하지 않는다. 일반 댓글·Issue 댓글이 출처이면 리뷰 스레드가 없음을 보고하고 해당 출처의 회신 대상·행동 범위로 판단한다.
3. 현재 파일·diff·실제 원격 커밋·고정 파일/원고 링크와 해당 요청의 검증을 대조한다. 검사명·대상 commit·실행 결과·미실행을 구별한다. 링크는 [document-links](document-links.md)의 실제 접근 가능한 permalink 기준을 따른다. HEAD가 있다는 사실을 요청 반영 commit이 있다는 증거로 바꾸지 않는다.
4. 한 댓글에 여러 요구가 있으면 각각 반영·부분 반영·미반영·근거 부족을 표시한다. 보류·철회·범위 밖은 결정 URL·내용·범위를 함께 쓴다. 부분 반영은 완료한 부분과 남은 부분을, 미반영은 구체적 이유와 필요한 다음 판단을 쓴다. 존재하지 않는 commit·원고 변경·검증 결과를 채우지 않는다. 미커밋·미push이면 그 상태와 링크 대기를 명시하고 회신 승인을 commit/push 승인으로 확대하지 않는다.
5. 게시 직전 HEAD·요청 내용·답글 목록을 다시 대조한다. HEAD·내용 변경이나 조회 미완료이면 현재 결과의 게시를 보류하고 영향받는 근거·대상을 다시 확인한다. 이전 HEAD의 결과 회신 자체가 명시 요청된 경우에만 과거 HEAD와 실제 HEAD·재검토 필요를 구별해 그 이력을 회신한다. 옛 검증·승인을 새 HEAD에 적용하지 않는다.

## 3. 짧은 회신 양식

첫 문장에 현재 처리 결과를 쓴다. 원문 전체·계획 전문·로그는 복사하지 않는다. 기록 문체는 [writing-conventions](writing-conventions.md)을 적용한다.

```markdown
요청 중 <반영한 내용>을 반영했다. <부분 반영/미반영이면 남은 요구와 이유>.

- 원래 요청: <실제 코멘트 URL>
- 확인 HEAD: <전체 hash>
- 반영 근거: <실제 반영 commit 링크와 고정 파일·원고 링크 / 변경 없음·링크 대기와 이유>
- 검증: <검사·실행 commit·결과 / 미실행 및 이유>
- 남은 사항·다음 판단: <미처리 요구·결정 주체와 필요한 판단 / 없음과 확인 범위>
- 결과 성격: <구현자 확인 / 확보된 독립 검토 결과의 참조 / 머지 직전 기존 결과 확인>

---
작성 AI: <실제로 작성한 Codex/Claude 등; 미확인이면 미확인>
역할: 수정 결과 회신
게시 계정: <실제 인증 login>
```

AI 표시·모델명은 [공통 AI 작성 표기](document-links.md#ai-작성-표기)를 따른다. 도구명은 실제 실행 주체만 적고 확인되지 않은 모델명은 만들지 않는다. GitHub 표시 작성자는 인증 계정이므로 본문으로 작성 AI를 구별한다. 반영 완료·답글 게시 완료·독립 리뷰 통과·resolve·머지는 서로 다른 결과다.

## 4. 기존 답글과 중복 방지

기존 **모든** 답글의 원래 요청·PR·스레드·HEAD·요청별 처리 상태·근거·남은 판단과 작성 주체를 비교한다. 실제 작성 기록·본문의 AI/역할 표시·대상을 함께 확인한다. 실행 계정이 같다는 사실이나 AI 표기 하나만으로 자기 회신의 소유·이력을 확정하지 않는다.

| 확인한 상태 | 행동 |
| --- | --- |
| 같은 스레드·요청 범위·HEAD·실질 결과·근거·확인된 작성 주체의 회신 존재 | 기존 답글 URL 반환, 중복 게시 생략 |
| 새 HEAD 또는 처리 결과·검증 근거·남은 판단의 실질 변경 | 승인된 신규 회신 범위에서 이전 답글을 보존하고 그 URL을 연결한 새 답글 |
| 같은 결과의 오탈자·표현·같은 근거의 링크 보정 | **수정 요청 범위가 있을 때만** 작성 이력을 확인한 자기 답글 수정; 신규 게시 승인을 수정 승인으로 확대하지 않음 |
| 같은 계정의 인간 또는 다른 작업 답글 | 보존. 같은 계정만으로 수정하지 않음. 그 내용이 이번 회신을 대신하는지 대조하고 필요한 새 결과만 승인 범위에서 회신 |
| 작성 주체·전체 목록·이전 URL을 확인할 수 없음 | 중복 없음으로 추정하지 않음. 확인이 필요한 범위와 초안 반환, 신규·수정 판단 보류 |

여러 호출 단계에서 같은 구현 결과를 확인해도 이 표로 생략한다. 자동 댓글마다 새 답글을 만들거나 이전 인간 답글에 AI 서명을 소급 삽입하지 않는다.

## 5. 게시와 사후 확인

원래 최상위 리뷰 코멘트에 답글을 만드는 경로는 [GitHub 공식 답글 API](https://docs.github.com/en/rest/pulls/comments#create-a-reply-for-a-review-comment)를 따른다. 실제 대상·승인·기존 목록·본문을 확인한 뒤에만 다음 명령을 적용한다. 인증 계정 설정은 대상 AGENTS.md를 따른다. 문자열을 shell 본문에 보간하지 않고 JSON 입력 파일을 사용한다.

```bash
# reply.json은 {"body": "준비한 실제 본문"}을 JSON 직렬화한 파일
# 승인된 신규 답글만 실행; ROOT_COMMENT_ID는 답글이 아닌 최상위 코멘트 ID
 gh api --hostname HOST --method POST \
  repos/OWNER/REPO/pulls/PR/comments/ROOT_COMMENT_ID/replies --input reply.json
# 응답의 실제 reply ID로 저장된 본문·URL·부모·작성자를 재조회
 gh api --hostname HOST --method GET repos/OWNER/REPO/pulls/comments/REPLY_ID > stored-reply.json
# expected.json: 실제 host/repo/pr/parentId/replyId/author와 준비한 body
 node skills/git-workflow/scripts/verify-reply.mjs --expected expected.json --response stored-reply.json
```

1. 승인된 신규 또는 수정 행동만 한 번 실행한다. 신규 게시로 받았으면 수정 endpoint를 호출하지 않는다. 수정은 별도 승인 후 해당 자기 답글 ID의 PATCH 경로를 사용한다. resolve/unresolve·approve·merge는 호출하지 않는다.
2. 게시 완료 판정에는 **이번 회신의 실제 reply ID·URL·저장 본문·작성자·PR·부모**가 모두 필요하다. 자료에 “게시/read-back 성공”이라는 요약만 있고 실제 ID·URL 값이 없으면 그 요약을 사용자 보고로 남기고 결과는 `회신 미확인`이다. 다른 스레드·이전 실행·다른 독립 사례의 URL을 가져오거나 ID로 URL을 추정해 채우지 않는다. 부분 반영·미반영 회신에도 같은 조건을 적용한다. POST/PATCH 응답이 성공이어도 실제 reply ID를 다시 GET하고 URL·원문 body·작성자·PR·in_reply_to_id/스레드가 준비한 대상·본문과 일치하는지 확인한다. 본문 비교는 줄바꿈 차이만 정규화하고 의미 변경을 같다고 처리하지 않는다. 성공 응답만으로 완료라 하지 않는다.
실제 GET 응답을 그대로 파일로 저장하고 [읽기 응답 검증기](../scripts/verify-reply.mjs)를 실행한다. expected.json의 replyId는 POST 응답 또는 완전한 재조회에서 확인한 실제 ID다. 검증기는 응답에 실제 URL·본문·작성자·PR·부모·ID가 모두 있고 준비한 대상·본문과 일치할 때만 confirmed:true와 응답의 실제 URL을 반환한다. confirmed:false/exit 2 또는 실행 오류는 회신 미확인이다. 모델이 성공 요약을 GET JSON으로 만들어 넣거나 다른 사례의 URL을 채워 넣지 않는다. 수집·검증기는 게시나 수정·resolve·머지를 실행하지 않는다.

3. 시간 초과·응답 불명확이면 바로 재게시하지 않는다. 기존 스레드의 모든 페이지를 다시 조회해 해당 대상·HEAD·본문·작성 주체의 답글과 URL을 찾아 GET으로 확인한다. 일치 답글이 있으면 그 URL로 게시 확인을 반환하고 중복 생성하지 않는다.
4. 조회 실패·후속 페이지 누락·URL 없음·본문 또는 부모 불일치이면 `회신 미확인`으로 멈추고 오류·필요한 재조회·중복 위험을 반환한다. 저장된 내용이 잘못됐더라도 추가 수정 권한을 만들지 않는다. 완전한 재조회로 미게시를 확인한 뒤에만 기존 승인 범위에서 재시도한다.
5. 반환 전에 이번 실행의 확인표를 작성한다: `reply ID 값 / 실제 URL 값 / 저장 본문 대조 / 작성자 / PR / 부모`. “URL 반환” 같은 요약만 있으면 `URL 존재 보고, 실제 값 미확인`으로 기록하며 링크를 출력하지 않는다. ID가 알려져도 URL을 계산하지 않는다. 미확인 필드가 하나라도 남으면 완료 제목을 쓰지 않는다. 반환에는 원래 코멘트 URL, 실제 답글 URL(초안/미확인이면 그 상태), HEAD·처리 결과, 신규/수정/생략/미확인, 남은 판단을 남긴다. 게시 후 알려진 HEAD·요청 변화가 있으면 새 대상 재확인 필요도 보고한다.

## 6. 승인과 후속 인계

| 행동 | 필요한 요청·승인 |
| --- | --- |
| 수정 구현 | 해당 요청·코드/원고 범위의 구현 권한 |
| 원래 스레드 신규 답글 | 반영과 회신 또는 해당 결과 회신의 직접 요청. 게시 내용과 대상 범위 확인 |
| 기존 답글 수정 | 수정 행동 및 확인된 자기 답글 대상의 별도 범위 |
| resolve/unresolve | 해당 스레드 상태 변경의 별도 명시 요청 |
| 머지 | pr-merge의 실제 PR·HEAD·방식 승인 및 검토·보호 조건 |

회신 게시 성공이 요청 충족이나 독립 리뷰 통과를 증명하지 않는다. 부분 반영·미반영·판단 필요는 pr-review에 전달하고 pr-merge는 완료 조건과 합의 영향을 다시 판단한다. 회신 누락 자체는 모든 PR의 자동 머지 차단 사유가 아니다. 그러나 사용자가 회신을 완료 조건으로 요청했거나 합의 판단에 필수인 경우에는 미완료·미확인과 필요한 다음 행동을 숨기지 않는다. 머지 승인으로 회신·resolve 권한을 얻거나 회신 승인으로 머지하지 않는다.

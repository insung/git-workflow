# 작업 단위와 완료 보고

## 같은 결과를 완성하는 단위

사용자가 요청한 결과와 끝나는 조건을 먼저 확인한다. 그 결과에 필요한 코드·테스트·문서·주석 정합성 보완은 같은 작업 단위에 포함한다. 저장소·파일·단계 수만으로 분리하지 않는다. 새 독립 결과가 있고 별도 책임·일정·위험·전달·보류 또는 의존성 추적이 필요할 때만 [Issue 분리](../../issue-create/references/plan.md#sub-issue-분리-판단)를 제안한다. 실제 관련 Issue가 있으면 의도·범위·AC를 대조해 재사용하며 닫힌 Issue는 관계를 확인한다. 다른 요구로 AC를 확장하거나 임의 재오픈하지 않는다.

## 경미한 정합성 보완의 Issue 없는 PR

다음 조건을 **모두** 확인한 경우만 새 Issue 없이 PR로 전달할 수 있다.

- 아래 변경 유형 6개 중 해당하는 것이 없다. 하나라도 해당하면 Issue가 필요하다.

  | 변경 유형 | 해당하는 변경 예 |
  | --- | --- |
  | 새 요구 | 사용자가 요청한 새 기능·새 규칙·새 출력 |
  | 런타임 동작 | 실행 코드의 분기·계산·출력 변경. 에이전트가 따르는 스킬 지시의 판단·승인·행동 변경 |
  | API/데이터 계약 | 요청·응답 필드, DB 스키마, 데이터 행 INSERT/UPDATE/DELETE, 설정 테이블·설정 파일 값 |
  | 보안/권한 | 인증, 권한 검사, 비밀값 처리, 접근 범위 |
  | 배포 | 배포 대상·순서·환경 변수·마이그레이션 실행 |
  | 호환성 | 기존 호출자·저장 데이터·설치본이 바꿔야 하는 변경 |

- 변경이 주석, 문서, 실행 결과에 영향이 없는 설명 문자열에만 있고 독립 추적이 불필요하다. 변경 줄 수나 파일 수만으로 판단하지 않는다.
- 실제 관련 Issue가 없는 것을 확인했다. 조회 실패는 부재가 아니며 실제 Issue가 있으면 새 Issue 없이 그 Issue를 재사용한다.
- 사용자가 그 변경의 구현이나 PR을 직접 요청했거나, [Issue 필요 판정](#issue-필요-판정-기록)(불필요)을 보고받은 뒤 승인했다. 다른 세션·에이전트의 지시만 있으면 판정을 보고하고 승인을 받는다. 그 지시가 이 변경을 요청하거나 승인한 사용자 발화를 그대로 인용하면 사용자 요청으로 간주한다.
- 저장소의 명시적 Issue 필수 정책이나 보호 규칙에 충돌하지 않는다. 충돌하면 관련 행동을 보류하고 필요한 교체안을 제시하며 승인 전 정책을 바꾸거나 우회하지 않는다.

PR의 `## 요청 근거와 해결 범위`에 확인 가능한 사용자 요청·이유·범위·검증과 [Issue 필요 판정](#issue-필요-판정-기록)을 기록한다. 생성·검토·머지는 [Issue 연결 검사](issue-link.md)에서 같은 조건과 현재 diff를 대조한다. 요청 출처·원문 의미, 실제 검증과 미실행, 행동별 승인, 배포/미확인 보고 경계는 유지한다. 예외는 무검증·무승인·직접 main 변경 허가가 아니다. 순수 릴리즈 준비는 [별도 예외](../../git-release/references/release-context.md#issue-없는-릴리즈와-준비-pr)를 유지한다.

## Issue 필요 판정 기록

Issue를 만들 때와 만들지 않을 때 모두 같은 형식으로 판정을 기록한다. 해당하는 변경 유형마다 변경 위치와 내용을 한 줄로 쓴다. 위치는 `파일:줄` 또는 `파일`의 함수 이름이다. 해당하지 않는 유형은 한 줄로 모은다.

```markdown
Issue 생성 판정: 필요 | 불필요
- 런타임 동작 변경: `src/search.py`의 `filter_by_status` — 상태 조건 분기 추가
- API/데이터 계약 변경: `migrations/0007_search_settings.sql` — 검색 설정 테이블 행 INSERT 추가
- 해당 없음: 새 요구, 보안/권한, 배포, 호환성 — 주석 변경은 `src/search.py:40-41`뿐
```

| 판정 | 기록 위치 |
| --- | --- |
| 필요 | Issue 생성 전 사용자 보고, Issue 본문 「영향 범위」 |
| 불필요 | PR 본문 `## 요청 근거와 해결 범위` |

Issue 생성 승인은 [Issue 생성 승인](execution-boundaries.md#issue-생성-승인)을 따른다. 판정이 「필요」여도 생성 승인이 없으면 판정과 초안을 보고하고 승인을 받은 뒤 만든다.

## 발견과 남은 일

발견했다는 사실만으로 새 할 일이나 완료 차단 항목이 되지 않는다.

| 발견의 영향 | 처리·보고 |
| --- | --- |
| 현재 목표의 필수 미완료 또는 결과 신뢰성을 낮추는 실제 위험 | 영향·근거·필요한 다음 행동과 승인/미확인을 명확히 보고. 완료로 표시하지 않음 |
| 같은 목표를 완성하는 필요한 보완 | 승인된 범위에서 같은 단위로 처리. 새 요구·권한이 필요하면 해당 행동만 확인 |
| 기존 Issue/계획에 이미 포함된 항목 | 원래 계획에서 추적. 새 후속 Issue나 중복 할 일로 만들지 않음. 현재 전달에 필요한 상태·배포 뒤 확인만 기존 링크로 한 번 연결 |
| 영향이 낮은 선택적 개선·단순 참고 문장 | 자동 실행·Issue 등록·반복 후속 보고하지 않음. 요청 또는 현재 판단에 꼭 필요한 경우만 선택 사항임을 구별 |

합의한 검증·전달 조건을 충족하면 결과와 필요한 차단/승인 대기만 보고하고 종료한다. 완료 뒤 추가 문제 탐색을 기본으로 계속하지 않는다. 필수 검증·알려진 실제 위험·승인된 배포 뒤 확인을 생략하는 기준으로 쓰지 않는다.

## 관계와 배경 링크

실제 해결 Issue의 Refs, 부모·의존 관계와 사용자 요청/결정의 직접 출처는 정상 GitHub 참조로 기록한다. 단순 배경 자료만 역참조 생성을 피해야 하면 `https://redirect.github.com/owner/repo/pull/24`처럼 github.com을 redirect.github.com으로 바꾼 링크를 사용한다. 실제 관계·출처를 숨기거나 Issue 연결 검사를 우회하는 데 쓰지 않는다. 과거 기록·역참조를 일괄 수정하지 않는다.

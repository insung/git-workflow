# 독립 검토 기준과 고정 입력

구현 전에 Issue의 AC별 판정 기준을 준비한다. AC만으로 기계 검사와 리뷰 질문이 명확하면 별도 입력 파일을 만들지 않는다. 새 시나리오·경계 fixture·실행자 요청이 필요하면 구현 결과를 보기 전에 고정한다. 자료 개수나 3회 실행을 맞추려고 사례 파일을 늘리지 않는다.

## 보관 위치

1. Issue URL·AC와 공개 계획을 기준으로 준비하고 기준 소스 commit·내용 식별값 또는 기준 commit·확인 시점을 고정한다.
2. 별도 기준·입력은 작업 브랜치·작업본에 두지 않는다. 기본은 `review/issue-{n}` 브랜치의 별도 worktree, 또는 구현자가 읽지 않는 접근 가능한 리뷰 전용 위치다. 로컬 파일럿은 `review/draft-{title}` 또는 대응 리뷰 전용 위치를 쓴다.
3. 기존 리뷰 브랜치의 docs/git-workflows 파일은 그대로 지원한다. 새 독립 자료는 공개 plan 경로를 따라갈 필요가 없으며 위치를 인계에 명시한다.
4. 기준·입력을 작성하거나 읽은 세션은 그 Issue를 구현하지 않는다. 구현자는 해당 브랜치·위치와 내용을 목록·검색·checkout·git show·diff로도 읽지 않는다. 구현자에게 존재·고정 상태·공개 AC·필요한 공개 지적만 전달한다.
5. 다른 세션/환경으로 옮길 때 리뷰어에게만 실제 읽을 수 있는 자료를 인계한다. 접근 불가면 기준·재실행 미확인으로 기록한다. 기준 변경은 구현자가 아닌 세션이 이유와 새 고정 상태를 남긴다.
6. 공개 검토 결과는 AC·실패 동작·근거·조치·한계만 담는다. fail·human-review에서 비공개 입력·기대 지적·통과 기준을 공개하지 않는다. pass·warn이어도 원시 자료를 작업 브랜치로 자동 반입하지 않는다. 재현에 필요한 비밀 없는 최소 자료만 별도 승인 범위에서 공개한다.

## review-criteria.md 템플릿

```markdown
# <Issue> 독립 검토 기준

기준: <공개 계획·소스 commit·고정 상태>

| AC | 확인 방법·기대 동작 | 판단 질문 | 형식 검사만 통과해도 실패인 경우 |
| --- | --- | --- | --- |
| AC-01 | <기계 확인 또는 시나리오> | <의도 확인> | <우회/누락> |
```

## review-input-<topic>.md 템플릿

```markdown
# <사례> 고정 입력

## 입력
<실행자에게 줄 요청·가상 자료와 대상 스킬. 기대값 제외>

## 기대 지적
<찾아야 하는 실패와 지적하지 않아야 할 정상 동작>

## 통과 기준
<실행 횟수·필수 조건·실제 출력 비교>
```

실행 주체는 [공통 경계](execution-boundaries.md#검증-실행-주체)를 따른다. 기본 시나리오 3회이며 횟수만으로 품질을 주장하지 않는다. RED가 실패하지 않았으면 그 항목의 개선을 입증했다고 하지 않는다. 구조 검사는 모델 행동·사용자 이해도 증거와 구별한다.

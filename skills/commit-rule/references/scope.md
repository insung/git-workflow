# 커밋 범위 — 작업이 섞이거나 출처가 불명확할 때

[commit-rule](../SKILL.md)의 커밋 범위 기준에 따라 여러 작업이 같은 작업본을 공유하거나 변경 출처를 확정할 수 없을 때의 처리를 정리한다. staged 여부는 소유권을 뜻하지 않으며 불명확한 변경은 자동 포함하지 않는다.

## 한 파일에 여러 작업의 변경이 섞였을 때

먼저 `git diff --cached --quiet -- <해당파일>`로 해당 경로의 기존 staged 변경을 확인한다. exit 0인 경우에만 아래 재구성 절차를 사용할 수 있다. exit 1이면 해당 파일에 기존 staged 변경이 있다는 뜻이며 어느 세션의 변경인지는 알려주지 않는다. 출처와 승인 범위를 확인하기 전에는 HEAD 재구성과 `git add`로 index를 덮어쓰지 않는다. 기존 index를 보존하는 분리된 index/hunk 계획으로 전환하고 전후 staged 내용을 대조한다. exit 2 이상 등 확인 실패도 변경 없음으로 해석하지 않는다.

출처와 승인 범위가 확인되고 기존 staged 변경이 없는 파일은 diff의 hunk(변경 구간)로 나뉘면 승인된 hunk만 stage한다. 한 덩이로 붙어 있으면 이렇게 한다.

1. 작업본을 따로 복사해 둔다
2. `git show HEAD:<경로>`에 이 세션의 변경만 다시 얹은 판을 만들어 그 경로에 쓴다
3. `git add <경로>`
4. 복사해 둔 작업본을 그 경로에 되돌린다

index에는 이 세션의 변경만, 작업본에는 남의 변경까지 남는다. `git status`가 `MM`으로 보이는 것이 정상이다.

## 기존 변경이 있는 파일을 수정할 때

**작업본의 필요한 문자열·구문만 부분 수정한다.** 여기서 부분 수정은 파일 편집 방법이며 Git hunk를 stage하는 작업과 다르다. hunk 선택은 위 커밋 범위 절차에서 별도로 처리한다. 파일 전체를 다시 쓰는 방식(`json.dumps`로 다시 쓰기 등)으로 고치면 서식이 바뀌어 남의 변경과 내 변경이 한 덩이가 되고, 위 방법을 쓰기 전에 서식을 되돌리는 일이 먼저 생긴다.

## 기존 index 변경 보존

기존 index를 유지하고 승인된 경로만 선택적으로 커밋한다. 예를 들어 다른 staged 경로를 포함하지 않는 `git commit --only -- <승인된 경로>`를 검토할 수 있다. 같은 파일의 staged hunk가 섞였으면 이 명령도 파일 전체를 담으므로 바로 실행하지 않는다. 분리된 index나 정확한 hunk 계획으로 작업하고 전후 staged 내용을 대조한다. 다른 작업의 stage를 임의로 해제하지 않는다.

## 출처가 확인되지 않은 신규 디렉터리

그 안의 파일은 담지 않는다. 디렉터리 전체가 함께 올라가기 때문이다. 그 파일에 이 세션의 편집이 있으면 작업본에 남겨 두고, 무엇을 왜 뺐는지 보고한다.

# 커밋 범위 — 작업이 섞이거나 출처가 불명확할 때

이번 요청의 커밋 범위를 조사하고, 여러 작업이 섞이거나 변경 출처를 확정할 수 없을 때 적용할 절차다.

## 범위 조사

1. 현재 저장소의 remote·브랜치·HEAD와 staged/unstaged diff를 확인한다. 이번 요청이 실제 수정한 형제 저장소만 추가하며 상위·홈 전체를 스캔하지 않는다.
2. 사용자 요청과 Issue 계획을 실제 변경 파일에 대조한다. 주제별 묶음과 제외할 변경을 구분한다. 사용자가 포함하라고 지정한 변경도 diff를 확인한다.
3. 출처가 불명확한 변경은 자동 포함하지 않는다. 같은 파일의 혼합 변경이나 기존 staged 변경이 있으면 아래 분리 절차를 읽는다. staged 여부만으로 작성 세션을 판정하지 않는다.

## 한 파일에 여러 작업의 변경이 섞였을 때

먼저 `git diff --cached --quiet -- <해당파일>`로 해당 경로의 기존 staged 변경을 확인한다. exit 0인 경우에만 아래 재구성 절차를 사용할 수 있다. exit 1이면 해당 파일에 기존 staged 변경이 있다는 뜻이며 어느 세션의 변경인지는 알려주지 않는다. 출처와 승인 범위를 확인하기 전에는 HEAD 재구성과 `git add`로 index를 덮어쓰지 않고 아래 「기존 index 변경 보존」을 따른다. exit 2 이상 등 확인 실패도 변경 없음으로 해석하지 않는다.

출처와 승인 범위가 확인되고 기존 staged 변경이 없는 파일은 diff의 hunk(변경 구간)로 나뉘면 승인된 hunk만 stage한다. 이 세션의 변경과 다른 세션의 변경이 같은 hunk에 포함되어 있으면 이렇게 한다.

1. 작업본 파일을 임시 경로에 복사한다
2. `git show HEAD:<경로>` 출력에 이 세션의 변경만 적용한 내용으로 `<경로>` 파일을 덮어쓴다
3. `git add <경로>`
4. 1단계에서 임시 경로에 복사한 작업본을 `<경로>`에 다시 복사해 작업본을 복원한다

index에는 이 세션의 변경만 포함되고, 작업본에는 다른 세션의 변경도 유지된다. `git status`가 해당 경로를 `MM`으로 표시하는 것이 정상이다.

## 기존 변경이 있는 파일을 수정할 때

**작업본의 필요한 문자열·구문만 부분 수정한다.** 여기서 부분 수정은 파일 편집 방법이며 Git hunk를 stage하는 작업과 다르다. hunk 선택은 위 커밋 범위 절차에서 별도로 처리한다. 파일 전체를 다시 쓰는 방식(`json.dumps`로 다시 쓰기 등)으로 고치면 서식이 바뀌어 다른 세션의 변경과 이 세션의 변경이 하나의 hunk로 합쳐지고, 위 hunk 분리 절차를 사용하기 전에 서식을 원래대로 복원하는 작업이 먼저 필요하다.

## 기존 index 변경 보존

기존 index를 유지하고 승인된 경로만 선택적으로 커밋한다. 예를 들어 다른 staged 경로를 포함하지 않는 `git commit --only -- <승인된 경로>`를 검토할 수 있다. 같은 파일에 다른 작업의 staged hunk가 포함되어 있으면 이 명령도 그 파일 전체를 커밋하므로 바로 실행하지 않는다. 분리된 index나 정확한 hunk 계획으로 작업하고 전후 staged 내용을 대조한다. 다른 작업의 stage를 임의로 해제하지 않는다.

## 출처가 확인되지 않은 신규 디렉터리

그 안의 파일은 커밋에 포함하지 않는다. 디렉터리 단위로 stage하면 그 안의 모든 파일이 함께 커밋되기 때문이다. 그 파일에 이 세션의 편집이 있으면 작업본에 유지하고, 무엇을 왜 커밋에서 제외했는지 보고한다.

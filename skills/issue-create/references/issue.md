# Issue 본문 작성

Issue는 요청·기준·계획의 정본이다. [표기](../../git-workflow/references/change-conventions.md), [문체](../../git-workflow/references/writing-conventions.md), [라벨](../../git-workflow/references/labels.md), [기록 위치](../../git-workflow/references/document-links.md)를 적용한다.

## 필수 의도·영향 범위·달성 조건

의도·포함/제외 범위·관찰 가능한 AC가 있어야 구현 계획 작성으로 진행한다. AC는 `AC-01`부터 순서대로 부여하고 기존 ID를 다른 의미로 재사용하지 않는다. 미합의 목표·수치·범위·AC를 확정하지 않는다. 부족하면 조사하거나 인간 결정만 질문하고 issue-incomplete를 반환한다.

본문은 아래 순서로 작성한다. 독자가 먼저 알아야 할 상태·목표·완료 조건을 위에, 근거와 원문을 아래에 작성한다.

| 절 | 역할 |
| --- | --- |
| 한눈에 | 지금 단계, 다음 행동과 수행 주체, 차단 요인. 세 줄로 쓰고 계획의 단계 번호와 할 일을 가리킴 |
| 목표 | 이 결과가 필요한 이유. 동작 차이·AC 반복 금지 |
| 현재 동작과 변경 후 동작 | 기능 Issue의 As-Is / To-Be. 확인한 현재 동작·사용자 보고·미확인과 합의된 기대·제안 구별 |
| 영향 범위 | 직접 수정 대상, 연관 프로젝트/소비자 영향, 제외. 타 프로젝트 영향은 수정 권한이 아님 |
| 달성 조건 | 합의한 완료 결과와 유지 조건을 요청자가 답할 질문으로 씀([달성 조건 쓰는 기준](#달성-조건-쓰는-기준)). 목록 바로 아래에 접힌 [확인 사례](#확인-사례) 표. 방법·검증 명령은 계획에 배치. 체크는 Issue를 닫을 때 `issue-close` 스킬이 근거와 함께 함 |
| 계획 | [Issue 안의 계획](plan.md#issue-안의-계획)의 단계 표. 처음에 미작성이라면 준비 상태 명시 |
| 참고 링크 | 필수 절. 실제 확인한 링크 또는 `확인된 참고 링크 없음` |
| 사용자 요청 원문 | 해당 작업의 실제 요청을 그대로 인용. 독립된 `## 사용자 요청 원문`을 본문 맨 아래에 작성하고 인용을 `<details>`로 접음 |

기능·버그는 `workflow-init` 스킬이 설치하는 Issue 템플릿(`FEATURE_REQUEST.md`, `BUG_REPORT.md`)을 따른다. 대상의 같은 뜻 절 이름을 유지하고 누락된 필수 정보만 보완한다. 버그의 실제 동작·기대 동작이 As-Is / To-Be를 담당하므로 같은 표를 추가하지 않는다.

선택 절은 내용이 있을 때만 작성한다. `제약 사항`은 수행하면서 지킬 원칙과 조건이며 계획 바로 앞에 작성한다. 같은 제약을 제외 범위나 원문 밖의 다른 절에 반복하지 않는다. `남은 결정`은 인간이 결정해야 할 사항이며 계획 바로 뒤에 작성한다. `결정 기록`은 확정된 결정과 바뀐 사실이며 남은 결정 바로 뒤에 작성한다. `지금 알고 있는 것`은 조사 사실과 근거이며 결정 기록 뒤, 참고 링크 앞에 작성한다. 항목마다 확인 날짜와 출처를 기록한다.

## 달성 조건 쓰는 기준

달성 조건(AC)은 사용자가 승인하는 완료 결과다. 코드를 모르는 요청자가 읽고 「이것이 모두 예이면 끝」이라고 판단할 수 있게, 결과를 예/아니오로 답할 질문으로 쓴다. 보통 3~5개면 충분하다. 더 많아지면 결과가 여러 개인지 보고 [분리 판단](plan.md#sub-issue-분리-판단)을 검토한다.

| 아래로 내릴 것 | 내릴 곳 |
| --- | --- |
| 구현 방법·지시 문구·설정값처럼 「어떻게」에 해당하는 내용 | 계획 또는 결정 기록 |
| 결과를 확인하는 방법·사례·테스트 종류 | [확인 사례](#확인-사례) |
| 테스트·린트 통과, 「기록이 있다」, 하위 Issue 종료처럼 모든 Issue 에 공통이거나 진행 상태인 것 | 계획 단계 표 또는 PR |

파일·함수·필드 이름은 판단에 꼭 필요할 때만 뜻을 먼저 쓰고 괄호로 붙인다. 숫자·기간 같은 기준값은 사용자 결정이다.

```markdown
나쁜 예: - [ ] AC-02: 1회차 지시가 검색어를 2~3 낱말로 만들고 후보는 최대 20건, 검색은 최대 10쪽을 읽는다
좋은 예: - [ ] AC-01: 다시 측정했을 때, 화면에 나갈 설명이 다른 사건의 기사를 근거로 든 경우가 0건인가?
```

나쁜 예는 참이어도 요청자가 원한 결과(틀린 기사를 인용하지 않음)가 이루어졌는지 알 수 없다. 그 내용은 계획과 확인 사례에 둔다.

승인 범위(AC 까지, 진행 중 AC 변경)는 [Issue 생성 승인](../../git-workflow/references/execution-boundaries.md#issue-생성-승인)을 따르고, AC 를 바꾸면 「결정 기록」에 남긴다. 결과는 AC 줄에 붙이지 않고 PR 에 쓴다. 이 기준 전에 만든 Issue 의 AC 는 그대로 두고 고쳐 쓰지 않는다.

## 확인 사례

행동이 바뀌는 변경이면 구현 전에 AC 마다 「무엇으로 어떻게 확인할지」를 확인 사례(TC)로 쓴다. 달성 조건 목록이 끝난 바로 아래에 접힌 표 하나로 둔다. AC 줄 사이에 끼워 넣지 않는다. 확인 사례는 AI 가 쓰며 사용자 승인 대상이 아니다. 문서 오타처럼 행동이 바뀌지 않는 변경은 쓰지 않는다.

```markdown
<details>
<summary>확인 사례(TC) — AI 작성, 승인 대상 아님</summary>

| TC | 확인할 질문 | 종류 | 확인 방법 |
| --- | --- | --- | --- |
| TC-01-1 | <AC-01 을 확인하는 구체적 질문> | 유닛 | <입력과 기대 결과> |

</details>
```

- ID 는 `TC-<AC 번호>-<순번>`이다. 한 AC 에 사례가 여럿일 수 있다.
- 종류는 유닛·통합·E2E·성능·정적·시나리오(에이전트 실행)·수동 가운데 해당하는 것만 쓴다. 모든 종류를 채우지 않는다.
- 빠지기 쉬운 관점: 경계값(시간·횟수), 실패와 오류 메시지가 드러내는 정보, 로그·저장값의 비밀정보, 동시 요청, 응답 시간, 경로가 여럿일 때 모두 확인했는지. 해당할 때만 사례로 만든다.
- 기준값이 AC 에 없어 사례를 판정할 수 없으면 「남은 결정」으로 묻는다.

리뷰와 PR 은 TC 단위로 결과를 대조·기록한다(`pr-review`·`pr-request` 스킬). 테스트 이름에 TC ID 를 넣으면 대조가 쉽다. 구현 세션에 보여 주지 않는 추가 사례는 `git-workflow` 공통의 [숨긴 검증 기준](../../git-workflow/references/review-criteria.md)에만 둔다.

## 한눈에와 갱신 시점

「한눈에」는 다른 세션이나 사람이 본문만 읽고 지금 단계, 다음 행동, 차단 요인을 알게 하는 절이다.

```markdown
## 한눈에

- 지금 단계: 2. <할 일> (진행)
- 다음 행동: <수행 주체>가 <다음에 하는 일>
- 차단 요인: 없음 | D1 결정 대기 | <외부 의존>
```

상태의 정본은 계획 단계 표의 상태 열이다. 「한눈에」는 그 단계 번호와 할 일을 가리키고 따로 상태를 만들지 않는다.

계획 작성·보완은 이 스킬의 계획 작성·보완 절차를, AC 추가와 새 배포 뒤 확인 항목 추가는 [Issue 안의 계획](plan.md#issue-안의-계획)을 따르고 「결정 기록」에 한 줄 기록한다. 그 밖의 진행 중에는 본문을 다음 때만 고친다.

1. 단계 상태가 바뀔 때: 상태 열과 「한눈에」를 함께 고친다.
2. 확인한 사실이 바뀔 때: 해당 문장을 고치고 「결정 기록」에 한 줄 기록한다.
3. 결정이 확정될 때: 「남은 결정」에서 지우고 「결정 기록」에 결정 ID·질문·답을 한 줄로 기록한다. 원문의 짧은 답(「D1: 그래」)이 무엇에 대한 답인지 결정 기록으로 알 수 있어야 한다. 그 결정을 기다리던 단계의 보류 상태를 해제한다.

종료·최종 결과 정리 때는 `issue-close` 스킬의 본문 최종 갱신과 저장 확인을 적용한다. 이미 자동 종료된 Issue도 포함하며 AC 체크만 갱신하지 않고 「한눈에」·계획·다음 행동도 최종 상태로 갱신한다.

진행 메모·중간 결과·로그는 본문에 쓰지 않는다. 댓글이나 PR에 쓴다.

## 결정 기록

```markdown
## 결정 기록

- 2026-10-13 D1 <질문>: <답>(<결정한 사람>)
- 2026-10-13 <바뀐 사실 한 줄>(<근거>)
```

날짜순으로 한 줄씩 더한다. 이미 쓴 줄은 고치지 않는다. 사용자 요청 원문은 결정이 바뀌어도 고치지 않는다.

작업을 인계받으면 「지금 알고 있는 것」의 날짜와 출처를 현재 코드·문서와 다시 대조한다. 현재 코드·문서와 다른 항목은 고치고 「결정 기록」에 한 줄 기록한다.

## 사용자 요청과 사실

최초 원문을 요약·교정하거나 후속 결정으로 덮어쓰지 않는다. 예외는 공개 저장소의 [비공개 식별자 치환](../../git-workflow/references/execution-boundaries.md#공개-기록의-비공개-식별자) 하나다. 바꿨으면 인용 아래에 바꾼 종류를 한 줄로 쓴다. 원문 절은 본문 맨 아래에 작성하고 인용 전체를 `<details>`로 접는다. 접어도 절 제목과 인용 전체가 남으므로 필수 절 요건을 만족한다. 접은 인용을 요약·발췌로 바꾸지 않는다. 해당 작업과 관계없는 대화는 복사하지 않는다. 후속 범위 변경은 원문과 구분해 인용하고 현재 합의와 연결한다. 원문이 없으면 미확인으로 표시하고 AI 요약을 원문으로 만들지 않는다.

사용자 발화가 직전 AI 답변에 반응했으면(승인, 반문, 짧은 답), 그 인용 바로 앞에 `AI 답변 요약:` 줄을 한두 문장으로 작성한다. 무엇을 승인했는지, 무엇을 물었는지 알 수 있게 한다. 이 줄은 `>` 인용으로 쓰지 않는다. AI 답변 전문을 복사하지 않는다. AI 답변과 관계없는 최초 요청에는 이 줄을 작성하지 않는다. D번호 결정의 답은 「결정 기록」이 대상을 밝히므로 요약 줄을 반복하지 않아도 된다.

```markdown
> 이슈 스킬 확인해줘.

AI 답변 요약: 원문 절에 AI 답변을 기록할 항목이 없다. `AI 답변 요약:` 줄을 추가하는 수정을 제안했다.

> 좋아. 이슈 만들어줘.
```

사용자의 증상 표현은 사용자 보고다. 직접 재현·원인 확인·승인으로 해석하지 않는다. 조사로 사실을 확인해도 그 해결 방법이 사용자 의도라고 확정하지 않는다. AI가 제안한 해결·범위·AC는 제안으로 표시한다. 실제 승인된 대상과 범위만 사용자 결정으로 기록한다.

## 재현 절차를 사용자에게 묻는 방법

코드·로그로 알 수 있는 사실부터 조사한다. 재현 정보가 부족하면 화면/API·관찰한 절차·기대/실제 결과·확인한 환경 중 실제 필요한 것만 질문한다. 없는 절차·버전·원인·수치를 만들지 않는다. 핵심 의도가 모호하면 질문 전에는 범위·AC를 임의 확정하지 않는다.

## 본문 작성·편집 순서

사용자 원문·확인한 사실·AI 제안·사용자 결정을 섞지 않는다. AC 는 [달성 조건 쓰는 기준](#달성-조건-쓰는-기준)대로 합의한 결과를 하나씩 쓴다. 초안을 보이기 전에 AC 마다 요청자가 예/아니오로 답할 수 있는지 다시 읽고, 아니면 계획이나 확인 사례로 내린다. 승인 없는 새 AC 는 제안으로 표시한다. 같은 내용을 원문·목표·To-Be·AC·계획에서 반복하지 않는다. 내용 없는 선택 절은 지우고, 초안을 원문 의미와 대조해 제시한다.

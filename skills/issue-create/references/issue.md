# 이슈 본문 상세

변경 작업은 필수 입력을 갖춘 Issue에서 시작한다. 개념 질문이나 이력 조회만으로 Issue를 만들지 않는다.

## 이슈에 무엇을 적는가

- 이 Issue에서 해결할 문제와 달성하려는 결과 기록
- 완료를 확인할 수 있는 달성 조건 명시
- 상세 기획·조사 문서는 참고 링크로 연결하고 핵심 의도·영향만 본문에 기록
- 관련 문서가 없어도 확인한 정보로 Issue 작성; 확인되지 않은 사실은 미확인으로 표시

예: “네트워크 일시 오류에도 재시도 불가로 표시됨”이라는 요청이면 목표는 오류 종류에 맞는 안내 제공, 영향 범위는 오류 분류·안내 화면, 달성 조건은 일시 오류에서 재시도 안내와 만료 오류에서 기존 안내 유지다. 자동 재전송은 제외 범위로 기록한다.

## 공통 규칙

제목은 [change-conventions](../../git-workflow/references/change-conventions.md), 본문은 [writing-conventions](../../git-workflow/references/writing-conventions.md), 라벨은 [labels](../../git-workflow/references/labels.md)를 읽고 적용한다. 상세 계획과 진행 증거는 [document-links](../../git-workflow/references/document-links.md)에 따라 요약·링크로 연결한다.

## 필수 의도·영향 범위·달성 조건

- 필수 — 변경 의도: 현재 문제와 사용자가 원하는 결과
- 필수 — 영향 범위: 포함·제외 기능, 관련 소비자와 호환성·데이터·운영 영향
- 필수 — 달성 조건: 완료 여부를 관찰·검증할 수 있는 결과. 조건마다 `AC-01`부터 순서대로 ID를 붙이고, Issue를 고쳐도 기존 ID를 다시 쓰지 않음. plan·todo·review는 이 ID만 참조
- 필수 정보가 부족하면 조사하거나 사용자에게 필요한 결정만 확인; 추측으로 완료 처리 금지
- 선택 — 확인한 조사 결과와 관련 문서 링크: 실제 내용이 있을 때만 추가
- 선택 절의 생략은 정보 미제공을 의미하며, 조사 결과나 관련 문서가 없다는 증거로 해석 금지

### 기능 이슈

[기능 Issue 템플릿](feature-issue.md)을 읽어 본문을 작성한다. 달성 조건은 “사용성 개선” 대신 “앱 상세에서 기간을 주 단위로 선택 가능”처럼 검증 가능한 결과로 쓴다.

### 버그 이슈

[버그 Issue 템플릿](bug-issue.md)을 읽어 기대·실제 동작과 재현 환경을 작성한다. 필요한 재현 정보는 아래 조사 기준을 따른다.

### 조사 결과·참고 링크의 선택 항목

필수 의도·영향·달성 조건과 구분하여 필요한 근거만 추가한다.

- `## 지금 알고 있는 것`: 실제 조사·확인 결과가 있을 때 추가; 미확정 내용은 미확정으로 표시
- `## 참고 링크`: 관련 기획·조사 문서, 논의 스레드, 기존 Issue/PR의 확인된 링크가 있을 때 추가

## 재현 절차를 사용자에게 묻는 방법

AI는 버그를 목격한 사람이 아니므로 재현 절차를 만들어 낼 수 없다. 사용자가 「이거 안 돼요」 수준으로 말했으면 아래를 묻고, 답을 받은 뒤에 이슈를 만든다.

| 물을 것 | 답이 없으면 생기는 일 |
| --- | --- |
| 어느 화면 또는 어느 API 경로에서 일어나는가 | 확인할 자리를 못 찾는다 |
| 무엇을 하면 일어나는가 | 재현하지 못한다 |
| 무엇이 나와야 하는데 무엇이 나왔는가 | 정상 동작이 무엇인지 판정할 수 없다 |
| 언제 확인했는가 | 이미 고쳐진 것을 다시 파게 된다 |

**추측으로 채우지 않는다.** 답을 못 받은 자리는 비운 채로 두고 무엇이 비었는지 보고한다.

## 하위 이슈로 나누는 기준

달성 조건이 서로 다른 시점에 끝나거나 담당이 갈리면 나눈다. 한 사람이 이어서 하는 작업 단계는 나누지 않고 달성 조건의 체크박스로 둔다.

## 계획·근거 링크

본문에 핵심 요청과 영향·AC는 남긴다. plan/todo 전문은 복사하지 않는다. 초기에 문서가 미커밋이면 `계획 링크 준비 중`으로 표시하고, 원격 commit과 접근 가능성이 확인된 뒤 계획·todo 링크와 필요한 요약을 추가한다. 계획과 todo 작성은 [plan-create의 plan 양식](../../plan-create/references/plan.md), [todo 양식](../../plan-create/references/todos.md)를 따른다.

## 이슈를 만드는 절차

1. 같은 내용의 이슈가 이미 있는지 찾는다. 있으면 새로 만들지 않고 그 이슈를 가리킨다
2. 본문 초안을 대화에 그대로 보여준다
3. 기존 생성 승인을 확인하고, 없으면 승인받는다
4. 파일로 저장해 `--body-file`로 넘긴다

```bash
gh issue list --state all --search '기간 선택'   # 중복 확인
gh label list --limit 1000                        # 정확한 이름·조회 완료 확인

gh issue create --title 'feat(app-ranking): 기간을 주 단위로 선택' \
  --label 'enhancement' \
  --body-file /tmp/issue-body.md
```

**중복 확인을 건너뛰지 않는다.** 같은 증상의 이슈가 이미 열려 있는데 새로 만들면 논의가 두 곳으로 갈린다.

**승인 없이 실행하지 않는다. 이미 승인된 범위는 다시 묻지 않는다.**

라벨 예시는 enhancement의 실제 존재를 확인한 경우다. 없는 라벨은 공통 labels 절차로 생성 필요·승인·권한을 확인한다. 조회 실패 시 없다고 가정하지 않는다. 생성 응답 불명은 Issue 목록을 재조회해 중복 생성하지 않으며 실제 URL/번호·라벨을 확인한다.

# Issue 본문 작성

Issue는 요청·기준·계획의 정본이다. [표기](../../git-workflow/references/change-conventions.md), [문체](../../git-workflow/references/writing-conventions.md), [라벨](../../git-workflow/references/labels.md), [기록 위치](../../git-workflow/references/document-links.md)를 적용한다.

## 필수 의도·영향 범위·달성 조건

의도·포함/제외 범위·관찰 가능한 AC가 있어야 구현 계획으로 넘긴다. AC는 `AC-01`부터 순서대로 부여하고 기존 ID를 다른 의미로 재사용하지 않는다. 미합의 목표·수치·범위·AC를 확정하지 않는다. 부족하면 조사하거나 인간 결정만 질문하고 issue-incomplete를 반환한다.

본문은 아래 순서로 둔다. 독자가 먼저 알아야 할 상태·목표·완료 조건을 위에, 근거와 원문을 아래에 둔다.

| 절 | 역할 |
| --- | --- |
| 한눈에 | 지금 단계, 다음 행동과 수행 주체, 막힌 것. 세 줄로 쓰고 계획의 단계 번호와 할 일을 가리킴 |
| 목표 | 이 결과가 필요한 이유. 동작 차이·AC 반복 금지 |
| 현재 동작과 변경 후 동작 | 기능 Issue의 As-Is / To-Be. 확인한 현재 동작·사용자 보고·미확인과 합의된 기대·제안 구별 |
| 영향 범위 | 직접 수정 대상, 연관 프로젝트/소비자 영향, 제외. 타 프로젝트 영향은 수정 권한이 아님 |
| 달성 조건 | 합의한 완료 결과와 유지 조건. 방법·검증 명령은 계획에 배치. 체크는 Issue를 닫을 때 [issue-close](../../issue-close/SKILL.md)가 근거와 함께 함 |
| 계획 | [Issue 안의 계획](plan.md#issue-안의-계획)의 단계 표. 처음에 미작성이라면 준비 상태 명시 |
| 참고 링크 | 필수 절. 실제 확인한 링크 또는 `확인된 참고 링크 없음` |
| 사용자 요청 원문 | 해당 작업의 실제 요청을 그대로 인용. 독립된 `## 사용자 요청 원문`을 본문 맨 아래에 두고 인용을 `<details>`로 접음 |

기능은 [기능 템플릿](../../workflow-init/assets/.github/ISSUE_TEMPLATE/FEATURE_REQUEST.md), 버그는 [버그 템플릿](../../workflow-init/assets/.github/ISSUE_TEMPLATE/BUG_REPORT.md)을 따른다. 대상의 같은 뜻 절 이름을 유지하고 빠진 필수 정보만 보완한다. 버그의 실제 동작·기대 동작이 As-Is / To-Be를 담당하므로 같은 표를 추가하지 않는다.

선택 절은 내용이 있을 때만 둔다. `제약 사항`은 수행하면서 지킬 원칙과 조건이며 계획 바로 앞에 둔다. 같은 제약을 제외 범위나 원문 밖의 다른 절에 반복하지 않는다. `남은 결정`은 인간이 정해야 할 사항이며 계획 바로 뒤에 둔다. `결정 기록`은 정해진 결정과 바뀐 사실이며 남은 결정 바로 뒤에 둔다. `지금 알고 있는 것`은 조사 사실과 근거이며 결정 기록 뒤, 참고 링크 앞에 둔다. 항목마다 확인 날짜와 출처를 붙인다.

## 한눈에와 갱신 시점

「한눈에」는 다른 세션이나 사람이 본문만 읽고 지금 단계, 다음 행동, 막힌 것을 알게 하는 절이다.

```markdown
## 한눈에

- 지금 단계: 2. <할 일> (진행)
- 다음 행동: <수행 주체>가 <다음에 하는 일>
- 막힌 것: 없음 | D1 결정 대기 | <외부 의존>
```

상태의 정본은 계획 단계 표의 상태 열이다. 「한눈에」는 그 단계 번호와 할 일을 가리키고 따로 상태를 만들지 않는다.

계획 작성·보완은 [계획 작성·보완](../SKILL.md#계획-작성보완)을, AC 추가와 새 배포 뒤 확인 항목 추가는 [Issue 안의 계획](plan.md#issue-안의-계획)을 따르고 「결정 기록」에 한 줄 남긴다. 그 밖의 진행 중에는 본문을 다음 때만 고친다.

1. 단계 상태가 바뀔 때: 상태 열과 「한눈에」를 함께 고친다.
2. 확인한 사실이 바뀔 때: 해당 문장을 고치고 「결정 기록」에 한 줄 남긴다.
3. 결정이 정해질 때: 「남은 결정」에서 지우고 「결정 기록」에 결정 ID·질문·답을 한 줄로 남긴다. 원문의 짧은 답(「D1: 그래」)이 무엇에 대한 답인지 결정 기록으로 알 수 있어야 한다. 그 결정을 기다리던 단계의 보류를 푼다.

진행 메모·중간 결과·로그는 본문에 쓰지 않는다. 댓글이나 PR에 쓴다.

## 결정 기록

```markdown
## 결정 기록

- 2026-10-13 D1 <질문>: <답>(<결정한 사람>)
- 2026-10-13 <바뀐 사실 한 줄>(<근거>)
```

날짜순으로 한 줄씩 더한다. 이미 쓴 줄은 고치지 않는다. 사용자 요청 원문은 결정이 바뀌어도 고치지 않는다.

작업을 이어 받으면 「지금 알고 있는 것」의 날짜와 출처를 현재 코드·문서와 다시 대조한다. 낡은 항목은 고치고 「결정 기록」에 한 줄 남긴다.

## 사용자 요청과 사실

최초 원문을 요약·교정하거나 후속 결정으로 덮어쓰지 않는다. 원문 절은 본문 맨 아래에 두고 인용 전체를 `<details>`로 접는다. 접어도 절 제목과 인용 전체가 남으므로 필수 절 요건을 만족한다. 접은 인용을 요약·발췌로 바꾸지 않는다. 해당 작업과 관계없는 대화는 복사하지 않는다. 후속 범위 변경은 원문과 구분해 인용하고 현재 합의와 연결한다. 원문이 없으면 미확인으로 표시하고 AI 요약을 원문으로 만들지 않는다.

사용자 발화가 직전 AI 답변에 반응했으면(승인, 반문, 짧은 답), 그 인용 바로 앞에 `AI 답변 요약:` 줄을 한두 문장으로 둔다. 무엇을 승인했는지, 무엇을 물었는지 알 수 있게 한다. 이 줄은 `>` 인용으로 쓰지 않는다. AI 답변 전문을 복사하지 않는다. AI 답변과 관계없는 최초 요청에는 이 줄을 두지 않는다. D번호 결정의 답은 「결정 기록」이 대상을 밝히므로 요약 줄을 반복하지 않아도 된다.

```markdown
> 이슈 스킬 확인해줘.

AI 답변 요약: 원문 절에 AI 답변을 둘 자리가 없다. `AI 답변 요약:` 줄을 두는 수정을 제안했다.

> 좋아. 이슈 만들어줘.
```

사용자의 증상 표현은 사용자 보고다. 직접 재현·원인 확인·승인으로 해석하지 않는다. 조사로 사실을 확인해도 그 해결 방법이 사용자 의도라고 확정하지 않는다. AI가 제안한 해결·범위·AC는 제안으로 표시한다. 실제 승인된 대상과 범위만 사용자 결정으로 기록한다.

## 재현 절차를 사용자에게 묻는 방법

코드·로그로 알 수 있는 사실부터 조사한다. 재현 정보가 부족하면 화면/API·관찰한 절차·기대/실제 결과·확인한 환경 중 실제 필요한 것만 질문한다. 없는 절차·버전·원인·수치를 만들지 않는다. 핵심 의도가 모호하면 질문 전에는 범위·AC를 임의 확정하지 않는다.

## 본문 작성·편집 순서

1. 사용자 원문과 확인한 근거로 목표·동작 차이·범위를 구별한다. 원문과 AI 해석을 섞지 않는다.
2. 합의한 AC를 한 결과씩 쓴다. 구현 방법·명령·이력은 AC에서 분리한다. 사용자 승인이 없는 새 AC는 제안으로 둔다.
3. 현재 단계에서 필요한 계획만 쓴다. 상세 설계도 Issue 본문에 두고 독립 결과의 추적이 필요하면 [분리 판단](plan.md#sub-issue-분리-판단)을 적용한다. 신규 plan/task/handoff/review 작업 기록을 만들지 않는다.
4. 각 사실은 코드·문서·실행 근거와, 각 사용자 결정은 승인 범위와 대조한다. 근거가 없으면 제안·미확인으로 고치거나 제거한다. 사실 확인을 사용자 합의 확인으로 대신하지 않는다.
5. 같은 내용을 원문·목표·To-Be·AC·계획에서 반복하지 않는다. 독립 판단은 문장을 나누고, 중요한 조건·위험·이유를 짧게 만들기 위해 삭제하지 않는다.
6. 필수 참고 링크를 확인하고 초안을 원문 의미와 대조해 제시한다. 내용 없는 선택 절은 삭제한다.

## 이슈를 만드는 절차

1. 변경 크기와 관계없이 열린/닫힌 기존 Issue의 의도·범위·AC를 대조한다. 열린 동일 범위는 재사용하고 닫힌 Issue와 다른 후속 범위는 배경 링크를 가진 새 Issue로 만든다.
2. 초안을 작성·대조하고 대화에 제시한다. 기존 생성 승인이 있으면 재승인 없이 그 범위를 실행한다.
3. 실제 라벨 목록과 [마일스톤 기준·목표 버전](../../git-workflow/references/milestones.md)을 확인하고 본문 파일로 생성한다. 목표가 정해지고 대상이 확인됐으면 `--milestone '<실제 이름>'`을 추가한다. 버전 미정이면 생략하고 이유를 보고한다.

```bash
gh issue create --repo owner/repo --title '[Issue] 검색 조건 개선' \
  --label enhancement --assignee @me --body-file /tmp/issue-body.md
```

예시 이름·라벨·계정은 실제 저장소 기준으로 확인한다. 인증 계정은 AGENTS.md를 따른다. 응답 불명은 재조회로 중복을 방지한다. 실제 URL·본문·라벨·assignee login·마일스톤 연결을 재확인한다. assignee나 마일스톤 연결 실패 시 이미 생성된 Issue를 삭제/중복 생성하지 않고 승인 범위에서 해당 연결만 재시도한다. 기존 assignee를 제거하지 않는다.

## 하위 이슈로 나누는 기준

기본은 하나의 Issue 본문 계획이다. [Sub-issue 분리 판단](../../issue-create/references/plan.md#sub-issue-분리-판단)에 따라 독립 완료·검증과 별도 추적 필요를 모두 확인한다. 복잡함·담당자 수·기존 task 수만으로 나누지 않는다. 실제 생성·연결·의존성·재조회는 [공통 절차](../../issue-create/references/sub-issues.md)를 따른다. 계획 작성만으로 구현 준비나 구현 완료를 주장하지 않는다.

예시: [짧고 모호한 요청과 단순 작업](../../../docs/examples/issue-centered-records/README.md).

# 종료 코멘트 양식

Issue를 닫거나 이미 닫힌 Issue에 결과를 보완할 때 읽는다. 코멘트는 결과 요약과 근거 링크만 포함한다. Issue 코멘트는 알림 채널로 그대로 나가므로, 「종료 결과」·「종료 사유」 첫 문단은 작업을 모르는 팀원이 읽을 수 있게 AC·D·단계 번호 없이 쓴다. plan·todo·handoff 전문은 복사하지 않는다. 링크 규칙은 [document-links](../../git-workflow/references/document-links.md)를 따른다.

## completed

completed 코멘트는 두 층이다. 접히지 않은 첫 부분은 사람이 읽는 요약이고, 접힌 블록은 AI 가 읽는 결과 경계와 상세 근거다.

```markdown
**회신 유형: 수정 결과 · 작성 AI: Codex**

## 종료 결과

<무엇이 바뀌었고 무엇이 남았는지 1~3문장. AC·D·TC·단계 번호와 케이스 기호 없이>

- 해결 PR: <PR URL>
- 배포 상태: <배포 완료 / 배포 대기와 이유 / 배포 없음과 이유>
- 후속 작업: <후속 Issue URL과 한 줄 설명. 없으면 없음>

<details>
<summary>결과 경계(AI 용)</summary>

## 결과 경계

| 케이스 | 판정 | 근거 | 비고 |
| --- | --- | --- | --- |
| A <직접 한 일의 짧은 이름> | 충족 | <PR·commit·확인 결과 링크> | |
| A' <A 의 변형> | <충족 / 미충족 / 미확인> | <링크 또는 확인하지 않은 이유> | |
| B <A 로 파생된 동작> | <충족 / 미충족 / 미확인> | <링크 또는 이유> | <후속 Issue URL 또는 제외 범위. 없으면 비움> |
| B1 <B 의 하위 경우> | <충족 / 미충족 / 미확인> | <링크 또는 이유> | |

- merge commit: <hash>

## 달성 조건 결과

| AC | 결과 | 근거 |
| --- | --- | --- |
| AC-01 | 충족 | <PR·검토 결과 또는 필요한 기존 문서의 확인된 근거> |

## 배포 뒤 확인 결과

| 항목 | 결과 | 근거 | 확인 시각 |
| --- | --- | --- | --- |
| <Issue 전달의 배포 뒤 확인 항목. 항목이 없으면 이 절 삭제> | 충족 | <조회 결과·링크> | <확인한 시각> |

## 작업 정리

| 대상 | 결과 | 근거 또는 이유 | 다음 행동 |
| --- | --- | --- | --- |
| <정확한 작업 워크트리 또는 원격 head 식별값> | <워크트리: 삭제 / 이미 없음 / 보류 / 실패 / 미확인 / 해당 없음. 원격 head: 이미 없음 / 남음 / 미확인> | <전후 조회의 확인 결과 또는 승인·보존·도구 제약/오류> | <남은 확인·보존·승인·인계. 없으면 없음> |

</details>
```

첫 부분만 읽어도 무엇이 어떻게 끝났는지 알 수 있게 쓴다. 미충족·미확인으로 남은 동작이 있으면 첫 부분에도 한 문장으로 쓴다.

### 결과 경계 표

결과 경계 표는 이번 작업으로 무엇이 되고 무엇이 안 되는지를 후속 AI 가 오해하지 않게 하는 표다.

- A 는 Issue 가 요청해 직접 바꾼 동작이다. A' 는 A 와 같은 동작의 변형(다른 입력·경로·화면·환경·경계값)이다.
- B, C 는 A 를 바꿔서 함께 영향받는 다른 동작이다. B1, B1' 는 B 의 하위 경우와 그 변형이다.
- 케이스는 AC, 확인 사례(TC), 영향 범위의 관련 동작·연관 영향·제외, PR 의 검증 결과·미검증, 리뷰가 찾은 영향에서 고른다. 사람이 「A 를 했으면 이것도 되겠지」라고 생각할 만한 변형과 파생을 빠뜨리지 않는다.
- 행마다 기호 뒤에 짧은 이름을 붙인다. 같은 이름을 「코멘트 기록」의 종료 줄에도 쓴다.
- 판정은 셋 중 하나다. 충족은 근거 링크가 있을 때만 쓴다. 미충족은 확인했고 되지 않거나 제외 범위라서 하지 않은 것이다. 미확인은 확인하지 않았거나 근거가 부족한 것이다. 미확인을 충족으로 쓰지 않는다.
- 미충족·미확인 행의 비고에 후속 Issue 또는 제외 범위를 쓴다. AC 에 대응하는 케이스가 미충족·미확인이면 issue-close 의 completed 차단 조건을 적용한다.

### 코멘트 기록의 종료 줄

게시 뒤 [Issue 코멘트 기록](../../git-workflow/references/document-links.md#issue-코멘트-기록)대로 본문 「코멘트 기록」 끝에 종료 줄을 더한다. 이 줄이 마지막 줄이다. 요약 칸은 결과 경계 표의 행을 `<기호> <짧은 이름> <판정>`으로 `/`로 이어 쓴다.

```markdown
- 2026-11-21 · 종료(completed) · A 기간 필터 충족 / A' 모바일 기간 필터 충족 / B 상태 필터 미충족(후속 [Issue 52](https://github.com/owner/repo/issues/52)) / C 엑셀 내보내기 미확인 · [코멘트](https://github.com/owner/repo/issues/48#issuecomment-2)
```

AC 표에는 Issue 본문의 모든 AC ID를 쓴다. 결과는 충족만 허용한다. PR의 「충족(배포 뒤 확인 대기)」는 배포 뒤 확인 결과가 모두 충족일 때만 충족으로 쓴다.

배포 뒤 확인 결과 절은 Issue 「전달」에 배포 뒤 확인 항목이 있을 때만 쓴다. 없으면 절을 만들지 않는다. 항목마다 한 행을 쓰고 결과는 충족만 허용한다.

정리 표는 이미 CLOSED인 Issue의 completed 결과 보완에서도 필수다. 각 대상의 결과를 별도 행으로 쓴다. 원격 head는 PR마다 저장소·head 이름·OID로 행을 작성한다. 머신 절대 경로 대신 원격 기록에서 대상이 구별되는 저장소·작업 branch·HEAD·worktree 식별값과 접근 가능한 PR·검토 기록 또는 기존 handoff 근거 링크를 사용한다. 같은 정확한 대상의 기존 승인이나 실행 전 부재 조회로 삭제 질문이 필요 없었으면 그 근거를 「근거 또는 이유」 칸에 쓴다.

## not planned

```markdown
**회신 유형: 반려·보류 사유 · 작성 AI: Codex**

## 종료 사유

<진행하지 않기로 한 이유>

- 결정: <결정한 역할과 결정 위치(대화·회의록·댓글 링크)>
- 대안: <대신 진행하는 Issue·방법. 없으면 없음>
- 다시 열 조건: <상황이 바뀌면 다시 검토할 조건. 없으면 없음>
```

## duplicate

```markdown
**회신 유형: 반려·보류 사유 · 작성 AI: Codex**

## 종료 사유

#<정본 Issue>와 해결 범위가 같아 그 Issue에서 진행한다.

- 옮긴 정보: <이 Issue에만 있던 재현 정보·요구사항. 정본 Issue에 복사한 댓글 링크. 없으면 없음>
```

`--duplicate-of`가 타임라인에 중복 관계를 기록한다. 이 Issue에만 있던 정보는 닫기 전에 정본 Issue에 댓글로 복사한다.

not planned·duplicate 코멘트도 게시 뒤 종료 줄을 더한다. 요약 칸에는 종료 사유를 한 줄로 쓴다(`- 2026-11-21 · 종료(not planned) · 데이터 계약 변경으로 진행하지 않음 · [코멘트](https://github.com/<owner>/<repo>/issues/<번호>#issuecomment-<ID>)`).

예시의 Codex와 회신 유형은 실제 작성 도구·본문의 주된 목적에 맞게 바꾼다.

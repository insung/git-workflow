# PR 코멘트 확인과 처리

[공통 실행 경계](../git-workflow/references/execution-boundaries.md)를 적용한다.
현재 요청뿐 아니라 같은 작업에서 이미 승인된 대상·구현·회신 범위를 확인한다. 짧은 “코멘트 확인해줘”를 매번 읽기 전용으로 초기화하지 않는다. 이미 코멘트 처리와 회신을 맡긴 작업이면 그 흐름을 이어간다. 사용자가 “내용만 확인”, “수정·게시하지 마”라고 제한하면 그 제한을 우선한다. 처리·회신 권한이 없는 단순 확인 요청을 자동 구현·게시로 확대하지 않는다.

## 실행

1. 실제 PR·연결 Issue·최신 HEAD를 확인하고 [공통 코멘트 확인](../git-workflow/references/pr-comment-check.md)을 실행한다. 전체 기존 답글과 합의를 함께 읽는다. 조회 미완료·HEAD 변경은 미확인이며 코멘트 없음이나 pass로 보고하지 않는다.
2. 먼저 리뷰의 제출 상태를 확인한다. `PENDING` 코멘트·리뷰 본문은 사용자에게 초안 내용·대상·제출 대기를 보고만 한다. 기존 구현·회신 승인이 있어도 그 초안을 근거로 수정·반려 처리·답글 게시·resolve·자동 Submit하지 않는다. 제출 상태 미확인은 처리하지 않고 재조회를 안내한다. Submit된 리뷰의 코멘트와 이미 게시된 PR·Issue 일반 댓글만 처리 대상으로 삼는다. 제출은 처리 대상이 된다는 뜻이며 실행 권한을 새로 부여하지 않는다.
3. 처리 대상 코멘트의 요청을 수용·부분 수용·반려·판단 보류로 구별한다. 수용할 요청은 기존 승인 범위에서 [수정 구현](../task-implement/SKILL.md)으로 구현·검증한다. 반려는 현재 코드·완료 조건·합의에 근거한 이유를 설명한다. AI의 반려 판단을 당사자가 합의한 철회·범위 밖·해결 완료로 바꾸지 않는다. 필요한 인간 결정과 미처리 부분을 남긴다.
4. 처리와 회신이 요청됐으면 [공통 수정 결과 회신](../git-workflow/references/pr-comment-reply.md)을 적용한다. 반영·부분 반영·반려·보류 결과를 원래 스레드에 돌려주고 실제 커밋·고정 파일 링크·검증·남은 사항·작성 AI를 기록한다. 기존 답글을 대조해 중복을 피하고 게시 후 실제 URL·저장 본문·작성자·PR·부모를 재조회한다. 단순 확인 요청이면 게시하지 않는다.
5. 사용자에게 **적용한 결과**를 보고한다. 코멘트별 판단과 이유, 실제 변경·커밋·검증 결과, 실제 답글 URL과 게시 확인/생략/미확인, 남은 판단과 다음 행동을 반환한다. 승인된 구현·회신 단계가 남았는데 조회 결과만 반환하며 작업을 끝내지 않는다. 조회·게시 실패나 권한 부족으로 중단한 단계는 구체적 이유와 재개 조건을 보고한다.

전체 검토가 필요하면 [pr-review](../pr-review/SKILL.md), 승인된 머지는 [pr-merge](../pr-merge/SKILL.md)로 인계한다. 처리·회신 승인은 스레드 resolve·머지 승인이 아니다. 반려 답글 게시도 resolve나 합의 완료를 뜻하지 않는다.

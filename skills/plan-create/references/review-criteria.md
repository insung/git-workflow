# 검토 기준·검증 입력 양식과 작성 규칙

구현 전에 pr-review의 판정 기준(`review-criteria.md`)과 다시 실행할 고정 입력(`review-input-<topic>.md`)을 만든다. 파일 이름은 [디렉토리 규칙](plan.md#디렉토리-규칙)을 따른다.

## 보관 위치

1. plan-create 세션이 plan·task 파일 커밋 뒤, 구현 시작 전에 작성한다. 구현 세션은 작성하지 않는다.
2. plan 커밋에서 `review/issue-{n}` 브랜치를 만든다. 로컬 파일럿이면 `review/draft-{title}`을 쓴다.
3. 두 종류 파일을 plan의 작업 디렉토리 경로(`docs/git-workflows/...`)로 그 브랜치에만 커밋한다. 작성은 별도 worktree(`git worktree add <경로> -b review/issue-{n} <plan 커밋>`)에서 한다.
4. 작업 브랜치에는 커밋하지 않고, 작업 브랜치의 작업본에 미추적 파일로도 두지 않는다.
5. 구현 세션은 `review/issue-{n}` 브랜치와 그 worktree를 읽지 않는다.
6. pr-review는 `git show review/issue-{n}:<경로>`나 그 브랜치의 worktree에서 읽는다.
7. 기준을 바꿀 때는 구현 세션이 아닌 세션이 같은 브랜치에 커밋하고 이유를 커밋 본문에 쓴다.
8. 작업 브랜치로의 반입 시점과 범위는 [pr-review의 기록 커밋](../../pr-review/SKILL.md#7-기록-커밋)을 따른다.

## review-criteria.md 템플릿

```markdown
# Issue #<n> 검토 기준

구현 전에 고정한 pr-review 입력이다. 구현 세션은 이 파일과 검증 입력을 읽지 않는다.

## 사용 방법

1. handoff.md와 각 task 파일의 처리 내용·결과를 읽는다.
2. 아래 AC별 기준으로 판정한다. 기계 확인은 직접 다시 실행한다.
3. <TC-nn>은 [review-input-<topic>.md](review-input-<topic>.md)의 고정 입력으로 다시 실행한다. 구현 세션이 만든 입력과 결과는 참고로만 본다.
4. 우회 확인과 공통 확인을 거친 뒤 review.md에 기록한다.

## AC별 기준

| AC | 기계 확인 (작업 디렉토리) | 판단 질문 | 실패로 보는 예 |
| --- | --- | --- | --- |
| AC-01 | <명령과 기대 출력> | <명령으로 확인할 수 없는 의도 질문> | <기계 확인을 통과해도 실패인 구현> |

## 우회 확인

| 확인 | 방법 |
| --- | --- |
| 완료 표시에 근거가 있는가 | task 파일의 `[x]` 행마다 처리 내용의 커밋을 `git show`로 확인 |
| 검증 결과가 실행 근거와 맞는가 | 결과 칸의 실행 커밋과 handoff의 명령·출력이 같은 HEAD인지 확인 |
| 구현 세션의 입력만으로 통과를 주장하는가 | 구현 세션 입력의 결과와 고정 입력 재실행 결과 비교 |

## 공통 확인

| 확인 | 기준 |
| --- | --- |
| 정본 | 같은 규칙이 한 파일에만 있고 다른 곳은 링크 |
| 커밋 | 단계·주제별 분리, 승인 밖 push·PR·Issue 댓글 없음 |
| 기록 | task 처리 내용·결과 칸 작성, 미실행은 미실행, 계획 이탈은 plan 결정과 변경 기록에 존재 |
```

## review-input-<topic>.md 템플릿

```markdown
# <TC-nn> 고정 입력: <주제>

<이 입력이 확인하는 동작 한 문장>. <실행 방법: 판정 주체가 직접 실행할 명령, 또는 실행자에게 줄 스킬과 요청문>.

## 입력

<가상 Issue·plan 단계 표·task·diff·handoff, 요청문 목록, 또는 명령과 입력 값>

## 기대 지적

| ID | 지적 | 근거 | 기대 판정 |
| --- | --- | --- | --- |
| F1 | <찾아야 하는 결함 또는 기대 출력과 다른 결과> | <입력 안의 위치> | <fail / warn / human-review> |

지적하지 않아야 하는 것: <정상 동작>

## 통과 기준

| 기준 | 조건 |
| --- | --- |
| 필수 | <실행 횟수> 모두 <ID> 지적 |
| 필수 | 변경 전 결과(RED)가 함께 기록됨 |
| 참고 | <판정에 쓰지 않는 관찰> |
```

## 작성 규칙

| 항목 | 규칙 |
| --- | --- |
| 작성 근거 | Issue의 AC ID와 task 파일의 검증 사례만 쓴다. 구현 결과를 보고 쓰지 않는다. |
| AC별 기준 | Issue의 AC ID마다 한 행을 쓴다. 기계 확인은 다시 실행할 명령과 기대 출력, 판단 질문은 명령으로 확인할 수 없는 의도, 실패 예는 기계 확인을 통과해도 실패로 볼 구현이다. 해당 없는 칸은 `-`. |
| 검증 입력 | 다시 실행할 사례(하위 에이전트 시나리오, 요청문 판정, 명령의 입력 값)마다 파일 하나를 만든다. `<topic>`은 짧은 영어 kebab-case다. 구현 세션의 테스트 입력과 다른 경계 값을 포함한다. |
| 기대 지적 | 명령 사례면 입력별 기대 출력을 쓴다. 지적하지 않아야 하는 정상 동작도 쓴다. 실행자에게 주는 범위는 [검증 실행 주체](../../git-workflow/references/execution-boundaries.md#검증-실행-주체)를 따른다. |
| 통과 기준 | 실행 횟수(시나리오는 기본 3회)와 필수·참고 조건을 쓴다. 실행 주체는 [검증 실행 주체](../../git-workflow/references/execution-boundaries.md#검증-실행-주체)를 따른다. |

# todo 양식

plan의 단계마다 `task-{nn}-{step-title}.md` 하나를 만든다. 파일 이름 규칙은 [디렉토리 규칙](plan.md#디렉토리-규칙)을 따른다. 맥락·결정은 plan에 두고, todo에는 이 단계의 변경 대상·작업·검증만 둔다. 작업 진행과 `완료`·`처리 내용`·`결과` 칸 기록은 [task-implement](../../task-implement/SKILL.md)를 따른다.

## todo 템플릿

```markdown
# <nn> <단계 제목>

계획: [plan의 단계 표](plan.md#단계)

## 변경 대상

| 구분 | 경로 | 이유 |
| --- | --- | --- |
| Create / Modify / Delete / Test | <경로> | <역할 또는 바꿀 동작> |

## 작업

| # | 작업 | 완료 | 처리 내용 |
| --- | --- | --- | --- |
| 1 | <관찰 가능한 결과를 만드는 작업> | [ ] | |

## 검증

| 사례 | AC | 명령·작업 디렉토리 | 기대 결과 | 결과 |
| --- | --- | --- | --- | --- |
| <a id="tc-01"></a>TC-01 | AC-01 | <명령>, <리포 상대 경로> | <기대 값·동작> | 미실행 |

## 제외 범위

- <이 단계에서 바꾸지 않는 것>
```

## 작성 규칙

| 절 | 작성 규칙 |
| --- | --- |
| 변경 대상 | 확인한 경로만 쓴다. 미확인 경로는 조사 작업의 결과로 채운다. |
| 작업 | 커밋하거나 검증할 수 있는 단위로 3~7개를 쓴다. 파일·함수 수준의 하위 task로 나누지 않는다. |
| 검증 | `AC` 열에는 Issue 달성 조건의 ID(`AC-01`)를 쓴다. 사례 ID에 `<a id="tc-nn"></a>` 앵커를 둔다. plan의 단계 표는 `task-01-<step-title>.md#tc-01` 주소로 링크한다. |
| 제외 범위 | 다른 단계가 맡는 변경과 이번에 하지 않는 변경을 쓴다. |

## 예제

```markdown
# 01 오류 분류

계획: [plan의 단계 표](plan.md#단계)

## 변경 대상

| 구분 | 경로 | 이유 |
| --- | --- | --- |
| Modify | `src/retry.ts` | 오류 종류별 재시도 여부 반환 |
| Test | `tests/retry.test.ts` | 분류 사례 assertion |

## 작업

| # | 작업 | 완료 | 처리 내용 |
| --- | --- | --- | --- |
| 1 | network·expired·unknown 오류 분류 함수 구현 | [x] | `classifyRetry` 추가, unknown은 기존 안내 반환 (a1b2c3d) |
| 2 | 사례별 유닛 테스트 작성 | [ ] | |

## 검증

| 사례 | AC | 명령·작업 디렉토리 | 기대 결과 | 결과 |
| --- | --- | --- | --- | --- |
| <a id="tc-01"></a>TC-01 | AC-01 | `npm test -- tests/retry.test.ts`, 리포 루트 | network 입력에서 true | 미실행 |
| <a id="tc-02"></a>TC-02 | AC-01 | 같은 명령 | expired 입력에서 false | 미실행 |

## 제외 범위

- 결제 요청 자동 재전송
- 안내 화면 문구 변경 (02 단계)
```

## 작업·검증의 정보 단위

[공통 작성·편집 기준](../../git-workflow/references/writing-conventions.md#정보-단위와-작성-후-편집)을 적용한다. 작업 한 행은 하나의 완료 결과, 검증 한 행은 하나의 관찰 동작과 기대/실제 결과를 담는다. 독립적으로 실패할 수 있는 결과는 나눈다. 처리 내용은 실제 변경과 커밋·계획 이탈만 요약하고 목적·결정 이유는 plan의 공통 맥락으로 연결한다. 미실행·실패·지난 커밋의 통과를 합쳐 현재 통과로 적지 않는다.

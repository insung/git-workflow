# plan.md 양식과 작성 규칙

## 디렉토리 규칙

1. 작업 디렉토리는 대상 리포의 `docs/git-workflows/{yyyy-MM}/{dd}_{issue-number}_{title}/`이다.
2. `{yyyy-MM}`·`{dd}`는 프로젝트 시간대의 작업 시작일이다. 작업 중에 바꾸지 않는다.
3. `{issue-number}`는 실제로 조회하거나 생성한 Issue 번호다. 생성 전 번호를 예측하지 않는다.
4. `{title}`은 작업 주제의 짧은 영어 kebab-case다.
5. 디렉토리에는 다음 파일을 둔다.

| 파일 | 작성 단계 | 내용 |
| --- | --- | --- |
| `plan.md` | plan-create | 요청·범위·단계·검증·전달 |
| `task-{nn}-{step-title}.md` | plan-create | 단계별 변경 대상·작업·검증 |
| `review-criteria.md` | plan-create | 검토 기준 |
| `review-input-<topic>.md` | plan-create | 검증 입력 |
| `handoff.md` | 구현 후 | 실제 구현·테스트 결과 |
| `review.md` | pr-review | 검토 결과 |

`{nn}`은 plan 단계 번호(01, 02, …), `{step-title}`은 그 단계 핵심 제목의 영어 kebab-case다. 단계가 하나여도 `task-01-{step-title}.md`를 쓴다.

```text
docs/git-workflows/2026-10/02_123_retry-guidance/
├── plan.md
├── task-01-retry-classification.md
├── task-02-retry-message.md
├── handoff.md
└── review.md
```

## 로컬 파일럿 디렉토리 규칙

원격 Issue를 만들거나 조회할 수 없을 때만 적용한다.

1. 디렉토리를 `{dd}_draft_{title}`로 만들고 프론트메터에 `issue: null`을 쓴다.
2. 원격 접근이 되면 issue-create로 같은 요청의 Issue를 조회하고, 없으면 승인 범위에서 생성한다.
3. 실제 번호를 확인한 뒤 디렉토리를 `{dd}_{issue-number}_{title}`로 한 번 옮기고 `issue`와 문서 링크를 갱신한다.
4. 실제 번호를 확인하기 전에는 draft 상태를 유지한다. 원격 PR 전에는 실제 Issue가 필요하다.

## plan.md 템플릿

```markdown
---
issue: "#<Issue 번호>"
status: draft
branch: "<작업 브랜치>"
base: "<PR 대상 브랜치>"
created: "<YYYY-MM-DD>"
---

# <변경 이름> 계획

## 요청

> <최초 요청 원문>

- 해석: <요청을 어떻게 이해했는지>
- 남은 결정: <없으면 없음. 있으면 결정과 변경 기록의 해당 행>

## 현재 동작과 변경 이유

| 현재 동작 | 근거 위치 | 바꿀 결과 |
| --- | --- | --- |
| <관찰한 동작> | <파일:줄 또는 문서> | <기대 동작> |

## 범위

| 구분 | 내용 |
| --- | --- |
| 포함 | <기능·파일 경계> |
| 제외 | <이번에 하지 않는 것> |
| 미변경 소비자 | <영향을 확인할 호출자·사용자> |
| 호환성·데이터·운영 | <영향 또는 없음> |

## 단계

| 단계 | 제목 | 설명 | 검증 사례 | 완료 |
| --- | --- | --- | --- | --- |
| [01](task-01-<step-title>.md) | <작업 핵심 제목> | <작업 핵심 요약> | [TC-01](task-01-<step-title>.md#tc-01)<br>[TC-02](task-01-<step-title>.md#tc-02) | [ ] |

실행 순서: 01 → 02. 검증이 실패하면 해당 단계로 돌아가 같은 사례를 다시 실행한다.

## 최종 검증

| 사례 | AC | 명령·작업 디렉토리 | 기대 결과 | 필요 승인 | 결과 |
| --- | --- | --- | --- | --- | --- |
| <a id="tc-f01"></a>TC-F01 | <AC> | <전체 테스트·통합 명령>, <리포 상대 경로> | <기대 결과> | <없음 또는 필요 승인> | 미실행 |

## 전달과 롤백

| 항목 | 내용 |
| --- | --- |
| 전달 방법 | <배포 대상·트리거·순서, 배포가 없으면 이유와 전달 방법> |
| 필요 승인 | <커밋·push·PR·머지·배포 중 필요한 것> |
| 적용 후 확인 | <성공 판단 기준> |
| 롤백 | <되돌릴 지점과 방법, 미확인이면 미확인> |

## 결정과 변경 기록

| 날짜 | 구분 | 내용 | 영향 AC·단계 | 상태 |
| --- | --- | --- | --- | --- |
| <YYYY-MM-DD> | 결정 / 요청 변경 / 계획 이탈 | <내용> | <AC·단계> | 승인 / 보류 |
```

## 프론트메터 규칙

| 필드 | 값 | 작성 규칙 |
| --- | --- | --- |
| `issue` | `"#123"`, `"owner/repository#123"`, 전체 Issue URL, `null` | 실제로 조회한 값을 쓴다. YAML에서 `#`는 주석이므로 따옴표로 감싼다. `null`은 로컬 파일럿에만 쓴다. |
| `status` | 아래 상태 값 | 단계 진행에 맞춰 바꾼다. |
| `branch` | 작업 브랜치 이름 | 작업 브랜치가 정해지면 쓴다. |
| `base` | PR 대상 브랜치 이름 | [branch-strategy](../../branch-strategy/SKILL.md)로 확인한 값을 쓴다. |
| `created` | `YYYY-MM-DD` | 작성 시작일을 쓰고 바꾸지 않는다. |

기준 커밋은 작업 중 계속 바뀌므로 프론트메터에 두지 않는다. 검토 기준 커밋과 HEAD는 handoff와 review에 기록한다.

`status`의 허용 값은 아래 표가 정본이다. 다른 문서는 이 표를 링크한다.

| 값 | 의미 |
| --- | --- |
| draft | 요청·범위·달성 조건 또는 단계 작성 중 |
| ready | 구현할 단계의 입력·검증·전달 계획 준비 완료 |
| in-progress | 구현·검증·전달 진행 중 |
| review-pending | 구현 인계 후 리뷰 또는 리뷰가 요구한 보완 대기 |
| completed | 모든 단계·검증·전달 완료. 미실행 필수 항목이 있으면 사용 금지 |

보류는 별도 값 없이 결정과 변경 기록에 `보류`로 남긴다. `status`는 사용자 승인이나 실제 머지·배포 상태를 대신하지 않는다.

## 절별 작성 규칙

| 절 | 작성 규칙 |
| --- | --- |
| 요청 | 최초 요청 원문만 인용한다. 이후 요청이 바뀌면 원문을 고치지 않고 결정과 변경 기록에 `요청 변경` 행을 추가한다. 현재 범위의 정본은 Issue다. |
| 현재 동작과 변경 이유 | 코드·문서에서 확인한 근거 위치를 쓴다. 확인하지 못한 동작은 미확인으로 쓴다. |
| 범위 | Issue의 영향 범위를 단계 기준으로 구체화한다. |
| 달성 조건(plan에 없음) | plan에 다시 쓰지 않는다. 달성 조건과 AC ID는 Issue 본문에만 두고, todo 검증 표와 최종 검증 표가 그 ID를 참조한다. Issue의 AC ID가 어느 검증에도 없으면 계획이 빠진 것이다. |
| 단계 | 독립적으로 검증할 수 있는 단위로 나눈다. 검증 사례는 todo의 사례 앵커로 링크한다. 구현 방식에 영향을 주는 미결정이 있으면 그 단계만 보류한다. 완료는 해당 todo의 작업과 검증이 실제로 끝났을 때 체크한다. |
| 최종 검증 | 단계를 넘는 통합·전체 검사만 쓴다. AC 열은 Issue 달성 조건의 ID를 쓴다. 단계별 사례와 변경 대상은 todo에 둔다. 유닛 테스트 대상이 없으면 이유와 대체 검사를 쓴다. |
| 전달과 롤백 | 필수다. 배포가 없으면 이유와 전달 방법을 쓴다. |
| 결정과 변경 기록 | 행을 추가만 하고 이전 행을 고치지 않는다. |

맥락·판단은 plan, 변경 대상·작업·단계별 검증은 todo, 상세 실행 근거는 handoff에 둔다.

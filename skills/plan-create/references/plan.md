# 계획 작성 계약과 예제

## 경로와 준비 조건

대상 리포 `docs/git-workflows/{yyyy-MM}/{dd}_{issue-number}_{title}/plan.md`에 쓴다. 날짜는 프로젝트 시간대를 따르고 시작 날짜를 유지한다. title은 짧은 kebab-case 주제다. 실제 Issue URL/번호를 조회·생성한 뒤 경로를 확정한다. 생성 전에는 미래 번호를 알 수 없으므로 순번을 예측하지 않는다.

원격 불가 로컬 파일럿은 `{dd}_draft_{title}` 임시 경로와 `issue: null`을 사용한다. 충돌 시 같은 작업이면 재개하고 다른 작업이면 title을 구분한다. 원격 접근이 회복되면 Issue 초안과 같은 요청의 기존 Issue를 열린 상태와 닫힌 상태 모두에서 먼저 조회한다. 실제 Issue가 있으면 재사용하고 없으면 승인된 생성 범위에서 issue-create로 만든 뒤 응답·재조회로 실제 번호를 확인한다. 승인·접근이 없으면 임시 상태를 유지하며 번호를 예측하지 않는다. 번호 확인 후 자신이 만든 임시 디렉토리를 확정 경로로 한 번 옮기고 plan·todo 및 인계 링크를 갱신한다. 기존 확정 경로가 있으면 내용을 확인하고 다른 작업을 덮어쓰지 않는다. 이전 규칙의 작업 경로도 실제 Issue 또는 draft 경로로 정리하고 연결 문서를 함께 갱신한다.

계획은 독립 검증 가능한 01/02 단위와 todo로 나눈다. 구현 방식에 영향을 주는 미결정이 있으면 해당 작업만 보류하고 필요한 결정을 기록한다. 모든 칸에 분류 태그를 반복할 필요는 없다. 검증·배포 계획은 필수이며 필요 없으면 이유와 전달 방법을 쓴다. 계획 작성 완료와 구현 완료를 구분한다.

## 메타데이터와 상태

`issue`는 하나의 참조 문자열이다. 같은 저장소는 `issue: "#123"`, 다른 저장소는 `issue: "owner/repository#123"` 또는 전체 Issue URL을 사용한다. 번호는 실제 조회한 값이다. YAML에서 `#`는 주석이므로 `issue: #123`으로 쓰지 않는다. 원격 Issue가 없는 파일럿은 `issue: null`과 맥락 절의 로컬 초안 링크로 구분하며 원격 PR 전에 실제 참조로 바꾼다.

`status`의 허용 값은 아래가 정본이다. 다른 문서에서는 이 정의를 링크하며 별도 enum 목록을 복제하지 않는다.

| 값 | 의미와 변경 시점 |
| --- | --- |
| draft | 의도·범위·달성 조건 또는 실행 계획 작성 중 |
| ready | 구현할 단위의 입력·선행 조건과 검증·배포/전달 계획 준비 완료 |
| in-progress | 계획에 따른 구현·검증·전달 진행 중 |
| review-pending | 구현 인계 후 리뷰 또는 리뷰가 요구한 결정·증거 보완 대기 |
| completed | 계획에 포함한 작업·검증·필요한 전달 완료; 미실행 필수 항목이 있으면 사용 금지 |

보류는 별도 status를 추가하지 않고 영향받는 섹션에 사유·필요 입력으로 기록한다. status는 사용자 승인이나 실제 머지·배포 상태를 대신하지 않는다. 완료 판단은 계획의 필수 전달 범위와 실제 증거를 따른다.

## plan.md 양식

계획에는 Issue의 배경, 사용자가 원하는 결과, 현재 동작과 수정 이유, 단계별 작업·흐름, 검증, 배포·전달 및 롤백을 채운다. 맥락·판단은 plan, 구체 작업 체크리스트는 todo, 실제 실행 결과는 handoff에 둔다.

```markdown
---
issue: "#<실제 Issue 번호>"
status: draft
baseline:
  branch: "<확인한 기준 브랜치>"
  commit: "<확인한 기준 커밋>"
---
```

## 채운 예제: 일시 오류 재시도

가상 예제이며 실제 Issue·검증·승인·배포 증거가 아니다. 프로젝트의 실제 명령으로 바꿔 사용한다.

- 맥락: 네트워크 일시 오류에도 “재시도 불가”만 표시된다는 요청이다. 사용자 의도는 일시 오류에서 다음 행동을 안내하는 것이다.
- 범위: 오류 분류와 안내. 결제 요청 자동 재전송과 DB 스키마는 제외한다.
- AC-01: 일시 오류에는 재시도 가능한 안내, 만료 오류에는 재시도 권유 없음.
- 01 retry-classification: 오류 분류 함수와 unit test, 01-todos.md, 정상·만료·알 수 없는 오류 사례.
- 02 retry-message: 안내 소비자 적용과 통합 테스트, 02-todos.md, 기존 오류 안내 유지.
- 흐름: 01 구현 → 01 unit 검증 → 02 적용 → 통합·회귀 검증 → commit → PR → 리뷰; 실패 시 해당 단위 수정·재검증.
- 검증: 확인된 프로젝트 unit 및 integration 명령, 사례별 기대/실제와 실행 커밋은 handoff에 기록하고 todo에는 해당 검증 링크를 연결한다.
- 배포: 설정에서 대상/트리거를 조사하기 전에는 미확인이다. 배포 준비 단위는 blocked이며 코드 조사·배포 방식 결정 후 갱신한다. 배포 승인과 이전 검증된 버전/롤백 가능성 확인 없이 실행하지 않는다.

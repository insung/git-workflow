# 계획의 위치와 작성 규칙

## Issue 안의 계획

계획 작성 단계는 유지한다. 새 작업은 Issue 본문에 계획·상세 설계·중요한 결정 이유를 기록하고, 독립 추적이 필요한 결과만 sub-issue로 나눈다. 신규 plan.md·task-*.md·handoff.md·review.md 작업 기록을 만들지 않는다. 이 참조 파일은 스킬 지침이며 작업별 계획 파일이 아니다.

```markdown
## 계획

1. <변경할 동작·구현 방향·중요한 선택 이유>
2. <선행 조건이 있는 경우 실행 순서>

검증: AC-01 — <입력·기대 동작·확인 방법>.
전달: <적용 대상·순서·적용 후 확인·롤백. 해당 없음이면 이유>.
```

정보가 없으면 필요한 미확인·남은 결정만 표시한다. 일곱 질문이나 고정된 단계 수를 요구하지 않는다. AC는 해당 Issue에서 정의하고 계획에 다시 정의하지 않는다. 결정 변경은 바뀐 점·이유를 기록하고 최초 원문은 보존한다.

| 정보 | 기록 위치 |
| --- | --- |
| 전체 목표·범위·제약·최종 AC·통합 검증·전달 | 상위 Issue |
| 공통 구조·대안·호환성·데이터 전환·롤백 설계와 결정 이유 | 상위 Issue의 계획 아래 필요한 절 |
| 독립 결과의 범위·AC·구현 방향·검증·전달 | 담당 sub-issue |
| 실제 변경·검증 결과·계획 차이·리뷰 | 담당 PR 또는 요청 범위의 대화 |

긴 설명도 관련 Issue 본문에 구성한다. 하위 Issue에는 공통 설계를 복사하지 않고 부모 링크와 적용되는 기준을 연결한다. 별도 비공개 검토 입력·제품 fixture·고유 증거는 [보관 기준](../../git-workflow/references/document-links.md#증거와-실행-로그)을 유지한다.

## Sub-issue 분리 판단

기본은 Issue 하나의 본문 계획이다. AI는 사용자 요청의 목표·범위를 읽고 아래 두 조건을 모두 확인할 때만 sub-issue를 제안한다.

1. 해당 결과에 독립적인 완료 조건과 검증 방법이 있음
2. 별도 PR·전달, 책임·일정, 독립 보류 또는 다른 작업과의 의존성을 따로 추적할 필요가 있음

복잡함·단계 수·파일 수·기존 task 문서 수는 분리 근거가 아니다. 담당자가 같아도 독립 전달·보류가 필요하면 분리할 수 있고, 담당자가 달라도 하나의 결과를 함께 완성하면 본문 계획으로 묶을 수 있다. 구현·테스트·문서 작성은 같은 결과의 단계면 분리하지 않는다. 고정된 최소·최대 Issue 수를 정하지 않는다.

| 사례 | 판단 |
| --- | --- |
| 오타·설정 오류와 회귀 테스트·사용 안내를 같은 PR로 전달 | Issue 하나의 계획 |
| 복잡한 API·화면·테스트를 하나의 완료·전달 단위로 처리 | Issue 하나의 상세 계획 |
| API v2와 소비자 전환을 독립 PR·검증으로 전달하고 전환이 API를 기다림 | 부모 + 결과별 sub-issue, 별도 선행 관계 |
| 기존 task 문서가 5개이나 새 결과·독립 추적 필요가 없음 | 문서 수로 하위 Issue를 만들지 않음 |

분리 제안은 결과 단위·이유·부모 AC와의 대응을 제시한다. 사용자 범위·완료 조건을 바꾸는 결정만 확인받고, 이미 승인된 일상적인 분해를 반복 승인받지 않는다. 실제 생성·연결은 [sub-issue 절차](todos.md)의 승인 범위에서만 실행한다.

## 상세 plan 생성 조건

이 절은 기존 링크 호환을 위해 유지한다. 새 작업에는 상세 plan 파일 생성 조건을 적용하지 않는다. 여러 저장소·역할의 실행 순서와 긴 구조·전환 설계도 상위 Issue에 기록한다. 작업 추적을 분리할 필요는 위 두 조건으로 판단한다.

## 기존 작업 재개

기존 docs/git-workflows의 plan·task·handoff·review·입력·로그와 고정 링크는 당시 기록으로 보존한다. 새 정책을 이유로 자동 삭제·이름 변경·일괄 변환하지 않는다.

1. 실제 Issue·PR의 최신 상태·AC·base/HEAD부터 확인
2. 연결된 기존 계획·담당 작업·공개 지적을 필요한 범위에서 읽고 현재 사실과 대조
3. 새 계획·결정·결과는 Issue·PR에 기록, 기존 체크·결과 갱신은 합의된 재개 범위에서만 수행
4. 기존 기록 이동·삭제가 요청되면 참조와 고유 내용을 조사하고 필요한 Issue·PR로 옮긴 뒤 승인 범위에서 정리

기록의 완료 표시는 현재 구현·검증·배포 증거가 아니다. 기존 task 개수로 sub-issue 수를 정하지 않는다.

## 로컬 파일럿 디렉토리 규칙

원격 접근 불가일 때만 Issue·PR 초안을 접근 가능한 작업용 임시 위치에 두고 local-draft/local-pr-draft로 표시한다. 새 docs/git-workflows 기록은 만들지 않는다. 실제 원격 PR 전에 실제 Issue와 관계를 확인하며 초안 번호·임시 경로를 원격 링크로 만들지 않는다.

# 계획의 위치와 작성 규칙

## Issue 안의 계획

Issue는 요청·기준·계획의 기본 진입점이다. 간단한 작업에는 별도 파일이 필요하지 않다. 일곱 질문이나 고정된 단계 수를 모두 채우지 않는다.

```markdown
## 계획

1. <변경할 동작과 필요한 구현 방향. 중요한 선택 이유가 있으면 별도 문장>
2. <선행 작업이 있을 때만 다음 단계>

검증: AC-01 — <입력·기대 동작·확인 방법>. AC-02 — <유지할 동작과 확인 방법>.
전달: <적용 대상·확인·롤백. 배포가 없으면 확인한 이유와 전달 방법>.
```

위 예제의 검증은 실제 작성 시 사례별로 문장이나 목록을 나눈다. 한 문장에 여러 독립 조건을 압축하지 않는다. 없는 정보는 채우지 않고 필요한 미확인·남은 결정만 표시한다.

| 정보 | 작성 기준 |
| --- | --- |
| 실행 방향 | 원하는 결과를 만드는 변경과 중요한 이유. 파일 경로는 실제로 확인한 것만 사용 |
| 검증 계획 | Issue AC ID마다 예상 입력·기대 동작·확인 방법. 정상·실패·경계·유지 중 해당 사례만 선정 |
| 추가 검토 | 확인된 연관 소비자·보안·데이터·운영 영향. 추측한 문제를 사실로 쓰지 않음 |
| 전달·롤백 | 배포 대상·순서·적용 후 확인·되돌릴 지점. 미확인 환경·실행 여부와 필요한 승인 구별 |
| 남은 결정 | 구현 결과·범위에 영향을 주는 인간 결정. 조사로 알 수 있는 것은 먼저 조사 |

단계별 작업·명령·원시 로그를 본문에 모두 열거하지 않는다. 완료 조건은 Issue의 AC이며 계획에서 다시 정의하지 않는다. 결정·요청 변경은 기존 합의와 바뀐 점·이유를 짧게 기록하고 최초 원문은 보존한다.

## 상세 plan 생성 조건

다음 중 하나로 본문만으로 실행 설계가 불명확할 때 별도 plan을 만든다. 파일 생성 이유를 Issue에 한 문장으로 남긴다.

- 여러 저장소나 역할 사이의 실행 순서·호환성·배포 의존성 조정
- 대안·구조·데이터 전환 등 별도 검토가 필요한 상세 설계
- 본문에 유지하면 핵심 판단이 묻히는 단계 의존성이나 재현 설명

단계 수·스킬 호출·증거 파일 존재만으로 상세 설계를 요구하지 않는다. 단일 저장소·역할의 한 결과라면 먼저 본문에 계획을 작성한다. 복잡한 작업도 plan 하나부터 시작하며 task 분리는 독립 작업 계약이 필요한 경우에만 한다 ([todo](todos.md)).

## 디렉토리 규칙

상세 설계가 필요할 때만 대상 리포의 `docs/git-workflows/{yyyy-MM}/{dd}_{issue-number}_{title}/plan.md`를 만든다. 날짜는 프로젝트 시간대의 작업 시작일, 번호는 실제 Issue, title은 짧은 영어 kebab-case다. 시작일은 작업 중 바꾸지 않는다.

```text
docs/git-workflows/YYYY-MM/DD_<issue>_<topic>/
└── plan.md
```

handoff.md·review.md·evidence/·txt는 필수 산출물이 아니다. [증거 보관 기준](../../git-workflow/references/document-links.md#증거와-실행-로그)을 적용한다. 독립 입력은 공개 plan과 같은 작업본에 두지 않는다.

## plan.md 템플릿

```markdown
---
issue: "<실제 Issue URL>"
status: draft
branch: "<작업 브랜치>"
base: "<대상 브랜치>"
created: "<YYYY-MM-DD>"
---

# <주제> 상세 설계

Issue: <원문·범위·제약·AC·현재 계획의 링크>
분리 이유: <Issue 본문에 두기 어려운 설계>

## 설계와 결정 이유

<확인한 전제, 선택한 방식·이유, 미합의 제안과 남은 결정 구별>

## 실행 순서와 의존성

<각 단계의 결과·선행 조건. 독립 작업 계약이 필요하면 해당 task만 연결>

## 검증과 전달

<본문에서 분리한 상세 AC별 검증·배포·롤백. 본문과 중복 기재하지 않고 서로 연결>
```

내용 없는 선택 절은 만들지 않는다. 사용자 원문·목표·범위·AC를 plan에 복사하지 않는다. 중요한 설계 변경은 이전 결정과 차이·이유를 기록하고 Issue의 현재 범위와 연결한다.

## 프론트메터 규칙

issue는 확인된 번호·URL을 쓰며 YAML의 `#` 참조는 따옴표로 감싼다. branch/base는 확인 후 쓰고 미정이면 미정으로 표시한다. 기준 코드 commit·미커밋 변경은 검증 기록에 둔다.

| status | 의미 |
| --- | --- |
| draft | 범위·설계·실행 계획 작성 중 |
| ready | 구현 입력·검증·전달 계획 준비 |
| in-progress | 구현·검증·전달 중 |
| review-pending | 검토 또는 증거 보완 대기 |
| completed | 합의된 모든 작업·필수 검증·전달 완료 |

보류는 남은 결정에 표시하며 completed는 필수 미실행이 있으면 쓰지 않는다. status는 머지·배포의 실제 상태를 대신하지 않는다.

## 기존 작업 재개

기존 docs/git-workflows의 plan·task·handoff·review·입력·로그는 과거 고정 링크와 당시 증거로 보존한다. 자동 삭제·이름 변경·일괄 변환하지 않는다.

1. 실제 Issue·PR의 최신 상태·AC·base/HEAD부터 확인한다.
2. 기존 plan의 공통 맥락·결정과 담당 task·handoff·공개 리뷰 지적을 읽는다. 옛 todo 이름도 기존 plan의 링크를 따른다.
3. 당시 결과를 현재 HEAD의 통과로 바꾸지 않는다. 저장소 문서와 원격 최신 상태가 다르면 시점과 남은 확인을 기록한다.
4. 기존 작업 계약이 유효하면 그대로 재개한다. 새 문서 형식 때문에 입력 부족으로 거절하거나 필수 파일을 추가 생성하지 않는다. 변경된 범위만 Issue의 현재 계획과 연결한다.

## 로컬 파일럿 디렉토리 규칙

원격 접근 불가일 때만 Issue 초안을 접근 가능한 작업용 임시 위치에 두고 local-draft로 표시한다. 상세 설계가 필요하면 `docs/git-workflows/{yyyy-MM}/{dd}_draft_{title}/plan.md`, `issue: null`을 쓴다. 실제 Issue 확인 후 번호 경로로 한 번 옮기고 링크를 갱신한다. 원격 PR 전에 실제 원격 Issue가 필요하다.

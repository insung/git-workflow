# 브랜치 전략 정의

## 기존 dev/prod 후보

[프로젝트 정책](project-policy.md)을 먼저 읽는다. 아래는 명시적으로 선택할 수 있는 기존 후보이며 새 전략의 자동 기본값이 아니다. dev에서 feature/ 작업 브랜치를 만들고 긴급 수정에는 hotfix/ 접두사를 쓴다. 대상 저장소에 명시적 규칙이 있으면 그 규칙이 우선이다.

| 브랜치 | 역할·흐름 |
| --- | --- |
| dev | 개발·통합 기준; feature의 분기·머지 대상 |
| feature/<scope>-<주제> | dev에서 분기, dev를 대상으로 변경 PR 준비 |
| hotfix/<scope>-<주제> | 기본적으로 prod에서 분기; prod 반영·배포 후 dev에 역반영 |
| prod | 운영 배포 기준; dev의 배포 대상 변경을 머지 |

일반 변경은 `dev → feature/… → dev → prod`로 진행한다. 긴급 수정은 `prod → hotfix/… → prod → dev 역반영`을 따른다. 예외 분기 기준은 해당 저장소와 배포 상태를 확인한다. 릴리즈 대상 prod 커밋에 태그를 남기고 릴리즈를 기록한다. 태그 형식·발행 검증은 [git-release](../../git-release/SKILL.md)가 담당한다. 이 이름을 채택해도 실제 기존 브랜치 이름을 자동 변경하지 않는다.

## 저장소별로 확인할 질문

저장소 문서와 workflow에서 확인할 수 없는 결정만 사용자에게 묻는다.

* dev/prod 후보를 선택한 경우 그 역할을 해당 저장소에 적용할 수 있는지
* 실제 배포가 브랜치 머지, 태그, 수동 실행 중 무엇으로 시작되는지
* hotfix가 prod의 현재 커밋에서 분기해도 실제 운영 버전과 일치하는지
* prod 반영 후 dev 역반영에 충돌이나 함께 배포하면 안 되는 변경이 있는지
* PR의 merge/squash/rebase 방식과 공유 브랜치 보호 규칙

당장 필요하지 않은 결정까지 한 번에 요구하지 않는다. 모르는 배포 기준을 브랜치 이름으로 추정하지 않는다. 배포하지 않는 저장소도 기존 PR 흐름을 우선하며 단일 브랜치 체계로 임의 변경하지 않는다.

## 조사와 결과

`git branch -a`, 최근 통합 이력, 배포 workflow와 태그를 확인한다. 로컬 원격 참조는 오래됐을 수 있다. 원격 조회가 필요하면 접근과 요청 범위를 먼저 확인한다.

다음 내용을 전략안으로 제시한다. 프로젝트 정책을 지속 기록할 때는 [초기화 승인·보존](../../workflow-init/references/branch-policy.md#승인과-보존)을 따르며 단일 정본을 사용한다. 전략 기록만을 위해 plan 파일을 만들지 않는다.

| 항목 | 기록할 내용 |
| --- | --- |
| 역할 | 각 브랜치가 맡는 통합·검증·운영 목적 |
| 일반 작업 | feature의 base, 이름, PR 대상과 머지 방식 |
| 긴급 수정 | hotfix 기준 커밋/브랜치, 첫 머지 대상, 역반영 경로 |
| 배포 | 실제 트리거·대상 커밋·태그와 롤백 기준 |
| 미정 | 결정이 필요한 항목과 그동안 보류할 행동 |

이미 진행 중인 브랜치와 열린 PR, 배포 자동화의 영향을 확인한 뒤 전략 변경을 제안한다. 정책 제안만으로 브랜치·보호 설정을 변경하지 않는다.

## 브랜치 작업을 요청받은 경우

[프로젝트 정책 읽기](project-policy.md)로 요청과 규칙을 대조하고 확인된 base의 커밋과 작업본 변경 상태를 먼저 확인한다. 요청한 브랜치만 만든다. 기존 브랜치 이동·이름 변경·삭제는 별도 요청 범위로 판단한다.

공유 브랜치를 rebase하거나 force push하지 않는다. 작업 브랜치의 이력 정리가 필요하면 다른 사용자와 승인 범위를 확인한다. 저장소의 merge 정책이 없다는 이유로 squash나 --no-ff를 자동 선택하지 않는다.

hotfix는 확정된 운영 기준에서 분기한다. 실제 배포된 커밋을 기준으로 삼는 전략이면 해당 커밋을 먼저 확인한다. 수정 뒤 정규 작업 브랜치에도 반영할 필요가 있는지 대조한다. 이 경로가 미정이면 긴급 수정의 분기·머지를 보류하고 필요한 결정을 반환한다.

# 릴리즈의 요청과 변경 기록

릴리즈 작업에 Issue가 필요한지와 추가 변경의 기록 위치를 정하는 정본이다. 대상 프로젝트의 명시적 Issue 필수 정책이 있으면 우선하며, 이 예외로 프로젝트 정책을 자동 변경하지 않는다.

## Issue 없는 릴리즈와 준비 PR

이미 검증된 커밋의 태그·Release 작업만 수행하면 별도 릴리즈 Issue를 강제하지 않는다. 대상 commit·태그·노트·검증·발행 결과를 연결하고 발행 승인은 기존 git-release 절차를 따른다.

순수 릴리즈 준비 PR은 다음 조건을 모두 충족할 때 원격 Issue 연결의 예외로 처리할 수 있다.

1. 변경은 버전 표기·CHANGELOG·릴리즈 노트·발행 메타데이터 준비에 한정된다. 기능·정책·의존성·배포 실행 설정·일반 문서 정리나 삭제가 섞이면 예외가 아니다. 파일 이름이 릴리즈 노트라는 이유로 새 정책 변경을 숨기지 않는다.
2. 사용자의 릴리즈 준비 요청과 목표 버전이 확인되고, PR 생성과 해당 push가 승인된 범위다. 열린 동일 범위 Issue가 있으면 재사용하고, Issue 생략을 이유로 연결을 제거하지 않는다. 닫힌 릴리즈 Issue를 임의 재개하지 않는다.
3. PR에 `## 릴리즈 준비와 요청 근거`를 두고 실제 사용자 요청·준비 이유·이전 배포와 후보 범위·변경 파일과 포함 PR·현재 검증·남은 결정/승인을 기록한다. 없는 요청이나 Issue 번호를 만들지 않는다. 포함 기능의 기존 Issue·PR 링크는 그대로 유지한다.
4. 실제 diff를 위 범위와 대조한다. 관련 Issue가 없는 이유와 적용한 예외를 명시하고 Closes를 쓰지 않는다. 실제 Issue가 있다면 일반 연결 검사를 수행한다.

PR 생성·검토·머지에서 같은 범위와 근거를 대조한다. 리뷰 중 새 변경이 추가되면 예외 조건을 다시 확인한다. 조건 미충족·자료 부족은 Issue 보완 또는 명시적 프로젝트 예외 결정으로 인계하며, 예외를 일반 기능 PR에 확대하지 않는다. Issue 없는 작업의 commit에는 가짜 Refs를 넣지 않는다. Issue 참조 생략이 검증·머지·발행 승인 생략을 뜻하지 않는다.

## 릴리즈 중 추가 작업

추가 작업의 요청·왜 필요한지·사용자 결정과 영향·AC를 먼저 기록한다. 발견은 구현 승인이 아니며, 범위 확장이 필요하면 제안하고 결정된 범위만 수행한다.

- 같은 릴리즈 준비의 완료·검증·전달 단위라면 열린 릴리즈 Issue에 추가할 수 있다. 최초 원문을 보존하고 후속 요청·결정·AC를 구별한다. 예: 릴리즈 안내 보완과 같은 PR로 전달할 기록 정리. 일반 문서 정리도 이슈를 사용하는 추가 작업이며 순수 준비 PR 예외와 구별한다.
- 독립 완료·검증과 별도 PR·일정·보류·의존성 추적이 모두 필요하면 [기존 분리 기준](../../issue-create/references/plan.md#sub-issue-분리-판단)에 따라 별도 Issue 연결을 제안한다. 파일 수·커밋 수만으로 분리하지 않는다.
- 릴리즈 Issue가 없는데 새 동작·정책 변경 등이 필요해지면 변경 Issue 또는 릴리즈 Issue를 제안하고 생성 승인 범위에서 기록한다. 기존 닫힌 Issue의 당시 범위를 새 요구로 확장하거나 자동 재오픈하지 않는다. 같은 기존 요구의 미충족 보완은 관계를 먼저 확인한다.

## 개별 수정의 출처

복합 릴리즈 Issue의 전체 목표는 개별 수정의 이유를 대신하지 않는다. 요청별 식별자 또는 의미가 분명한 절·실제 댓글 링크를 사용하고, 변경 단위가 어떤 요청·결정·AC를 구현했는지 PR에 연결한다. 모든 프로젝트에 별도 요청 ID를 강제하지 않으며 AC 없는 역사 기록도 실제 원문과 diff로 조사한다.

예: R1 버전 준비 / AC-01 / 버전 커밋, R2 읽기 부담을 줄이는 기록 정리 / AC-02 / 정리 커밋, R3 후속 timeout 변경 / AC-03 / 후속 PR. commit의 Refs가 같은 Issue를 가리켜도 세 이유는 각각 대조한다. squash이면 PR 내부 변경 범위와 요청을 대조한다.

설계·요청은 Issue, 실제 결과·검증·계획 차이는 PR, 배포 범위와 전환·발행 결과는 릴리즈에 남긴다. 같은 전문을 반복하지 않는다. [git-history](../../git-history/SKILL.md)는 실제 도입 변경·관련 요청·후속 결정과 기록 공백을 구별한다. 과거 기록과 이력을 이 기준에 맞춰 자동 변환하지 않는다.

# 커밋 이력 기반 릴리즈 노트

릴리즈 노트는 선택한 배포 범위에서 사용자가 겪는 변화를 설명한다. 커밋 제목은 후보를 찾는 색인이고, 실제 변경과 배포 범위가 근거다. 저장소에 기존 `CHANGELOG`, 릴리즈 템플릿, release-drafter 또는 제품별 발행 방식이 있으면 그 형식과 분류를 먼저 따른다.

## 범위 고정

1. 어떤 제품·패키지·배포 단위의 노트인지 확인한다. 여러 제품이 한 저장소에 있으면 해당 제품의 이전 배포 지점과 이번 대상 지점을 따로 찾는다.
2. 이전 릴리즈 태그 또는 확인된 배포 커밋을 `base`, 이번 릴리즈 후보 커밋을 `target`으로 정한다. 날짜순 최신 태그가 반드시 이전 배포 지점은 아니다. 태그 형식, 실제 배포 기록과 조상 관계를 확인한다.
3. 기준이 불명확하면 임의 버전과 날짜를 붙이지 않는다. 확인 가능한 커밋을 기준으로 `Unreleased` 초안을 만들거나 기준점 결정을 요청한다.

```bash
git merge-base --is-ancestor <base> <target>
git log --first-parent --format='%h %s' <base>..<target>
git log --format='%H %s%n%b' <base>..<target>
git diff --name-status <base> <target>
```

첫 로그는 통합 흐름의 변경 단위를, 두 번째는 병합된 브랜치 안의 세부 커밋과 본문을 확인하는 데 쓴다. `--first-parent`가 머지 커밋만 보여 주는 것은 아니다. squash, rebase, 일반 커밋도 통합 흐름에 따라 나타날 수 있다. PR과 label은 접근 가능할 때 보조 근거로 확인한다. GitHub 접근이 안 되면 로컬 Git 근거의 한계를 밝히고 계속할 수 있다.

## 내용 선정

- `feat`, `fix`, `perf`를 후보로 찾되, 제목만 옮기지 않는다. 해당 diff, PR 설명 또는 변경 문서에서 사용자에게 나타나는 결과를 확인한다.
- 여러 커밋이 하나의 기능을 완성했으면 한 항목으로 묶는다. 머지 커밋과 내부 커밋을 중복 기재하지 않는다.
- `docs`, `refactor`, `build`, `ci`, `chore` 등도 설치 절차, 지원 환경, 운영 방식이나 호환성을 바꿨다면 포함한다. 내부 정리만 한 커밋은 보통 제외한다.
- 호환성 변경은 이전 사용 방법과 필요한 전환 조치를 확인해 별도로 드러낸다. 커밋 표기만으로 실제 호환성 단절을 단정하지 않는다.
- 아직 합쳐지지 않았거나 선택한 `target` 뒤에 들어간 변경은 제외한다. 모노레포에서는 경로만 보고 공용 코드의 영향을 놓치지 않도록 소비자도 확인한다.

## 결과 중심 초안과 편집

[GitHub CLI 릴리즈](https://github.com/cli/cli/releases)를 참고해 첫 문단에 핵심 변화, 본문에 변경 종류별 사용자 결과, 필요한 전환 조치와 검증·추적 근거를 둔다. 분류 이름·순서는 제품의 실제 변화와 저장소 규칙에 맞춘다. 자동 생성한 PR 목록은 후보 목록이며 완성 노트를 대신하지 않는다.

1. 선정한 변경마다 사용자 결과·적용 조건·승인·기존 동작 보존·전환·검증 한계를 적는다.
2. 같은 기능의 여러 커밋은 결과 하나로 묶고 관련 조건은 짧게 연결한다. 독립적인 결과·승인 조건·보존 판단은 항목을 나눈다.
3. 실제 내용이 있는 기능·개선, 수정, 설치·운영 등의 절만 만든다. 호출명·경로·지원 환경 변경은 전환 안내로도 추적한다.
4. 제목과 첫 문단만 읽어도 핵심 결과를 이해하도록 편집한다. 공개 GitHub Release의 name은 `v버전`만, 본문 첫 줄은 핵심 결과를 설명하는 구체적 H2 제목(예: `## 재시도 안내와 호출명 전환`)으로 구별한다. “핵심 변화”라는 자리표시자를 그대로 제목으로 쓰지 않는다. 저장용 문서 제목은 `# v버전 — 핵심 변화`로 쓸 수 있다. 프로젝트의 별도 제목·언어·템플릿 규칙이 있으면 우선한다.
5. [공통 편집 순서](../../git-workflow/references/writing-conventions.md#정보-단위와-작성-후-편집)로 원문과 대조한 뒤 초안을 제시한다. 설명 목록은 완결된 문장을 허용하고 제목·표의 짧은 값은 명사형을 유지한다.

## GitHub CLI 참고 기본 구성

[GitHub CLI](https://github.com/cli/cli/releases)의 분류별 짧은 변경 목록과 PR·전체 비교 연결을 참고한다. 이 저장소의 승인된 기본 형식은 다음과 같다. 프로젝트의 별도 형식이 있으면 우선하며, 내용이 없는 절은 만들지 않는다.

1. 본문 첫 H2에 핵심 변화를 쓰고 한두 문장으로 사용자 결과를 요약한다.
2. `## 변경 사항` 아래 실제 변화가 있는 분류만 둔다. 기본 후보는 `### 🚀 기능·개선`, `### 🐛 수정`, `### 📚 운영·기록 개선`이다. 성능·보안·의존성 등 다른 변화는 실제 내용에 맞게 추가한다. type만으로 분류하지 않는다.
3. 각 항목은 사용자 결과와 필요한 조건을 한두 문장으로 쓰고 확인된 관련 PR을 연결한다. 같은 결과의 커밋·PR은 묶고 내부 절차 전문·파일 목록·해시·AC 표는 상세 근거로 연결한다. 승인·보존·호환성·중요한 위험은 간결화를 이유로 누락하지 않는다. 확인된 출처가 없으면 임의 PR 번호·작성자를 붙이지 않는다.
4. `## 업그레이드 안내`에는 필요한 호출·경로·설정 전환과 설치·새 세션 조건을 둔다. 이전/새 사용 방법이 여러 개면 표로 비교한다. 자동 변경 여부와 기존 동작 보존, 별도 승인 조건도 관련 항목에 남긴다.
5. `## 검증`에는 실제 검사 결과와 중요한 미검증·한계를 짧게 남기고 자세한 AC·명령·검토·적용 근거를 확인된 PR·Issue로 연결한다. 테스트 통과·캐시 일치를 호스트 호출·효과 측정·독립 리뷰의 증거로 대신하지 않는다.
6. 마지막에는 `**전체 변경:**` 뒤에 이전 태그 → 이번 태그라는 링크 문구와 확인한 비교 URL을 둔다. 저장소·공개 기준 태그·대상 포함을 대조한다. 이전 공개 태그가 없으면 확인한 커밋 비교를 사용한다. 대상 태그가 미발행이면 예정 비교를 발행 완료로 쓰지 않고 준비 상태를 표시하거나 확인한 커밋 비교를 사용한다. 비교 기준·URL이 불명확하면 링크를 생성하지 않고 이유를 남긴다.

공개 노트에 상세 실행 경과를 반복하지 않되, 어떤 결과와 한계가 생략되는지 원문과 대조한다. GitHub CLI의 기여자·보안·의존성 절도 실제 내용과 확인된 근거가 있을 때만 사용한다. 완성 형태는 [간결한 공개 노트 예시](release-notes-example.md)를 참고한다.

## 작성과 재확인

저장소의 기존 언어, 제목, 순서와 링크 형식을 따른다. 형식이 없으면 기능·수정·성능·호환성·설치 또는 운영 변경 중 실제 내용이 있는 분류만 사용한다. 항목은 커밋 명령형 대신 사용자가 얻는 결과로 쓰고, 추적이 필요하면 확인된 커밋 또는 PR을 연결한다.

버전과 날짜는 저장소의 확정된 릴리즈 정보가 있을 때만 적는다. 테스트 결과나 배포 완료 여부도 별도의 실행 증거가 있을 때만 적는다. 초안을 `base..target`의 전체 변경과 다시 대조해 누락·중복·범위 밖 항목을 확인한다.

사용자가 노트를 저장할 파일을 지정했거나 저장소의 기존 발행 파일에 쓰라고 요청했다면 그 파일을 갱신한다. 그 외에는 검토할 초안을 제시한다. 노트 작성 자체는 커밋, 태그, 푸시, GitHub Release 발행 또는 배포를 실행하지 않는다.

## 완성 예시

아래는 가상 입력과 결과다. 버전·변경·검사 수는 실제 배포 증거가 아니다. `feat`의 안내 추가, `docs`의 호출명 변경, `refactor`의 기존 오류 안내 유지 변경을 실제 사용자 결과로 선정한 예다.

```markdown
공개 Release name: v1.2.0

## 재시도 안내와 호출명 전환

일시 오류에서 재시도 방법을 확인할 수 있다. 안내 호출명은 retry-guide로 바뀐다.

## 변경 사항

### 🚀 기능·개선

- network 오류에서 재시도 방법을 안내한다.

### 🐛 수정

- expired 오류의 기존 안내를 유지한다.

## 업그레이드 안내

- retry-help 호출을 retry-guide로 바꾼다.
- 자동 재전송은 포함하지 않는다.
- AGENTS.md 변경은 정확한 경로·추가 전문·위치 승인 후 적용한다.

## 검증

- 제공된 회귀 검사 결과는 8/8 통과다. 실기기 검증은 미실행이다.
- 범위는 이전 공개 v1.1.0부터 이번 v1.2.0까지다. 확인된 PR 링크가 없어 링크를 만들지 않는다.
```

실제 작성에서는 승인된 변경 범위의 PR·diff를 연결한다. 미발행 버전 갱신 커밋은 공개 릴리즈 비교의 기준으로 바꾸지 않고 내부 구간의 근거로 표시한다. 같은 버전의 수정 배포라면 기존 설치자의 재설치 필요 여부와 새 세션 필요 조건을 보존한다.

## 복합 항목의 편집 예시

개선 전:

> agents-init을 추가해 개별 프로젝트와 여러 프로젝트의 루트에 채택 선언을 제안하고, 정확한 경로·추가 전문·위치를 보여주고 명시적 승인 후 기존 내용을 보존하며 추가하고 중복·충돌을 확인함.

개선 후:

```markdown
### AGENTS.md 채택 선언

agents-init으로 개별 프로젝트 또는 여러 프로젝트의 루트에 채택 선언을 제안할 수 있다.

- 승인: 정확한 경로·추가 전문·위치를 보여주고 명시적 승인 후 추가한다.
- 확인: 기존 선언과의 중복·충돌을 먼저 확인한다.
- 보존: 기존 AGENTS.md 내용은 유지한다.
```

[공통 편집 순서](../../git-workflow/references/writing-conventions.md#정보-단위와-작성-후-편집)로 핵심 결과와 각각 판단할 조건을 분리한 예다. 문장 수를 줄이기 위해 승인·확인·보존 의미를 삭제하지 않는다.

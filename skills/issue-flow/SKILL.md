# 목표 단위 진행 흐름 보고

[공통 실행 경계](../git-workflow/references/execution-boundaries.md)를 적용한다.
보고는 읽기 전용이다. Issue·PR·브랜치를 바꾸지 않으며, 바꾸는 파일은 2절의 상태 파일뿐이다.

보고의 답은 **순서도 + 변경표**다. 순서도는 목표 하나에 속한 Issue·PR·결정을 노드로, 선행 관계를 화살표로 그린다. 매번 새로 그리지 않고 **지난번 사용자에게 보여 준 판(기준판)** 과 비교해 진행 위치와 바뀐 것을 표시한다.

## 1. 범위

- 범위는 **목표 하나**다. 목표는 한 문장(예: 「일별 배치를 실행해 집계 결과를 DB에 남긴다」).
- 그 목표를 위해 열린·닫힌 Issue, 그 Issue들이 낳은 다른 저장소의 Issue·PR, 사용자 결정(d1…)을 노드로 넣는다.
- 목표와 관계없는 Issue는 넣지 않는다. 지나가며 언급만 된 아이디어도 넣지 않는다.

## 2. 상태 파일(기준판)

- 이름: `flow-<목표 슬러그>.json`. 없으면 첫 보고에서 v1로 만든다.
- 위치: 사용자가 지정한 폴더. 지정이 없으면 관리 세션의 작업 폴더에 두고 경로를 보고한다. 대상 저장소에는 커밋하지 않는다.
- 보고할 때마다 판을 하나 더한다. 이전 판은 지우지 않는다.

```json
{
  "goal": "목표 한 문장",
  "versions": [
    {
      "v": 3,
      "date": "2026-10-28",
      "nodes": [
        {"id": "batch#32", "repo": "owner/batch", "title": "#32 집계 저장",
         "goal": "집계 결과를 DB에 쓴다", "status": "wait_user",
         "deps": ["batch#7"], "evidence": "PR #39 (머지 대기)"}
      ]
    }
  ]
}
```

- `id`는 고정 키다(`<저장소 약칭>#<번호>`, 결정은 `decision:d3`). 제목이 바뀌어도 id는 바꾸지 않는다.
- `goal`은 몇 단어. 박스에 그대로 들어간다.

## 3. 상태 값

| status | 뜻 | 색 |
| --- | --- | --- |
| done | 원천에서 확인된 완료(PR MERGED와 merge commit, Issue CLOSED·stateReason COMPLETED) | 회색 |
| now | 하위 세션이 작업 중 | 주황 |
| wait_user | 사용자 승인·결정·실행을 기다린다 | 주황 |
| todo | 선행이 끝나지 않아 시작 전 | 청록 |
| dropped | 하지 않기로 했다 | 그림에서 빼고 변경표에만 |

`done`은 **GitHub를 다시 조회해 확인한 것**만 쓴다. 하위 세션 보고만으로 완료로 바꾸지 않는다.

## 4. 보고 순서

1. 상태 파일의 최신 판을 읽는다(기준판).
2. 원천을 다시 조회한다: 노드마다 Issue·PR 상태, merge commit. 새 하위 세션 보고와 사용자 결정을 반영한다.
3. 기준판과 비교해 변경을 넷으로 나눈다: **완료됨**(status가 done으로), **새로 생김**(새 id), **바뀜**(goal·deps·repo 변경, 또는 done이 아닌 status 변경), **삭제**(dropped 또는 id 사라짐).
4. 순서도를 그린다(5절). 아래에 변경표(6절)를 붙인다.
5. 사용자에게 보여 준 판을 새 판으로 저장한다.

## 5. 순서도 그리기

- SVG 한 장(시각화 도구가 있으면 그 도구, 없으면 mermaid flowchart).
- **저장소 영역:** 목표 저장소는 아래 큰 점선 영역, 그 밖의 저장소는 위 점선 영역. 영역 이름을 영역 오른쪽 위에 쓴다.
- **박스:** 제목 한 줄 + 목표 한 줄. 긴 설명은 그림 밖 본문으로.
- **화살표:** `deps`대로. 동시에 진행하는 노드는 옆으로 나란히.
- **진행 표시:**
  - 기준판 이후 done이 된 노드: 「이번에 완료」 꼬리표
  - now 노드: 「지금 여기」 꼬리표, 테두리 굵게
- **변경 표시:**
  - 새로 생김: 점선 테두리 + 「새로」 꼬리표
  - 바뀜: 「바뀜」 꼬리표. deps가 바뀌었으면 그 화살표만 굵게
  - 삭제: 그림에서 빼고 변경표에만
- 완료 노드가 많으면 한 박스로 묶는다(「완료: #3 #31 #5 …」). 이번에 완료된 것은 묶지 않는다.
- 범례 한 줄: 색 3개 + 점선 = 새로.

## 6. 출력 계약

답은 이 순서로만 쓴다.

1. **첫 줄:** `v3 → v4: 완료 2 · 새로 1 · 바뀜 1 · 삭제 0` (첫 보고는 `v1: 노드 n개`)
2. **순서도**
3. **변경표** — 변경이 있을 때만

   | 노드 | 지난 판 | 이번 판 | 바뀐 이유 |
   | --- | --- | --- | --- |
   | #32 집계 저장 | todo | wait_user | PR #39 생성, 머지 승인 대기 ([하위 세션 보고]) |

   「바뀐 이유」에는 사용자 결정(id·발언) 또는 하위 세션 보고·PR 링크를 쓴다.
4. **사용자가 할 일** — wait_user 노드만, 노드마다 한 줄(어디서 무엇을).
5. **대기 중 결정** — 결정 노드만, 권장안과 함께.

이 다섯 부품 밖의 문장은 넣지 않는다.

## 자주 하는 실수

| 실수 | 대신 이렇게 |
| --- | --- |
| 기준판을 읽지 않고 처음부터 다시 그린다 | 상태 파일을 먼저 읽고 diff를 표시한다 |
| 하위 세션 보고만 보고 done으로 바꾼다 | GitHub를 다시 조회해 merge commit·CLOSED를 확인한다 |
| 박스에 설명을 길게 쓴다 | 제목 + 목표 한 줄. 나머지는 변경표·본문 |
| 다른 저장소 작업을 목표 저장소 영역에 섞는다 | 저장소 영역을 나눈다 |
| 삭제된 노드를 말없이 없앤다 | 변경표에 「삭제 · 이유」로 남긴다 |
| 보여 준 판을 저장하지 않는다 | 보고 끝에 새 판을 상태 파일에 더한다 |

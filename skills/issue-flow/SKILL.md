# 목표 단위 진행 흐름 보고

[공통 실행 경계](../git-workflow/references/execution-boundaries.md)를 적용한다.
보고는 읽기 전용이다. Issue·PR·브랜치를 바꾸지 않으며, 만드는 파일은 2절의 기록 파일뿐이다.

보고의 답은 **순서도 + 변경표**다. 이전 보고에서 사용자에게 보여 준 버전(이전 버전)과 비교해 진행 위치와 바뀐 것을 알린다.

## 1. 범위

- 범위는 **목표 하나**다. 목표는 한 문장(예: 「일별 배치를 실행해 집계 결과를 DB에 남긴다」).
- Issue 번호로 요청받으면 그 Issue의 목표를 목표로 삼는다.
- 목표를 정할 근거가 없으면 「정하는 중」으로 쓰고 사용자에게 묻는다.
- 목표를 가진 Issue는 목표와 함께 쓴다(예: 「#93 · 목표 문장」). 작업 노드로 따로 그리지 않는다.
- 그 목표를 이루는 sub-issue·PR, 다른 저장소의 Issue·PR, 하위 세션의 작업을 노드로 넣는다.

## 2. 기록 파일

보고할 때마다 버전 번호 n을 1 증가시키고 두 파일을 남긴다. 이전 버전 파일은 지우지 않는다.

| 파일 | 내용 |
| --- | --- |
| `flow-<목표 슬러그>.json` | 목표 문장과 버전별 노드 상태 |
| `flow-<목표 슬러그>-v<n>.<확장자>` | 이번에 보여 준 순서도 원본 |

위치는 사용자가 지정한 폴더다. 지정이 없으면 관리 세션의 작업 폴더에 둔다. 대상 저장소에는 커밋하지 않는다.
순서도 파일은 그 파일만 열어도 보여 준 모양 그대로 보이게 저장한다.

```json
{
  "goal": "목표 한 문장",
  "versions": [
    {"v": 3, "date": "2026-10-28", "diagram": "flow-daily-batch-v3.svg",
     "nodes": [{"id": "batch#32", "title": "#32 집계 저장",
                "desc": "집계 결과를 DB에 쓴다", "status": "wait_user",
                "deps": ["batch#7"], "evidence": "PR #39 (머지 대기)"}]}
  ]
}
```

`id`는 고정 키다. 제목이 바뀌어도 바꾸지 않는다.

| 노드 | id |
| --- | --- |
| Issue·PR | `<저장소 약칭>#<번호>` |
| 결정 | `decision:<슬러그>` |
| 번호 없는 작업 | `task:<슬러그>` |

## 3. 상태 값

| status | 보고에 쓰는 말 | 뜻 |
| --- | --- | --- |
| done | 완료 | 원본 데이터에서 확인된 완료 |
| now | 진행 중 | 하위 세션이 작업 중 |
| wait_user | 사용자 대기 | 사용자 승인·결정·실행 대기 |
| todo | 시작 전 | 선행 작업이 끝나지 않음 |
| proposed | 제안 | 검토에서 찾았고 아직 하기로 정하지 않음 |
| dropped | 제외 | 하지 않기로 함 |

`done`은 원본 데이터를 다시 확인한 것만 쓴다. 하위 세션 보고만으로 완료로 바꾸지 않는다.

- Issue·PR: GitHub 재조회(PR MERGED와 merge commit, Issue CLOSED·stateReason COMPLETED)
- 결정: 사용자 답
- 번호 없는 작업: 결과 파일·커밋을 직접 확인

## 4. 순서도에 넣을 것

- 목표 문장
- 노드마다 핵심 설명. 다른 문서를 열지 않아도 무슨 일인지 알 수 있는 말로 쓴다.
- Issue·PR 번호. 번호가 없는 노드는 번호 없이 쓴다.

결정 ID·AC 번호 같은 내부 ID와 status 영문 값은 보고에 쓰지 않는다. 뜻을 말로 쓴다.

## 5. 보고 순서

1. json의 최신 버전과 그 버전의 순서도 파일을 읽는다(이전 버전).
2. 원본 데이터를 다시 조회한다. 노드마다 Issue·PR 상태와 merge commit을 보고, 하위 세션 보고(세션 알림·세션 목록)와 사용자 결정을 반영한다.
3. 검토를 요청받았으면 하위 세션의 결과를 Issue의 계획·달성 조건과 대조한다. 빠진 것·고칠 것을 찾고, 새 작업이면 `proposed` 노드로 더한다.
4. 이전 버전과 비교해 변경을 넷으로 나눈다: **완료**(status가 done으로 바뀜), **추가**(새 id), **수정**(제목·설명·deps 변경, 또는 done·dropped가 아닌 status 변경), **제외**(dropped로 바뀜 또는 id 사라짐).
5. 답을 쓰고, json에 새 버전을 더하고, 순서도를 `-v<n>` 파일로 저장한다.

## 6. 출력

1. **요약** — 목표 문장, 전체 진척(완료 n / 전체 m), 이전 보고 이후 바뀐 것을 한두 문장으로. 첫 보고는 「첫 보고」라고 쓴다.
2. **순서도**
3. **변경표** — 이전 보고 이후 바뀐 노드만. 첫 보고에는 쓰지 않는다.

   | 작업 | 변경 | 이전 상태 → 현재 상태 | 이유 |
   | --- | --- | --- | --- |
   | #32 집계 결과를 DB에 저장 | 수정 | 시작 전 → 사용자 대기 | PR #39를 만들었고 머지 승인을 기다림 |

4. **보완할 것** — 검토를 요청받았을 때만. 항목마다 근거와 제안을 쓴다.
5. **사용자가 할 일** — 사용자 대기·제안 노드마다 한 줄(어디서 무엇을). 결정이면 권장안을 함께 쓴다. 없으면 「없음」.

요청이 그 밖의 설명이나 형식을 원하면 더한다.

## 자주 하는 실수

| 실수 | 대신 이렇게 |
| --- | --- |
| 이전 버전을 읽지 않고 처음부터 다시 그린다 | json과 이전 순서도 파일을 먼저 읽는다 |
| 하위 세션 보고만 보고 done으로 바꾼다 | 원본 데이터를 다시 확인한다 |
| 검토를 요청받고 상태만 옮겨 적는다 | 계획·달성 조건과 대조해 「보완할 것」을 쓴다 |
| 제외된 노드를 말없이 없앤다 | 변경표에 「제외 · 이유」로 남긴다 |
| 보여 준 버전을 저장하지 않는다 | json에 버전을 더하고 순서도 파일을 남긴다 |

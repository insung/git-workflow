# 프로젝트 브랜치 전략 초기화

선택한 프로젝트의 전략 문서와 읽기 경로만 제안·적용한다. 초기화 자체로 브랜치 생성·이름 변경·삭제, PR 생성·머지, 보호 설정, 배포 자동화와 플러그인 설치를 수행하지 않는다.

## 관행 확인과 제안

1. 대상 프로젝트의 절대 경로와 저장소를 확인한다. 적용되는 AGENTS.md, README·기여 안내·기존 정책 정본, 브랜치·최근 통합 이력·열린 PR, 배포 workflow·태그를 읽는다. 원격 접근 불가나 오래된 원격 참조는 미확인으로 보고한다. 이력은 관행의 근거이며 승인된 정책과 구별한다.
2. 먼저 확인된 관행을 요약한다. 「기존 프로젝트에서는 이렇게 진행한 것으로 보인다. 이 관행을 유지할지, 바꾸고 싶은 부분이 있는지」를 확인한다. 모든 정책 필드를 처음부터 입력하도록 요구하지 않는다. 사용자가 원하는 전략이 있으면 기존 관행과의 차이, 이번 작업에 필요한 미정 결정만 묻는다.
3. [전략 후보](branch-options.md)를 기존 관행과 비교한다. 기존 관행 유지, GitHub Flow, Trunk 기반, Release Flow, Gitflow, 기존 dev·feature·prod·hotfix 중 선택할 수 있다. 후보 이름 선택은 기록 승인이나 실제 브랜치 전환 승인이 아니다. 진행 중인 브랜치·PR와 배포에 미칠 영향을 설명한다.
4. 일반 작업의 base·이름·PR 대상·머지 방식, hotfix의 실제 운영 기준·첫 반영·역반영 경로, 배포 트리거·커밋·태그·롤백 기준을 전략안으로 제시한다. 불필요한 배포 항목은 해당 없음, 모르는 항목은 미정과 보류할 행동을 쓴다. 배포되지 않는 저장소에 prod·release를 강제하지 않는다.

## 정본 위치와 최소 연결

기존 승인된 정책 정본 재사용을 우선한다. 없으면 `BRANCH-STRATEGY.md`를 제안하되 사용자가 원하는 README 지정 절이나 다른 기존 문서도 가능하다. AGENTS.md 직접 기록은 일반·긴급 수정·미정 처리를 몇 줄로 충분히 표현할 수 있는 간단 전략에만 제안한다. 상세 후보 설명·배포 정책은 별도 정본에 두고 AGENTS에는 연결만 둔다. 정본을 여러 문서에 복제하지 않는다.

아래 내용은 완성 문서의 작성 항목이며 별도 plan/task 파일 생성 템플릿이 아니다.

| 항목 | 승인안에 쓸 내용 |
| --- | --- |
| 정본·범위 | 프로젝트 상대 경로와 지정 절, 적용 저장소와 기존 문서의 연결 |
| 일반 작업 | 실제 통합 브랜치, 작업 base·이름·PR 대상·머지 방식 |
| 긴급 수정 | 운영 기준 커밋/브랜치 확인 방법, 첫 반영과 역반영 대상·순서 |
| 배포 | 실제 트리거·대상 커밋·태그·롤백, 해당 없음 또는 미정 |
| 미정·충돌 | 필요한 결정과 결정 전 보류할 행동 |

외부 정본의 AI 읽기 경로는 적용되는 AGENTS.md에 다음 정도의 짧은 추가안을 제안한다. 실제 프로젝트 상대 링크와 절로 바꾼다.

```markdown
## 브랜치 전략

브랜치 생성·PR 대상 결정·hotfix 작업 전에 [브랜치 전략](BRANCH-STRATEGY.md)을 읽고 따른다.
규칙이 충돌하거나 필요한 항목이 미정이면 관련 행동 전에 확인한다.
```

간단 전략을 AGENTS.md에 직접 기록한다면 일반 작업·hotfix 경로·미정 시 확인만 최소 줄로 제안하고 다른 정본을 만들지 않는다. 전략 선택에 필요한 조건이나 정책 필드를 생략하여 최소화하지 않는다. AI 연결을 거절하면 정본 기록과 읽기 경로 미연결을 별도로 보고한다. AGENTS.md 채택 선언 항목을 선택하지 않아도 전략의 최소 연결을 별도로 제안할 수 있으나, 선언 전체를 함께 추가하지 않는다.

## 승인과 보존

1. 쓸 필요가 있는 모든 파일의 **절대 경로, 추가·수정할 전문, 정확한 위치, 구분 줄바꿈, 기존 내용과 차이**를 제시한다. 파일 부재 상태도 기록한다. README는 기본적으로 기존 바이트를 보존하여 승인한 새 절만 추가한다. 기존 절 수정이 필요하면 그 수정 diff를 별도 제시하고 해당 수정의 명시적 승인을 받는다.
2. 전략안과 모든 문서 변경안의 **명시적 승인**을 기다린다. 최초 init 요청, 후보 선택, 응답 없음은 쓰기 승인이 아니다. 일부 승인이나 읽기 연결 거절은 승인된 부분에만 적용한다. AGENTS도 경로·전문·위치 승인이 필요하다.
3. 같은 전략이나 같은 뜻의 읽기 연결이 이미 있으면 중복 추가하지 않는다. 일부 누락이면 누락만 제안한다. 기존 규칙과 충돌하면 내용을 덮어쓰거나 정본을 새로 복제하지 않고 해결안을 승인받는다.
4. 적용 직전 **대상 파일 모두를 다시 읽고** 제안 당시의 존재·내용·링크 대상 상태와 비교한다. 생성·삭제·동시 수정이 있으면 쓰기를 보류하고 새 상태의 경로·전문·위치·차이를 재제시하여 재승인받는다. 승인 당시 같았던 파일에만 승인한 추가·수정을 적용하고 그 외 바이트는 보존한다.
5. 적용 후 기존 바이트 보존, 승인한 전문·위치, 단일 정본과 유효한 읽기 링크, 동일 재초기화 시 무변경을 확인한다. 선택하지 않은 항목은 변경하지 않는다. 결과는 정본 기록·읽기 연결·미정·미실행으로 구분한다.

문서 존재나 패키지 검사만으로 AI 준수를 완료 처리하지 않는다. 스킬 이름 없는 일반 브랜치·PR 대상·hotfix 요청에서 [정본 읽기](../../git-workflow/references/project-branch-policy.md)와 실제 정책 적용을 실행하여 확인한다. 실행하지 못하면 미검증과 호스트 조건을 보고한다.

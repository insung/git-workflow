# v0.9.0 — Issue·PR 기록 통합과 변경 맥락 추적

계획과 실행 결과를 Issue·PR에 모으고, 코드에서 요청·결정의 근거를 추적할 수 있다. PR 피드백 처리·회신과 버전별 마일스톤 확인을 기존 작업 흐름에 연결한다.

## 기능·개선

- 새 작업의 계획·상세 설계·독립 작업 계약을 Issue에 기록한다. 구현·검증·검토 결과는 PR 또는 요청 범위의 대화에 남기며 신규 plan/task/handoff/review 파일을 생성하지 않는다. 기존 작업 기록은 보존한다. [PR #50](https://github.com/insung/git-workflow/pull/50)
- 계획 작성과 sub-issue 분해는 issue-create, 구현·검증·인계는 git-workflow로 통합한다. 기본은 Issue 하나이며 독립 완료·검증과 별도 추적 필요가 함께 있을 때만 분해한다. 부모 완료는 자식 상태뿐 아니라 전체 AC·통합 검증·전달 결과를 대조한다. [PR #50](https://github.com/insung/git-workflow/pull/50)
- pr-comment-check에서 PR·연결 Issue의 요청을 확인하고 승인된 처리와 원래 스레드 회신을 이어갈 수 있다. 조회만 요청하면 조회·판단까지만 수행한다. 페이지 누락·조회 실패·대상 HEAD 변경은 확인 불완전으로 처리한다. 미제출 리뷰는 보고하되 처리 대상에서 제외한다. [PR #47](https://github.com/insung/git-workflow/pull/47)
- 수정 결과 답글은 반영·부분 반영·미반영·이미 충족을 구별하고 작성 AI와 실제 근거를 기록한다. 중복 답글을 확인하고 게시 뒤 실제 응답 필드를 재조회한다. 회신 게시와 스레드 resolve는 각각 승인 범위를 따른다. [PR #47](https://github.com/insung/git-workflow/pull/47)
- git-history로 코드의 동작 기원에서 커밋·PR·Issue·문서의 요청과 결정까지 읽기 전용으로 추적한다. Refs 부재, squash·merge·rename, 후속 변경, 유사한 무관 후보와 접근 제한을 구별한다. [PR #48](https://github.com/insung/git-workflow/pull/48)
- Issue 기반 새 커밋에 실제 관련 Issue를 Refs 푸터로 남긴다. 다른 저장소·host를 구별하고 출처 참조에 자동 종료 키워드를 사용하지 않는다. Issue 없는 작업에는 Refs를 요구하지 않는다. [PR #42](https://github.com/insung/git-workflow/pull/42)
- workflow-init에 마일스톤 운영 설정을 독립 선택 항목으로 추가한다. 목표 버전이 확인된 Issue를 연결하고 기존 마일스톤 메타데이터를 보존한다. 릴리즈 준비에서는 확정 범위 완료·100%와 실제 대상 커밋 포함을 대조한다. 이월과 마일스톤 종료는 별도 승인 범위다. [PR #52](https://github.com/insung/git-workflow/pull/52)

- PR 작성 스킬의 호출을 pr-create에서 pr-request로 바꾼다. 기존 PR 작성·Issue 연결·검증·리뷰 인계 절차를 유지하며 이전 이름의 호환 진입점은 제공하지 않는다. [PR #54](https://github.com/insung/git-workflow/pull/54)
- 답글은 직접 요청의 결과·이유·필요한 검증을 중심으로 간결하게 작성하고, 질문·기록 위치 제안도 각각 판단한다. 대상·HEAD·작성자·부모의 내부 검증은 유지한다. [PR #55](https://github.com/insung/git-workflow/pull/55)
- 순수 릴리즈 준비 PR은 버전·노트·발행 메타데이터 범위와 실제 요청·검증 기록을 충족하면 별도 Issue 없이 전달할 수 있다. 프로젝트의 명시적 Issue 필수 정책은 우선한다. 새 동작·정책·기록 정리 등의 추가 작업은 같은 전달 단위면 릴리즈 Issue에 기록하고, 독립 추적이 필요하면 별도 Issue를 연결한다. git-history는 복합 이슈의 개별 요청·결정·AC와 실제 변경을 대조한다. [Issue #56](https://github.com/insung/git-workflow/issues/56)

## 수정

- issue-close에서 실제 검증 근거로 충족된 task 항목을 별도 승인 없이 체크한다. 미충족·미확인 항목은 completed 종료를 막는다. [PR #44](https://github.com/insung/git-workflow/pull/44)
- 머지 PR의 원격 head 삭제를 pr-merge에서 issue-close로 옮긴다. 열린 Issue의 completed 종료 승인 후 안전 조건을 충족한 원격 head를 삭제한다. 이미 닫힌 Issue의 삭제는 별도 확인하며 로컬 브랜치·dirty·공유·보호할 작업은 보존한다. Closes 없이 본문으로 연결된 머지 PR도 조회한다. [PR #44](https://github.com/insung/git-workflow/pull/44)

## 전환 안내

- pr-create 호출은 pr-request로 전환한다.
- plan-create 호출은 issue-create의 계획 작성·보완으로, task-implement 호출은 git-workflow의 구현 요청으로 전환한다. 외부에서 이전 reference 경로를 직접 연결했다면 새 위치로 갱신한다.
- 설치 환경에는 발행 후 플러그인 갱신과 새 세션이 필요하다. workflow-init은 설치된 플러그인의 스킬을 갱신하지 않는다. 소비 프로젝트의 기존 템플릿·AGENTS.md는 별도 갱신 범위를 확인한다.
- 기존 작업 문서를 자동 삭제하거나 과거 기록을 일괄 변환하지 않는다.

## 검증과 근거

- 준비 기준: 공개 v0.8.0 `23720c78720f5e906412a56759684fec93bb1ed2` → 원격 main `48277b8e64ef24c48557b82242d10e2b5b059e28`와 이번 준비 변경. 최종 태그 대상은 준비 PR의 검토·머지 후 결정한다. 위 여덟 기존 PR의 머지 커밋은 기준 main에 포함됐다.
- 이번 준비의 최종 검사와 공개 지침 사례 결과는 준비 PR의 AC별 검증에 기록한다. 설치된 Codex·Claude 캐시·호스트 자동 선택, 실제 GitHub sub-issue 실행과 발행은 이번 준비에서 검증하지 않는다.
- git-history의 기존 합성 시나리오는 변경 전후 모두 핵심 기준을 통과했으므로 탐색 정확도 개선을 주장하지 않는다. 이번 복합 릴리즈 사례도 실행 결과와 지침 명시화를 구별한다.

## 발행 전 남은 조건

- 기존 7개 기능 Issue는 completed 종료됐고 PR #54·#55까지 main에 포함됐다. 이번 준비 Issue #56은 구현·검토·머지와 완료 근거 확인 뒤 종료한다. 발행 시 마일스톤 범위·100%·실제 태그 포함을 다시 대조한다.
- 대상 commit·태그·노트를 제시하고 태그 push·GitHub Release 발행 승인을 확인한다. 공개 Release 제목은 이전 표기 결정에 따라 `v0.9.0`, 본문 첫 헤딩은 핵심 변화의 H2로 편집한다.
- 발행 후 원격 태그·Release와 대상 commit을 확인한다. 마일스톤 종료는 별도 종료 승인 뒤 수행한다. 태그·Release 발행·플러그인 설치는 미실행이다.

# 읽기 쉬운 작업 기록: 개선 전후

아래는 가상 편집 예시다. 번호·커밋·결과는 실제 작업의 증거가 아니다. 다섯 문서가 결론과 다음 행동을 전달하면서 같은 사실을 보존하는 방식을 보여준다. [공통 편집 기준](../../../skills/git-workflow/references/writing-conventions.md#정보-단위와-작성-후-편집), [문서 역할](../../../skills/git-workflow/references/document-links.md#문서별-역할과-읽기-순서)을 적용한다.

## 공통 원문

network 오류에 재시도 안내가 없어 사용자가 앱을 재실행한다. expired 안내는 유지한다. 자동 결제 재전송과 서버 변경은 제외한다. 중복 결제 위험 때문에 버튼은 안내만 한다는 결정이 승인됐다. 사용자는 2026-10-02 앱 v2.1 결제 화면에서 비행기 모드를 켜고 결제 선택 시 「처리 실패」를 확인했다. 오류 분류·안내 문구가 변경됐다. network→retry 검사는 abc1234에서 통과했으나 현재 def5678에서 문구가 바뀌었다. expired assertion과 실기기 재현은 미실행이다. plan/task/handoff는 로컬 미push다. 전달은 앱 업데이트, 롤백은 구현 커밋 revert이며 실행 미확인이다. AC-01은 network 안내, AC-02는 expired 안내 유지다.

## Issue: 문제와 완료 결과

개선 전:

> 오류 분류를 고치고 문구를 바꾸고 단위 테스트를 실행해서 network 안내와 expired 유지를 검증하며 완료하고, 로그 조사와 앱 업데이트도 필요하다. 중복 결제 위험 때문에 자동 재전송은 하지 않는다.

개선 후:

```markdown
## 목표
network 오류에서 재시도 안내를 제공한다. 현재 안내가 없어 사용자가 앱을 재실행한다.

## 기대 동작
network 오류에서 재시도 방법을 안내한다. expired 오류에서는 기존 안내를 유지한다.

## 실제 동작
사용자는 결제 선택 시 「처리 실패」를 확인했다.

## 재현 절차

1. 결제 화면에서 비행기 모드 활성화
2. 결제 선택
3. 「처리 실패」 확인

## 확인한 환경

- 확인한 날짜: 2026-10-02
- 화면: 결제 화면
- 앱 버전: v2.1

## 영향 범위
포함

- 오류 분류와 안내 문구를 변경한다.

제외

- 자동 결제 재전송과 서버 변경은 제외한다.

호환성·운영 영향

- expired 안내를 유지한다.
- 중복 결제 위험 때문에 버튼은 안내만 제공한다는 결정이 승인됐다.

## 달성 조건

- [ ] AC-01: network 오류에서 재시도 안내 제공
- [ ] AC-02: expired 오류의 기존 안내 유지

## 지금 알고 있는 것

- 원인과 수정 후 실기기 결과는 미확인이다.
- 계획 문서는 로컬 미push이며 계획 링크 준비 중이다.
```

AC에는 완료 결과를 남기고 구현 방법과 실행 절차를 plan/task에 둔다. 버그 Issue에서는 재현·환경을 필수 절로 유지한다.

## plan: 목적과 결정 이유

개선 전:

> 분류 변경, 문구 변경, network 테스트 통과, expired 테스트 작성, 앱 배포와 롤백을 모두 진행한다. 안내 버튼은 재전송하지 않고 검토가 필요하다.

개선 후:

```markdown
## 공통 맥락
목적은 오류 종류에 맞는 안내 제공이다. expired 안내와 결제 재전송 금지 결정을 유지한다.

## 결정
| 결정 | 이유 | 상태 |
| --- | --- | --- |
| 버튼은 안내만 제공 | 중복 결제 위험 | 승인 |

## 단계
01 오류 분류 → 02 문구·유지 검증. 검증 실패 시 해당 단계 보완.

## 전달과 롤백
앱 업데이트로 전달. 롤백은 구현 커밋 revert, 실행 미확인.
```

공통 목적·판단은 plan이 공유하고, 실제 검사 통과 이력은 task/handoff에 둔다. AC ID는 Issue가 정본이다.

## task: 기대와 실제 실행

개선 전:

> 분류와 문구를 구현했고 network 테스트도 통과했으므로 완료다. expired와 실기기는 나중에 확인한다.

개선 후:

```markdown
## 작업
| 작업 | 완료 | 처리 내용 |
| --- | --- | --- |
| 오류 분류·문구 변경 | [x] | 현재 def5678, 문구 재변경 |
| expired assertion 작성 | [ ] | 대응 테스트 누락 |

## 검증
| 사례·AC | 기대 | 실제 |
| --- | --- | --- |
| TC-01·AC-01 | network→retry 안내 | 현재 def5678 미실행; abc1234 통과는 과거 이력 |
| TC-02·AC-02 | expired 안내 유지 | assertion 누락·미실행 |
| TC-03·AC-01 | 실기기 network 안내 | 미실행 |
```

문구를 다시 바꾼 현재 HEAD의 검증 상태와 과거 통과를 분리한다. 실행 명령·환경·시각은 handoff에 연결하며 모르는 값을 만들지 않는다.

## PR: 변경 결론과 위험

개선 전:

> 오류 분류를 고쳤고 문구를 바꿨고 검사를 실행했고 기존 안내도 유지하며 상세 명령은 plan과 task와 handoff에 있다. 원격 링크는 곧 추가하고 앱 업데이트로 배포한다.

개선 후:

```markdown
## 관련 작업
로컬 Issue 초안, AC-01·AC-02. plan/task/handoff 미push, 확인된 원격 링크 없음. 원격 Issue 연결 전 local-pr-draft.

## 변경
network 재시도 안내를 위한 오류 분류·문구 변경. expired 안내 유지 범위.

## 확인
현재 def5678 검증 미실행. abc1234의 network→retry 통과는 이력. expired assertion 누락·실기기 미실행. 상세는 로컬 handoff.

## 위험
중복 결제 위험 때문에 자동 재전송 제외. 서버 변경 없음. 앱 업데이트 전달, 구현 커밋 revert 롤백은 실행 미확인.
```

기존 저장소 템플릿의 절 이름을 유지하고 필수 정보는 같은 뜻의 절에 배치한다. 미push 문서에 가짜 원격 URL을 붙이지 않는다.

## review: 독립 판정과 필요한 조치

개선 전:

> 작업 1 분류 구현 완료, 작업 2 문구 구현 완료, 작업 3 network 테스트 통과, 작업 4 expired 미완료, 실기기 미완료, plan대로 구현했으며 검토가 필요하다.

개선 후:

```markdown
결과: fail. AC-02 대응 assertion을 추가하고 현재 HEAD에서 재검증 필요.

- 검토 HEAD: def5678
- 근거: 현재 정적 diff·task 기록. 실제 diff를 확인한 범위를 명시
- 한계: 런타임 증거 없음; abc1234 통과는 현재 문구 증거 아님

## 지적

- AC-02: expired 유지 assertion 없음. 유지 동작을 고정할 테스트 추가 필요.

## 독립 대조
| AC·시나리오 | 근거 | 판정 |
| --- | --- | --- |
| AC-01 network 안내 | 분류·문구 변경, abc1234 검사 이력 | def5678 미검증 |
| AC-02 expired 유지 | assertion 없음 | 테스트 누락 |

## 다음 행동
구현 담당은 assertion·현재 실행 증거 보완. 리뷰 담당은 새 HEAD 고정 후 재검토. 머지 승인 별도.
```

실제 review에서는 구현·assertion 위치와 실행 근거를 연결한다. 문제가 없는 경우도 대상 HEAD·판정·근거·한계를 남기며 task 표를 복사하지 않는다.

## 보존 확인과 인계

| 원문 정보 | 개선 후 위치 |
| --- | --- |
| 문제·목표·AC-01/02 | Issue |
| 포함·제외·중복 결제 결정과 이유 | Issue 핵심 맥락·plan 결정·PR 위험 |
| 날짜·v2.1·화면·비행기 모드·「처리 실패」 | Issue 재현 |
| abc1234 통과·def5678 변경·expired 누락·실기기 미실행 | task·PR 확인·review 한계 |
| 로컬 미push·원격 링크 없음 | Issue 상태·PR 관련 작업 |
| 앱 업데이트·revert·실행 미확인 | plan 전달·PR 위험 |

구현은 Issue → plan 공통 맥락 → 담당 task → handoff·공개 지적 순서로 읽고 보완 결과를 반환한다. 리뷰는 Issue → plan → diff·task·handoff → 독립 기준·입력 순서로 읽고 판정·조치를 반환한다. 조정은 Issue → plan → 역할별 결과를 읽고 의존성·통합 상태·다음 담당을 연결한다. 모든 역할은 중복 결제 위험으로 정한 재전송 금지 판단을 공유한다. 독립 입력은 구현자에게 전달하지 않는다.

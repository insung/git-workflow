# Issue 중심 기록 예시

이 문서는 가상 작성 예시다. 번호·파일·명령·commit·결과는 실제 실행 증거가 아니다. 현재 작업에 적용할 때 조사·승인·실행한 값으로 바꾼다. [현재 기록 규칙](../../../skills/git-workflow/references/document-links.md)을 따른다.

## 모호한 요청

요청 원문: “검색이 느려. 개선해줘.”

- 사용자 보고: 검색 지연. 실제 시간·조건·원인 미확인
- 남은 결정: 어떤 검색의 어떤 지연을 줄일지. 목표 수치는 사용자와 미합의
- 조사: 코드·현재 측정 근거부터 확인
- 작성 금지: 확인 없이 “인덱스 누락이 원인”, “캐시 도입 승인”, “200ms 이하” 확정

원문을 독립 절에 인용하고 참고 링크가 없으면 `확인된 참고 링크 없음`을 남긴다. 의도·범위·AC가 부족하면 issue-incomplete이며 합의된 구현 계획으로 넘기지 않는다. 필요한 질문만 하며 모든 빈 칸을 AI 추정으로 채우지 않는다.

## 단순 작업의 Issue

```markdown
## 목표

저장 버튼의 오타를 바로잡는다.

## 사용자 요청 원문

> 저장 버튼의 오타를 고쳐줘. 저장 동작은 유지해.

## 현재 동작과 변경 후 동작

현재 label은 `저쟝`이다. 변경 후 `저장`을 표시한다.

## 영향 범위

직접 변경: ui/save-button.ts의 label.
제외: 저장 handler 변경.
서버·데이터 영향: 조사한 label 변경 범위에서 없음.

## 달성 조건

- [ ] AC-01: 버튼에 `저장` 표시
- [ ] AC-02: 기존 저장 동작 유지

## 계획

label만 교정한다.
검증: AC-01은 label 값, AC-02는 기존 handler 사례로 확인한다.
전달: 코드 변경으로 전달한다. 앱 적용 경로는 미확인이다.
서버 배포는 서버 변경이 없어 해당하지 않는다.
롤백: label 변경을 되돌린다. 실행 여부는 미확인이다.

## 참고 링크

확인된 참고 링크 없음
```

이 예제에서는 사용자 요청과 두 AC가 합의됐다는 전제를 둔다. 실제로 미합의면 제안으로 표시한다. 단일 결과·역할이라 별도 plan/task/handoff를 생성하지 않는다. 공개 AC·계획과 기존 검사로 판정 방법이 충분하다고 메인이 확인하면 별도 검토 입력·리뷰 위치 없이 진행한다. 채택된 메인·구현자 역할 분리는 작은 작업에도 유지한다. 검증 방법·명령은 실제 프로젝트에서 확인한 것만 보완한다.

## 실제 결과를 담는 PR

가상 제공 결과: 코드 `abc1234`, label·기존 handler 검사 4개 통과, 실기기 접근 불가. 이 결과를 실제 저장소 검증으로 주장하지 않는다.

```markdown
## Issue와 해결 범위

관련 Issue: 가상 #901. 실제 원격 연결 미확인.
해결 범위: AC-01·AC-02.

## 변경 내용

저장 버튼은 `저장`을 표시한다. label만 교정했다.

## 완료 조건 확인과 검증 근거

대상: 가상 abc1234, base 미확인.
AC-01: 제공된 label assertion 통과.
AC-02: 제공된 handler 검사 통과.
총 4개 검사 통과는 가상 입력의 결과다. 실행 명령·환경·시각은 미제공이다.
실기기 검증은 기기 접근 불가로 미실행이다.

## 위험·배포·다음 조치

실제 기기의 표시와 저장 흐름은 미확인이다.
서버 변경이 없어 서버 배포는 없다. 앱 적용·배포 완료는 미확인이다.
label 역변경으로 되돌릴 수 있지만 실제 롤백은 미실행이다.
실행 명령·환경·시각과 실기기 결과를 확보해 검토한다.
```

PR에 Issue 원문·전체 계획·제약을 복사하지 않는다. 실행 증거 부족은 숨기지 않으며 handoff 파일 부재만으로 입력 부족이라 하지 않는다.

## 복잡하지만 하나의 결과인 경우

로그인 API·화면·테스트를 하나의 PR과 전달 단위로 완료하면 Issue 하나의 계획에 실행 순서와 상세 설계를 기록한다. 코드·테스트·사용 안내를 단계별 sub-issue로 나누지 않는다. 기존 task 문서가 5개여도 새 결과의 독립 추적 필요를 다시 판단한다.

## 독립 결과를 추적하는 경우

API v2와 소비자 전환을 각자 독립 PR·검증으로 전달하고 전환이 API를 기다린다면 상위 Issue 아래 두 sub-issue를 제안한다. 하위 Issue에는 부모 URL·기여 AC와 자체 범위·AC·계획을 기록한다. 포함 관계는 sub-issue, 소비자 전환의 선행 조건은 blocked by 관계로 구별한다.

긴 호환성·데이터 전환·순차 배포·롤백 설계는 부모 본문에 기록하고 하위 Issue에서는 연결한다. 계획만 요청됐다면 구성 초안을 반환하고 생성하지 않는다. 생성과 작업 분해까지 승인됐다면 기존 중복을 확인하고 생성·연결 뒤 관계를 재조회한다.

자식 두 개가 모두 닫혀도 부모의 최종 AC·통합 검증·필수 전달을 확인해야 완료다. 취소된 자식이나 미배포 상태를 진행률로 숨기지 않는다. 분리 기준과 실행 절차는 [Issue 계획](../../../skills/issue-create/references/plan.md)와 [sub-issue](../../../skills/issue-create/references/sub-issues.md)를 따른다.

## 고유 증거

제품 테스트·지속 재현 fixture는 tests 등 기존 경로에 보존한다. 일시 로그는 작업용 임시 경로에 두고 핵심 기대/실제·명령·대상·환경·시각·미실행을 PR에 남긴다. 다시 얻기 어려운 배포/외부 상태의 고유 증거만 필요한 최소 자료로 영구 보존한다. 임시 로그 경로는 공유 근거 링크가 아니다.

## 기존 기록 재개와 문서 허브

기존 plan/task/handoff는 [재개 규칙](../../../skills/issue-create/references/plan.md#기존-작업-재개)에 따라 보존·참조한다. 원격 최신 상태와 당시 기록을 구별한다.

문서 허브에는 기획 링크·현재 구현과 결정 이유·인프라 정의·실제 배포 확인 또는 대기·운영/롤백·Issue/PR 근거를 전달한다. 배포 설정이나 머지만으로 실제 배포를 확인했다고 하지 않는다. 이 예시의 서버 배포 없음은 배포 확인 완료와 다르다.

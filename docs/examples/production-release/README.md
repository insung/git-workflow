# 운영 릴리즈 / Production release

> dev의 통합 변경을 운영에 반영하고 릴리즈 노트를 준비해줘.

## 흐름

릴리즈 범위·관련 Issue 확인 → 필요 시 릴리즈 Issue/plan → dev에서 prod 대상 PR → 통합/회귀·배포/롤백 근거 → pr-review·사용자 승인·pr-merge → 실제 승인된 배포와 사후 확인 → git-release: 이전 릴리즈..선택한 prod 커밋 비교·노트·승인된 발행

## 확인할 경계

- 배포와 태그의 정확한 실행 순서는 실제 프로젝트의 트리거와 정책을 따른다.
- 필수 Issue 연결에는 실제 승인된 릴리즈 범위와 달성 조건이 대응해야 한다.
- GitHub Release·태그만으로 서버 배포를 완료했다고 하지 않는다.
- 배포 실패·복구·태그/Release 발행 상태는 각각 사실에 맞게 기록한다.

## 노트 초안 예시

아래는 가상 결과다. 버전·검사 수는 실제 배포 증거가 아니다. 저장소의 제목·언어·발행 형식이 우선이며, git-workflow에서는 `v버전 — 핵심 변화`를 사용한다.

```markdown
# v1.2.0 — 결제 재시도 안내와 호출명 전환

network 오류에서 재시도 방법을 확인할 수 있다. 안내 호출명은 retry-guide로 바뀐다.

## 기능·개선

- network 오류에서 재시도 방법을 안내한다.

## 수정

- expired 오류의 기존 안내를 유지한다.

## 전환 안내

- retry-help 호출을 retry-guide로 바꾼다.
- 중복 결제 위험 때문에 자동 재전송은 제외한다.
- AGENTS.md 변경은 정확한 경로·추가 전문·위치 승인 후 적용한다.

## 검증과 변경 근거

- 제공된 회귀 검사 결과는 8/8 통과다. 실기기 검증은 미실행이다.
- 이전 공개 v1.1.0 이후의 안내 추가·호출명 변경·기존 안내 유지 변경을 대조했다.
- 확인된 원격 PR·비교 URL이 없으므로 링크는 준비 중이다.
```

`docs`의 호출명 변경과 `refactor`의 기존 안내 유지도 사용자 결과에 영향을 주면 포함한다. PR·커밋 제목을 나열하지 않고 같은 결과를 묶은 뒤 승인·보존 조건을 분리한다. 공개 비교 범위·전환 조치·미검증을 원문과 대조한 초안을 제시하며, 실제 발행은 별도 승인 범위다.

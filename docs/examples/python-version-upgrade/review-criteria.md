# 파이썬 버전 업그레이드 검토 기준

구현 전에 고정한 pr-review 입력이다. 구현 세션은 이 파일과 검증 입력을 읽지 않는다. 이 파일은 `review/draft-python-version-upgrade` 브랜치에 있고, 작업 브랜치의 작업 디렉토리에는 pr-review의 [기록 커밋](../../../skills/pr-review/SKILL.md#7-기록-커밋) 뒤에 나타난다. 보관 규칙은 [검토 기준·검증 입력 양식](../../../skills/plan-create/references/review-criteria.md#보관-위치)을 따른다.

## 사용 방법

1. [handoff.md](handoff.md)와 각 task 파일의 처리 내용·결과를 읽는다.
2. 아래 AC별 기준으로 판정한다. 기계 확인은 직접 다시 실행한다.
3. TC-02는 [review-input-runtime-compat.md](review-input-runtime-compat.md)의 고정 입력으로 다시 실행한다. 구현 세션이 만든 입력과 결과는 참고로만 본다.
4. 우회 확인과 공통 확인을 거친 뒤 [review.md](review.md)에 기록한다.

## AC별 기준

| AC | 기계 확인 (작업 디렉토리) | 판단 질문 | 실패로 보는 예 |
| --- | --- | --- | --- |
| AC-01 | 01 단계에서 확정한 로컬·이미지 실행 명령으로 시작해 출력한 버전이 목표 버전과 같음 (리포 루트) | 선언 파일뿐 아니라 CI·이미지 등 실제 실행 경로가 모두 목표 버전을 쓰는가 | 런타임 선언만 바꾸고 이미지 베이스가 이전 버전인 구현 |
| AC-02 | 격리 환경에서 의존성 설치 후 주요 모듈 import가 종료 코드 0 (리포 루트) | 잠금 파일이 목표 런타임에서 다시 생성한 결과인가 | 설치를 이전 런타임에서만 확인하고 통과로 기록 |
| AC-03 | fixture 회귀 명령이 정상·실패·빈 응답·경계 입력에서 기준 결과와 같음 (리포 루트) | 기준 결과가 변경 전 구현의 산출물인가 | 실패 입력의 기대값을 새 구현의 출력으로 덮어쓴 테스트 |
| AC-04 | 배포 설정 문서에 트리거·사전 점검·롤백 조건·담당이 있음 (`grep`으로 항목 확인) | 확인하지 못한 환경을 확정으로 쓰지 않고 보류로 표시했는가 | 승인 없이 배포를 실행했다고 쓰거나 롤백 절차를 추정으로 채운 문서 |

## 우회 확인

| 확인 | 방법 |
| --- | --- |
| 완료 표시에 근거가 있는가 | task 파일의 `[x]` 행마다 처리 내용의 커밋을 `git show`로 확인 |
| 검증 결과가 실행 근거와 맞는가 | 결과 칸의 실행 커밋과 handoff의 명령·출력이 같은 HEAD인지 확인 |
| 구현 세션의 입력만으로 통과를 주장하는가 | 구현 세션 입력의 결과와 고정 입력 재실행 결과 비교 |

## 공통 확인

| 확인 | 기준 |
| --- | --- |
| 정본 | 같은 규칙이 한 파일에만 있고 다른 곳은 링크 |
| 커밋 | 단계·주제별 분리, 승인 밖 push·PR·Issue 댓글 없음 |
| 기록 | task 처리 내용·결과 칸 작성, 미실행은 미실행, 계획 이탈은 plan 결정과 변경 기록에 존재 |

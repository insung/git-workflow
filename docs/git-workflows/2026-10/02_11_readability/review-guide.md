# 구현 후 review의 작성 방식

현재 구현 리뷰 결과가 아니라, Issue #11에서 적용할 기록 방식이다. 고정 입력·기대 지적은 독립 리뷰 브랜치에 따로 보관한다.

## 판정

전체 판정과 판단 이유를 먼저 기록한다. pass·warn·fail·human-review의 기존 의미는 바꾸지 않는다.

## 지적

한 행에는 하나의 문제만 기록한다. 각 문제의 근거와 필요한 조치를 분리한다.

| 문제 | 근거 | 필요한 조치 |
| --- | --- | --- |
| 하나의 결함 | 해당 위치·관찰 결과 | 하나의 해결 행동 |

## 조건별 결과

Issue의 ID로 충족·미충족·미확인을 표시한다. 달성 조건 전문과 구현 과정을 반복하지 않는다. 결과의 상세 증거는 task·handoff를 연결한다.

## 필요한 맥락

판정을 이해하는 데 필요한 맥락만 기록한다. 예를 들어 과거 테스트만 통과했으면 현재 HEAD의 미검증을 명시한다. 상세 이력은 근거 문서를 연결한다.

## 편집 확인

- 판정·지적·필요 조치가 먼저 드러나는가?
- 한 지적에 서로 다른 문제가 섞였는가?
- 다른 문서의 전문을 반복했는가?
- 근거·미검증·위험이 편집 과정에서 사라졌는가?

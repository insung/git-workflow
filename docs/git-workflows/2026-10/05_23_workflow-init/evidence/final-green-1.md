## B

행동: YAML·의존성·인증 및 조회 성공 확인 → 미리보기 → 누락만 --apply → 재조회. 추가 승인 질문 없음. .github·AGENTS.md 및 기존 라벨 변경 없음. 시뮬레이션에서는 원격 명령을 실행하지 않았으므로 생성 완료로 보고하지 않음.

## C

template-init 호환 진입점으로 템플릿만 처리합니다. 기존 `.github/ISSUE_TEMPLATE/feature_request.md`의 이름과 바이트를 보존하고 대문자 FEATURE_REQUEST.md를 추가하지 않습니다. 없는 BUG_REPORT.md와 PULL_REQUEST_TEMPLATE.md만 정본에서 복사합니다. 기존 파일의 배경↔목표, 완료 기준↔달성 조건은 같은 정보를 요구하므로 누락으로 보고하지 않습니다. 나머지 필수 절은 실제 내용을 대조해 누락 또는 판단 보류와 근거를 보고합니다. 라벨 미확인: remote 없음.
행동: 저장소·작업본 및 다른 PR 템플릿 위치 확인 → 없는 두 정본만 설치 → 기존 파일 diff와 의미 대응 보고. AGENTS·라벨·릴리즈 설정 및 커밋·push 없음. 시뮬레이션에서는 실제 복사하지 않음.

## D

agents-init 호환 진입점으로 선언만 제안합니다.
대상: `/fixture/project/AGENTS.md`
추가 위치: 기존 파일 끝. 기존 바이트는 보존하고, 기존 끝부분과 선언 사이가 빈 줄 하나로 구분되도록 필요한 줄바꿈을 추가합니다.
추가 전문:
```markdown
## Git workflow

이 프로젝트는 git-workflow를 따른다.
Issue 생성 → plan 작성 → 별도 에이전트 구현 → 메인 독립 검증 → PR 검토 → 사용자 승인 후 머지 → Issue 종료 순서로 진행한다.

- 메인 에이전트는 Issue·plan, 구현 위임, 검증, PR 생성·검토, 승인 후 머지와 실제 머지 확인 뒤 Issue close·결과 기록을 조정한다. 직접 구현하지 않으며, 구현 전에 검토 기준·검증 입력을 고정하고 고정 상태를 확인한다. 고정이 미확인이면 구현 위임을 보류한다.
- Issue 기반 구현 요청에서는 이전 대화를 상속하지 않는 별도 구현 에이전트를 생성해 승인된 단계를 반복 지시 없이 위임한다. 위임 메시지에 공통 목적·유지할 결정·담당 범위와 읽기 순서(Issue → plan 공통 맥락·결정·단계 → 담당 task → handoff·공개 리뷰 지적)를 반드시 명시한다. 비공개 검토 기준·검증 입력은 구현자에게 전달하지 않는다.
- 구현 에이전트는 task-implement에 따라 구현·자체 테스트·결과 인계를 담당한다. 메인은 인계 결과를 고정 기준으로 독립 검증하며, 실패하면 구현자에게 수정을 위임한 뒤 재검증한다.
- 기본 역할 분리와 단계 진행은 요청 범위와 행동·대상별 승인을 따른다. 읽기 전용 질문·Issue 작성만 요청한 경우에는 구현으로 확대하지 않는다.
```
이 추가안에 대한 명시적 승인 뒤 적용합니다. 최초 초기화 요청은 추가안 승인이 아니므로 현재 파일은 변경하지 않습니다.
행동: 기존 지침을 보존하고 정확한 추가안 승인 대기. 템플릿·라벨·릴리즈 설정 변경 없음.

## E

릴리즈 노트 분류 설정만 확인합니다. 기존 `.github/release.yaml`은 release.yml과 같은 네이티브 설정으로 취급하여 보존하고 새 release.yml을 복사하지 않습니다. release-drafter.yml도 보존하며 두 자동화와 정본의 차이·충돌 가능성을 보고합니다. 정본은 documentation을 제외하지 않고 문서·사용 안내 범주에 둡니다. 해당 PR이 실제 동작을 바꾼다면 제목이나 documentation 라벨만으로 성격을 단정하지 않고 기존 분류·자동화와 실제 변경을 확인해 해당 기능/수정 분류를 판단합니다.
행동: 기존 설정과 정본 대조 → 차이와 병합·교체 적용안 제시 → 해당 변경 승인 전 쓰기 없음. 라벨 생성 요청이 없으므로 참조 라벨 누락은 보고만 함. Release·태그 발행 없음.
